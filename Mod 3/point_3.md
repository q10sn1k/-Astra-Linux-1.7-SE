# Модуль 3. Постоянное хранение журналов и фильтрация критических событий

Вся работа выполняется **на одной удалённой Astra Linux Special Edition 1.7 по SSH**, в Bash обычного пользователя с правом выполнять `sudo`. Второй сервер, контейнер, графический интерфейс и команды на вашем компьютере не требуются.

Материал состоит из двух частей:

1. **Подготовка и объяснение инструментов:** пакеты и репозитории, journald, syslog-ng, уровни сообщений, хранение журналов и устройство учебного стенда.
2. **Пошаговая практика:** файл настройки journald, отдельный сборщик syslog-ng, два учебных отправителя, проверка фильтра `crit..emerg`, повторный запуск с сохранением данных и результаты для отчёта.

В задании разрешено моделирование. Здесь настройки journald готовятся в отдельном учебном дереве каталогов, **без применения к системной службе**. Это важно: установка лимита `50M` для рабочего журнала может привести к удалению части старой истории по правилам хранения. Отдельный процесс syslog-ng действительно принимает сообщения и сохраняет их в настоящие файлы на сервере. Перезапуск именно этого процесса позволяет проверить сохранность данных после его остановки.

| Элемент исходного задания | Как выполняется в этой практике |
| --- | --- |
| `/etc/systemd/journald.conf` | Учебный файл `model/etc/systemd/journald.conf` внутри собственного каталога |
| `Storage=persistent`, ограничение размера | Подготовка и проверка текста настройки; состояние рабочего journald читается отдельно |
| `/etc/syslog-ng/syslog-ng.conf` | Своя конфигурация отдельного экземпляра syslog-ng |
| `/var/log/critical_alerts.log` | Файл `server/var/log/critical_alerts.log` внутри стенда |
| Централизованный сбор | Два отправителя с разными метками направляют события одному процессу через личный Unix-сокет |
| Постоянное хранение | Файлы в `/var/lib/astra-point3-UID`, проверка после остановки и повторного запуска сборщика |

Это локальная модель сбора от нескольких источников, а не передача между настоящими сетевыми узлами. Стенд не доказывает включение постоянного режима системного journald и не заменяет промышленную систему аудита. В отчёте это указывается прямо.

Команды вводите по одному блоку, последовательно. При `STOP` или неожиданной ошибке следующий шаг не выполняйте. Многострочные блоки с `EOF` вставляйте целиком. Примеры вывода условные: UID `1000`, пользователь `student`, даты и имена на вашей машине могут отличаться. Не копируйте примеры вывода как команды.

## Часть 1. Подготовка, пакеты и устройство журналирования

### 1. Пакет, пакетный менеджер и репозиторий

Пакет `.deb` содержит файлы программы, сведения о версии и зависимостях. Зависимость — другой пакет, необходимый программе: например, библиотека обработки сообщений. При установке пакета могут выполняться служебные сценарии и запускаться службы.

| Инструмент | Назначение | Что делает в этой практике |
| --- | --- | --- |
| `dpkg` | Ведёт сведения об установленных пакетах | Проверяет завершённость операций |
| `dpkg-query` | Читает пакетную базу | Показывает установленные версии |
| `dpkg-deb` | Читает и распаковывает `.deb` | При необходимости извлекает программу в личный каталог |
| `apt-get` | Работает с пакетами через настроенные источники APT | При необходимости скачивает архивы |
| `apt-cache` | Читает индексы APT | Показывает доступные версии и зависимости |

Репозиторий — источник пакетов с индексом. Источники уже настроены администратором в `/etc/apt/sources.list` и `/etc/apt/sources.list.d/`. APT использует эти сведения для поиска подходящей версии пакета.

`apt-get update` обновляет индексы, `install` устанавливает пакеты, `download` только скачивает указанный архив в текущий каталог. `download` **не устанавливает зависимости автоматически**. `dpkg-deb --extract` распаковывает файлы, но не регистрирует пакет в системе и не запускает его установочные сценарии.

APT и dpkg обычно уже входят в Astra Linux. Устанавливать другой пакетный менеджер не требуется. Репозитории Debian, Ubuntu и другого выпуска Astra к этой машине для упражнения не подключайте. Если разрешённый источник недоступен, сначала нужен доступ к нему или подготовленный комплект пакетов соответствующего выпуска и архитектуры.

Обычная установка `syslog-ng-core` на машине с другим системным сборщиком может затронуть его пакеты. Поэтому основной маршрут использует уже установленную программу; запасной маршрут распаковывает архив в стенд, сохраняя действующие службы.

### 2. Проверьте удалённую систему

```bash
whoami
hostname
cat /etc/astra_version
printf '%s\n' "$BASH_VERSION"
sudo -v
sudo dpkg --audit
```

`whoami` показывает пользователя, `hostname` — машину, `cat` читает файл версии. `printf` выводит строку `%s` и перевод строки `\n`; `$BASH_VERSION` содержит версию Bash. `sudo -v` проверяет административные полномочия, при необходимости запрашивая пароль без отображения символов. `dpkg --audit` ищет незавершённые состояния пакетов, ничего не исправляя.

**Пример результата:**

```text
student
astra-lab
1.7.4
5.0.3(1)-release
```

После успешных `sudo -v` и `dpkg --audit` обычно сообщений нет. Если аудит пакетов сообщает проблему, сначала разберите её. Общий `set -e` в SSH-оболочке не включайте: неожиданная ошибка могла бы завершить сеанс.

Проверьте основные команды:

```bash
command -v apt-get apt-cache dpkg-query dpkg-deb journalctl systemd-cat logger timeout
command -v find findmnt df sort paste ldd stat grep awk sed cmp wc head tail sha256sum
sudo sh -c 'command -v syslog-ng'
```

`command -v` показывает путь к программе. Последняя строка запускает через `sudo sh -c` только проверку поиска: административная программа может находиться в `/usr/sbin`, которого нет в обычном `PATH`.

**Ожидается:** пути к программам. Например, `/usr/sbin/syslog-ng`. Если не найден только syslog-ng, используйте запасной маршрут раздела 4. Если отсутствуют остальные инструменты, сначала потребуется их подготовка из разрешённого репозитория.

### 3. Создайте отдельное место для работы

```bash
LAB_UID="$(id -u)"
LAB_GID="$(id -g)"
LAB_ROOT="/var/lib/astra-point3-$LAB_UID"
LAB_CONFIG="$LAB_ROOT/syslog-ng.conf"
LAB_SOCKET="$LAB_ROOT/run/input.sock"
LAB_CRIT="$LAB_ROOT/server/var/log/critical_alerts.log"
LAB_ALL="$LAB_ROOT/server/var/log/all_training.log"
LAB_TAG_A="point3-a-$LAB_UID"
LAB_TAG_B="point3-b-$LAB_UID"
LAB_TAG_J="point3-journal-$LAB_UID"
LAB_SINCE="$(date --iso-8601=seconds)"
```

`id -u` получает UID, `id -g` — основной GID группы. `$(...)` подставляет результат команды. Остальные строки сохраняют пути и метки в переменных. Кавычки удерживают каждое значение одним аргументом. `date --iso-8601=seconds` сохраняет время начала для последующей выборки журнала. **Ожидается:** отсутствие вывода.

Создайте новый каталог:

```bash
if [ "$LAB_UID" -eq 0 ]; then
    printf '%s\n' 'STOP: используйте обычного пользователя, не root.'
elif sudo test -e "$LAB_ROOT" || sudo test -L "$LAB_ROOT"; then
    printf '%s\n' 'STOP: каталог стенда уже существует; проверьте предыдущую работу.'
else
    sudo mkdir -m 700 -- "$LAB_ROOT" &&
        sudo chown "$LAB_UID:$LAB_GID" -- "$LAB_ROOT"
fi
```

`if / elif / else / fi` выбирают ветку. `-eq` сравнивает числа. `test -e` обнаруживает существующий объект, `test -L` — ссылку, включая повреждённую; `||` означает «или». `mkdir -m 700` создаёт каталог с доступом только владельцу. `chown` передаёт его вашему UID и GID; `&&` выполняет передачу только после успешного создания. `--` завершает разбор флагов.

**Ожидается:** отсутствие сообщений. При `STOP` дальше не идите. Каталог `/var/lib` выбран для данных, которые должны сохраняться между запусками; права администратора понадобились только для создания собственного подкаталога.

```bash
mkdir -m 700 -- "$LAB_ROOT/run" "$LAB_ROOT/report" "$LAB_ROOT/packages" "$LAB_ROOT/tools"
mkdir -p -m 700 -- "$LAB_ROOT/model/etc/systemd" "$LAB_ROOT/server/var/log"
findmnt -T "$LAB_ROOT" -o TARGET,FSTYPE,SOURCE
df -h "$LAB_ROOT"
```

`mkdir` создаёт рабочие каталоги. `-p` создаёт недостающих родителей; доступ ко всему дереву дополнительно ограничивает верхний каталог с правами `700`. `findmnt -T` находит файловую систему, содержащую путь; `-o` выбирает столбцы точки монтирования, типа и источника. `df -h` показывает свободное место в удобных единицах.

**Пример сокращённого результата:**

```text
TARGET FSTYPE SOURCE
/      ext4   /dev/vda1
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        30G   12G   17G  42% /
```

Здесь ничего не форматируется и не монтируется. Если данные попадают на `tmpfs`, это хранилище в памяти: утверждать хранение на диске нельзя. Для такого сервера сначала выберите с администратором доступный постоянный раздел. Для упражнения достаточно нескольких мегабайт свободного места.

### 4. Подготовьте syslog-ng

#### 4.1. Основной маршрут: программа уже установлена

```bash
LAB_BIN="$(sudo sh -c 'command -v syslog-ng' || true)"
LAB_CMD=()
if [ -n "$LAB_BIN" ]; then
    LAB_CMD=("$LAB_BIN")
    "${LAB_CMD[@]}" --version
else
    printf '%s\n' 'syslog-ng не найден: выполните запасной маршрут раздела 4.2.'
fi
```

`-n` проверяет непустую строку. `|| true` допускает отсутствие программы именно при поиске, а не скрывает ошибки её запуска. `LAB_CMD` — массив Bash: хранит команду и её аргументы отдельно. `"${LAB_CMD[@]}"` передаёт элементы без потери границ. `--version` выводит версию и параметры сборки, не запуская сбор событий.

**Ожидается:** например, `syslog-ng 3 (3.19.1)` и дополнительные сведения. Конфигурация ниже рассчитана на syslog-ng 3.19 и новее. При более старой версии не обновляйте работающий системный сборщик ради практики: сначала потребуется подходящий учебный инструмент.

Если версия показана, **раздел 4.2 пропустите**. Наличие системной службы syslog-ng не мешает: учебный процесс получит другие настройки и служебные файлы.

#### 4.2. Запасной маршрут: извлечение программы без системной установки

Этот раздел выполняется только при отсутствии syslog-ng. Посмотрите, что предлагает APT:

```bash
apt-cache policy syslog-ng-core
apt-cache depends syslog-ng-core
```

`policy` показывает установленную и доступную версии с источниками; `depends` — зависимости. **Ожидается:** доступная версия из репозитория вашего выпуска Astra и список библиотек. При `Candidate: (none)` пакета в текущих индексах нет. Не добавляйте случайный репозиторий и не заменяйте системный сборщик.

Если источник корректен, но индексы устарели, можно обновить только сведения APT:

```bash
sudo apt-get update
```

`update` скачивает индексы настроенных источников, но не обновляет установленные программы. **Ожидается:** успешное получение индексов без ошибок подписи и недоступных обязательных источников. При ошибке сначала восстановите доступ к разрешённому репозиторию.

Скачайте архив в стенд:

```bash
( cd "$LAB_ROOT/packages" && apt-get download syslog-ng-core )
```

Скобки запускают подоболочку: её `cd` меняет каталог только для скачивания. `&&` запрещает скачивание, если переход не удался. `download` получает архив указанного пакета без установки. **Ожидается:** строка загрузки и один архив `syslog-ng-core_...deb` в `packages`.

```bash
LAB_DEBS=("$LAB_ROOT"/packages/syslog-ng-core_*.deb)
if [ "${#LAB_DEBS[@]}" -eq 1 ] && [ -f "${LAB_DEBS[0]}" ]; then
    dpkg-deb --field "${LAB_DEBS[0]}" Package Version Architecture Depends &&
        dpkg-deb --extract "${LAB_DEBS[0]}" "$LAB_ROOT/tools"
else
    printf '%s\n' 'STOP: нужен ровно один архив syslog-ng-core.'
fi
```

`*` в имени выбирает скачанный архив. `${#LAB_DEBS[@]}` — число элементов массива, `${LAB_DEBS[0]}` — первый элемент; `-f` проверяет обычный файл. `--field` читает поля пакета, `--extract` распаковывает содержимое в `tools`. Установочные сценарии не выполняются, пакетная база не меняется. **Ожидается:** имя, версия, архитектура и зависимости, затем распаковка без сообщений.

Соберите команду с частными библиотеками и модулями:

```bash
LAB_BIN="$LAB_ROOT/tools/usr/sbin/syslog-ng"
LAB_MODULE_DIR="$(find "$LAB_ROOT/tools" -type f -name libafsocket.so -printf '%h\n')"
LAB_LIBRARY_PATH="$(find "$LAB_ROOT/tools" -name '*.so*' -printf '%h\n' | sort -u | paste -sd: -)"
if [ -x "$LAB_BIN" ] && [ -n "$LAB_MODULE_DIR" ] && [[ "$LAB_MODULE_DIR" != *$'\n'* ]]; then
    LAB_CMD=(env "LD_LIBRARY_PATH=$LAB_LIBRARY_PATH" "$LAB_BIN" "--module-path=$LAB_MODULE_DIR")
    env "LD_LIBRARY_PATH=$LAB_LIBRARY_PATH" ldd "$LAB_BIN"
    "${LAB_CMD[@]}" --version
else
    printf '%s\n' 'STOP: не найдены исполняемый файл или единственный каталог модулей.'
fi
```

`find -type f -name` ищет обычный файл с именем модуля; `-printf '%h\n'` выводит его родительский каталог. Второй поиск собирает каталоги библиотек, `sort -u` убирает повторы, `paste -sd: -` соединяет строки двоеточиями. `-x` проверяет возможность запуска. Проверка `[[ ... != *$'\n'* ]]` запрещает несколько найденных каталогов модулей.

`env` задаёт `LD_LIBRARY_PATH` только запускаемой команде. Переменная указывает загрузчику на частные библиотеки; `--module-path` задаёт каталог модулей syslog-ng. Настройка не экспортируется в вашу оболочку и не применяется к системной службе. `ldd` показывает библиотечные зависимости доверенного исполняемого файла из репозитория Astra.

**Ожидается:** найденные библиотеки и версия программы. Если видите `not found` или ошибку загрузки, пока не продолжайте. Распаковка ядра syslog-ng не заменяет подготовку его библиотечных зависимостей.

Например, **только если отсутствует именно `libivykis.so.0`**, соответствующий пакет можно добавить в частное дерево:

```bash
( cd "$LAB_ROOT/packages" && apt-get download libivykis0 ) &&
    for LAB_DEB in "$LAB_ROOT"/packages/libivykis0_*.deb; do
        dpkg-deb --extract "$LAB_DEB" "$LAB_ROOT/tools" || break
    done
```

`for ... do ... done` обрабатывает скачанный архив; `|| break` прекращает цикл при ошибке. **Ожидается:** скачивание и извлечение библиотеки. Затем повторите предыдущий блок сборки `LAB_CMD`, чтобы обновить список каталогов. Для других отсутствующих библиотек имя пакета определяется по зависимостям именно вашего архива; не подменяйте библиотеку файлом от другой ОС. Модуль может иметь дополнительные зависимости, которые проявятся при проверке конфигурации.

Если получить совместимые зависимости из разрешённого источника не удалось, практическую часть пока выполнить нельзя. Установку пакетов с удалением действующего сборщика этот маршрут не предлагает.

### 5. Как связаны journald и syslog-ng

`systemd-journald` собирает события служб, ядра и приложений в структурированный journal. Его читают через `journalctl`. `syslog-ng` принимает сообщения из настроенных источников, фильтрует и направляет их, например, в текстовый файл. Они могут работать совместно, но способ их соединения зависит от конфигурации конкретной машины.

В учебном syslog-ng источник будет **собственным Unix-сокетом**, а не системным `/dev/log` и не `system()`. Unix-сокет — локальная точка обмена между процессами; сетевой адрес и порт не нужны. Два вызова `logger` с разными метками моделируют два приложения, которые используют один сборщик.

| Уровень | Число | Проходит `crit..emerg` |
| --- | --- | --- |
| `emerg` | 0 | Да |
| `alert` | 1 | Да |
| `crit` | 2 | Да |
| `err` | 3 | Нет |
| `warning` | 4 | Нет |
| `notice` | 5 | Нет |
| `info` | 6 | Нет |
| `debug` | 7 | Нет |

«Выше по важности» означает **меньше числовое значение**. `crit..emerg` включает три уровня, а не только `crit`. Facility, например `local5`, обозначает категорию и не меняет важность. `local5.crit` — категория `local5`, уровень `crit`.

Для реального journald `Storage=persistent` означает предпочтительное хранение в `/var/log/journal`; при ранней загрузке или недоступной записи возможен временный каталог `/run/log/journal`. `SystemMaxUse=50M` ограничивает использование места постоянными файлами журнала с учётом механизма их ротации; это не гарантия ровно 50 MiB и не срок хранения. Настройка не ограничивает отдельный текстовый файл syslog-ng.

Хранение на диске позволяет пережить остановку процесса и, при исправном постоянном хранилище, перезагрузку ОС. Оно само по себе не защищает от удаления администратором, повреждения диска и изменения записей. Рабочая система аудита дополнительно требует правил доступа, сроков хранения, резервирования и проверки доставки. Здесь отрабатываются только настройки и маршрут учебных сообщений.

## Часть 2. Практика: настройки хранения и критические сообщения

### 6. Прочитайте текущее состояние journald

```bash
systemctl is-active systemd-journald.service
sudo journalctl --disk-usage
sudo sed -n '1,120p' /etc/systemd/journald.conf
```

`systemctl is-active` только проверяет состояние службы. `journalctl --disk-usage` показывает занимаемое журналами место. `sed -n '1,120p'` выводит строки с первой по сто двадцатую: `-n` отключает обычный вывод всех строк, `p` печатает выбранный диапазон.

**Пример сокращённого результата:**

```text
active
Archived and active journals take up 24.0M in the file system.
[Journal]
#Storage=auto
#SystemMaxUse=
```

Строка с `#` — комментарий, а не активное присваивание. По одному основному файлу нельзя определить все действующие настройки: могут существовать дополнения, которые его перекрывают. Посмотрите их, если они есть:

```bash
for LAB_D in /usr/lib/systemd/journald.conf.d /run/systemd/journald.conf.d /etc/systemd/journald.conf.d; do
    if [ -d "$LAB_D" ]; then
        sudo find "$LAB_D" -maxdepth 1 -type f -name '*.conf' -print
    fi
done
```

`-d` проверяет каталог; `find -maxdepth 1` ограничивает поиск его непосредственным содержимым, `-print` выводит имена найденных конфигураций. **Ожидается:** список файлов или отсутствие вывода. Их имена и содержимое помогают понять переопределения; наличие файла не подтверждает, что служба уже перечитала его последнюю редакцию.

Наличие постоянного каталога можно проверить отдельно:

```bash
if sudo test -d /var/log/journal; then
    sudo journalctl --directory=/var/log/journal --disk-usage
else
    printf '%s\n' 'Каталог постоянного journal сейчас отсутствует.'
fi
```

`--directory` выбирает каталог чтения. **Ожидается:** объём найденных журналов либо сообщение об отсутствии каталога. Наличие каталога и старых файлов ещё не доказывает текущий режим `Storage=persistent`. Перезагрузка для проверки в этой практике не выполняется.

### 7. Подготовьте учебный journald.conf

```bash
cat > "$LAB_ROOT/model/etc/systemd/journald.conf" <<'EOF'
[Journal]
Storage=persistent
SystemMaxUse=50M
EOF
cat "$LAB_ROOT/model/etc/systemd/journald.conf"
```

`cat > ... <<'EOF'` записывает текст до отдельной строки `EOF`. Кавычки у ограничителя сохраняют текст буквально. `>` создаёт файл или заменяет только этот учебный файл. Второй `cat` показывает результат:

```ini
[Journal]
Storage=persistent
SystemMaxUse=50M
```

`[Journal]` — секция настроек. `Storage=persistent` выбирает постоянный режим, `SystemMaxUse=50M` задаёт учебное ограничение. Пояснения после значения на той же строке не добавляются: комментарии в конфигурациях systemd безопаснее оформлять отдельной строкой, начинающейся с `#`.

Проверьте, что файл содержит именно нужный образец:

```bash
printf '[Journal]\nStorage=persistent\nSystemMaxUse=50M\n' |
    cmp -s - "$LAB_ROOT/model/etc/systemd/journald.conf" &&
    printf '%s\n' 'Учебный journald.conf соответствует образцу; системная настройка не применялась.'
```

`|` передаёт вывод `printf` программе сравнения; `cmp -s` сравнивает молча, `-` обозначает стандартный ввод. `&&` печатает подтверждение только при совпадении. **Ожидается:** указанная строка подтверждения.

Это проверка содержимого учебного файла, а не проверка его применения службой. `systemd-analyze verify` предназначен для unit-файлов и не заменяет проверку настроек journald. Файл не копируется в `/etc`, системный journald не перезапускается, существующие журналы не очищаются.

### 8. Подготовьте конфигурацию отдельного syslog-ng

```bash
cat > "$LAB_CONFIG" <<EOF
@version: 3.19
@module afsocket
@module affile
@module syslogformat

options {
    flush-lines(1);
    stats-freq(0);
    keep-hostname(yes);
    chain-hostnames(no);
};

source s_src {
    unix-dgram("$LAB_SOCKET" perm(0600));
};

filter f_critical { level(crit..emerg); };

destination d_all_training {
    file("$LAB_ALL" perm(0600)
        template("\$ISODATE|\$HOST|\$PROGRAM|\$LEVEL|\$MSG\n"));
};

destination d_critical_alerts {
    file("$LAB_CRIT" perm(0600)
        template("\$ISODATE|\$HOST|\$PROGRAM|\$LEVEL|\$MSG\n"));
};

log { source(s_src); destination(d_all_training); };
log { source(s_src); filter(f_critical); destination(d_critical_alerts); };
EOF
chmod 600 -- "$LAB_CONFIG"
cat "$LAB_CONFIG"
```

В отличие от предыдущего блока, ограничитель `EOF` без кавычек: Bash подставляет наши пути. Перед макросами syslog-ng стоят `\$`, чтобы Bash оставил `$ISODATE`, `$HOST`, `$PROGRAM`, `$LEVEL`, `$MSG` для самого сборщика. В готовом файле обратных косых черт перед `$` уже не будет. `\n` внутри шаблона обозначает перевод строки, который обработает syslog-ng. `chmod 600` разрешает чтение и запись конфигурации только владельцу.

**Ожидается:** показанный текст с вашими абсолютными путями, например `/var/lib/astra-point3-1000/run/input.sock`.

| Фрагмент | Что означает |
| --- | --- |
| `@version: 3.19` | Версия синтаксиса конфигурации |
| `@module` | Явная загрузка модулей сокетов, файлов и формата сообщений |
| `flush-lines(1)` | Передавать записи в файловый вывод без ожидания большого пакета строк; это не гарантия физического `fsync` |
| `stats-freq(0)` | Отключить периодические статистические сообщения экземпляра |
| `keep-hostname(yes)` | Сохранять имя узла сообщения |
| `chain-hostnames(no)` | Не наращивать цепочку имён узлов |
| `source s_src` | Объявить источник с именем `s_src` |
| `unix-dgram(...)` | Принимать локальные сообщения в собственном сокете |
| `perm(0600)` | Ограничить доступ к сокету или создаваемому файлу владельцем |
| `filter f_critical` | Объявить правило отбора трёх критических уровней |
| `destination` | Указать файл назначения и формат строки |
| `log { ... };` | Соединить источник, необязательный фильтр и назначение |

Имена вроде `s_src` и `d_critical_alerts` — ссылки на объекты конфигурации. Они должны совпадать с именами в `log`. В исходном задании `s_src` предполагался существующим; здесь он объявлен явно.

Первый маршрут пишет **все учебные** сообщения в `all_training.log`; второй — только `crit`, `alert`, `emerg` в `critical_alerts.log`. Поэтому мы проверим и прохождение важных сообщений, и исключение менее важных. Запись одного события в два файла ожидаема: маршруты независимы.

Шаблон содержит время, узел, программу, уровень и текст через `|`. Это удобный учебный формат. Реальные сообщения могут содержать такой разделитель, поэтому для произвольных журналов нужен более строгий формат разбора.

### 9. Проверьте синтаксис до запуска

```bash
if [ "${#LAB_CMD[@]}" -eq 0 ]; then
    printf '%s\n' 'STOP: сначала подготовьте команду syslog-ng по разделу 4.'
else
    "${LAB_CMD[@]}" --syntax-only --no-caps --cfgfile="$LAB_CONFIG" &&

```

`--syntax-only` проверяет конфигурацию без запуска сбора; `--cfgfile` выбирает именно наш файл; `--no-caps` отключает управление привилегиями Linux capabilities для запуска от обычного пользователя. Он не выдаёт дополнительных прав. **Ожидается:** `Синтаксис syslog-ng проверен.` Перед ним возможны предупреждения конкретной версии.

При ошибке модулей или библиотек сначала завершите подготовку инструментов. Синтаксически правильная конфигурация ещё не гарантирует доступность путей и доставку сообщений — это проверяется следующим шагом.

### 10. Подготовьте один ограниченный запуск сборщика

Для простоты процесс будет работать по 15 секунд и сам завершаться. Вам не понадобится искать PID и вручную останавливать службу. Функция ниже запускает **только учебный экземпляр**, отправляет сообщения и ждёт его завершения. Сначала вставьте её определение целиком:

```bash
lab_batch() {
    local mode="$1" ready=0 sent=0 rc n runner
    if [[ "$mode" != first && "$mode" != restart ]]; then
        printf '%s\n' 'STOP: допустимы только first и restart.'
        return 1
    fi
    if ! mkdir -m 700 -- "$LAB_ROOT/run/busy"; then
        printf '%s\n' 'STOP: другой запуск или следы прерванного запуска; см. раздел 16.'
        return 1
    fi
    if [[ -e "$LAB_ROOT/run/syslog-ng.pid" || -e "$LAB_SOCKET" || -L "$LAB_SOCKET" ]]; then
        rmdir -- "$LAB_ROOT/run/busy"
        printf '%s\n' 'STOP: служебные файлы уже существуют; см. раздел 16.'
        return 1
    fi
    timeout --signal=TERM --kill-after=5s 15s "${LAB_CMD[@]}" \
        --foreground --no-caps --cfgfile="$LAB_CONFIG" \
        --pidfile="$LAB_ROOT/run/syslog-ng.pid" \
        --persist-file="$LAB_ROOT/run/syslog-ng.persist" \
        --control="$LAB_ROOT/run/syslog-ng.ctl" \
        > "$LAB_ROOT/report/console-$mode.log" 2>&1 < /dev/null &
    runner=$!
    for n in {1..50}; do
        if [[ -S "$LAB_SOCKET" ]]; then ready=1; break; fi
        sleep 0.1
    done
    if [[ "$ready" -eq 1 ]]; then
        if [[ "$mode" = first ]]; then
            logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG_A" --priority local5.info -- 'event=training_info id=1' &&
            logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG_A" --priority local5.warning -- 'event=training_warning id=2' &&
            logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG_B" --priority local5.err -- 'event=training_error id=3' &&
            logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG_A" --priority local5.crit -- 'event=training_critical id=4' &&
            logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG_B" --priority local5.alert -- 'event=training_alert id=5' &&
            logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG_B" --priority local5.emerg -- 'event=training_emergency id=6' && sent=1
        else
            logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG_A" --priority local5.crit -- 'event=after_restart id=7' && sent=1
        fi
    fi
    wait "$runner"
    rc=$?
    if [[ "$rc" -eq 124 ]]; then
        rm -f -- "$LAB_ROOT/run/syslog-ng.pid" "$LAB_SOCKET" "$LAB_ROOT/run/syslog-ng.ctl"
        rmdir -- "$LAB_ROOT/run/busy"
    fi
    if [[ "$rc" -eq 124 && "$sent" -eq 1 ]]; then
        printf 'Пакет %s отправлен; учебный процесс завершён по таймеру.\n' "$mode"
    else
        printf 'STOP: ready=%s sent=%s exit=%s; прочитайте console-%s.log.\n' "$ready" "$sent" "$rc" "$mode"
        return 1
    fi
}
```

**Ожидается:** отсутствие вывода — пока определена только функция.

Разберём её по смыслу:

- `lab_batch() { ... }` сохраняет набор команд под именем. `$1` — первый аргумент вызова; `local` делает переменные внутренними для функции. `return 1` прекращает функцию с признаком ошибки, а не закрывает SSH.
- `[[ ... ]]` проверяет условия Bash; `&&` внутри проверки означает «и». Каталог `busy` служит простым замком: одновременно запускать два экземпляра с одними путями нельзя. `!` отрицает успех команды. `rmdir` удаляет только пустой каталог.
- `timeout ... 15s` ограничивает время процесса. `--signal=TERM` посылает штатный сигнал завершения; `--kill-after=5s` принудительно завершит тот же управляемый запуск, если он не остановится за дополнительные пять секунд. Это не поиск и остановка системного syslog-ng.
- `--foreground` оставляет сборщик под управлением `timeout`. `--pidfile`, `--persist-file`, `--control` задают собственные PID-файл, файл внутреннего состояния и управляющий сокет. Persist-файл syslog-ng не связан с настройкой journald `Storage=persistent`.
- `> ... 2>&1` сохраняет вывод и ошибки в свой файл: поток `2` присоединяется к потоку `1`. `< /dev/null` отключает ввод из терминала. `&` запускает команду в фоне, `$!` получает PID фонового `timeout` для ожидания.
- `for n in {1..50}` делает не более 50 проверок, `sleep 0.1` ждёт одну десятую секунды; `-S` проверяет Unix-сокет. `break` заканчивает поиск готовности.
- У `logger` параметр `--socket` выбирает личный адрес, `--socket-errors=on` включает сообщения об ошибке сокета, `--tag` задаёт метку отправителя, `--priority` — категорию и уровень. `--` завершает флаги; дальше идёт вымышленный текст. Цепочка `&&` прекращает отправку при первой ошибке.
- `wait` ждёт окончания именно запущенной команды. `$?` сохраняет её код: `124` здесь ожидаем, потому что работа остановлена таймером. `137` означает принудительное завершение и не считается успешным результатом упражнения.
- Только после ожидаемого завершения удаляются оставшиеся служебные пути этого запуска. `rm -f` допускает уже отсутствующий файл; путь к логам в эту команду не входит. Наличие `sent=1` подтверждает отправку, но содержимое файлов всё равно проверяется отдельно.

Блок не меняет системную конфигурацию, не читает `/dev/log`, не слушает сетевых портов и не использует `sudo` для запуска демона.

### 11. Отправьте шесть сообщений и проверьте фильтр

Сначала убедитесь, что это первый запуск с пустыми учебными журналами:

```bash
if [[ -e "$LAB_ALL" || -e "$LAB_CRIT" ]]; then
    printf '%s\n' 'STOP: результаты уже есть; повторная отправка изменит ожидаемые количества.'
else
    lab_batch first
fi
```

**Ожидается:** примерно через 15 секунд строка `Пакет first отправлен; учебный процесс завершён по таймеру.` Пока блок выполняется, следующее приглашение Bash не появляется — это нормально.

Теперь сборщик уже остановлен, но файлы доступны:

```bash
cat "$LAB_ALL"
cat "$LAB_CRIT"
wc -l -- "$LAB_ALL" "$LAB_CRIT"
```

`cat` читает файлы, `wc -l` считает строки. **Ожидается:** шесть записей в общем файле и три в критическом. Пример критического файла:

```text
2026-11-03T12:10:01+03:00|astra-lab|point3-a-1000|crit|event=training_critical id=4
2026-11-03T12:10:01+03:00|astra-lab|point3-b-1000|alert|event=training_alert id=5
2026-11-03T12:10:01+03:00|astra-lab|point3-b-1000|emerg|event=training_emergency id=6
6 /var/lib/astra-point3-1000/server/var/log/all_training.log
3 /var/lib/astra-point3-1000/server/var/log/critical_alerts.log
9 total
```

Время, узел, пробелы и обозначения уровня могут немного отличаться. Сообщения `info`, `warning`, `err` должны быть только в общем файле. `crit`, `alert`, `emerg` должны быть в обоих.

Проверьте отсутствие менее важных сообщений в критическом файле:

```bash
if grep -E 'event=training_(info|warning|error) ' "$LAB_CRIT"; then
    printf '%s\n' 'STOP: в критический журнал попало лишнее сообщение.'
else
    LAB_GREP_RC=$?
    if [ "$LAB_GREP_RC" -eq 1 ]; then
        printf '%s\n' 'Менее важные учебные сообщения исключены.'
    else
        printf '%s\n' 'STOP: grep не смог прочитать журнал.'
    fi
fi
```

`grep -E` использует расширенное регулярное выражение, `(info|warning|error)` выбирает один из трёх вариантов. Код `1` означает отсутствие совпадений, код больше `1` — ошибку, поэтому они обрабатываются раздельно. **Ожидается:** `Менее важные учебные сообщения исключены.`

Проверьте оба отправителя:

```bash
grep -F -- "|$LAB_TAG_A|" "$LAB_CRIT"
grep -F -- "|$LAB_TAG_B|" "$LAB_CRIT"
stat -c '%U %a %s %n' -- "$LAB_CRIT"
```

`grep -F` ищет буквальный текст; разделители `|` задают границы метки. `stat -c` выводит владельца `%U`, права `%a`, размер в байтах `%s`, имя `%n`. **Ожидается:** одна запись первого отправителя, две второго, владелец вашей учётной записи и права `600`.

События отправлены не в системный journal: `journalctl -p crit` не обязан их показывать. Это намеренно изолированные сообщения. Никакие учебные `emerg` и `alert` не отправляются в рабочий `/dev/log`.

### 12. Проверьте сохранность после повторного запуска

Сохраните контрольную сумму трёх исходных критических записей:

```bash
sha256sum "$LAB_CRIT" > "$LAB_ROOT/report/critical-before.sha256"
sha256sum --check "$LAB_ROOT/report/critical-before.sha256"
```

`sha256sum` вычисляет SHA-256 содержимого файла. `>` записывает результат с абсолютным путём; `--check` повторно вычисляет сумму и сравнивает. **Ожидается:** `.../critical_alerts.log: OK`. Это проверка неизменности относительно сохранённой суммы, а не защита от злоумышленника, который может изменить оба файла.

Повторный запуск допишет одну новую запись:

```bash
if [ "$(wc -l < "$LAB_CRIT")" -eq 3 ] && [ "$(wc -l < "$LAB_ALL")" -eq 6 ]; then
    lab_batch restart
else
    printf '%s\n' 'STOP: перед повторным запуском ожидаются 3 критические и 6 общих записей.'
fi
```

`wc -l < файл` получает только число строк из содержимого файла, `$(...)` подставляет его в числовое сравнение. **Ожидается:** сообщение `Пакет restart отправлен; учебный процесс завершён по таймеру.`

```bash
head -n 3 -- "$LAB_CRIT" > "$LAB_ROOT/report/critical-original.txt"
LAB_OLD_HASH="$(awk '{print $1}' "$LAB_ROOT/report/critical-before.sha256")"
LAB_NEW_HASH="$(sha256sum "$LAB_ROOT/report/critical-original.txt" | awk '{print $1}')"
if [ "$LAB_OLD_HASH" = "$LAB_NEW_HASH" ]; then
    printf '%s\n' 'Три исходные записи сохранены без изменений.'
else
    printf '%s\n' 'STOP: исходные записи изменились.'
fi
tail -n 1 -- "$LAB_CRIT"
wc -l -- "$LAB_ALL" "$LAB_CRIT"
```

`head -n 3` выбирает первые три строки, `awk '{print $1}'` получает первое поле — сумму. `=` сравнивает строки. `tail -n 1` показывает последнюю строку. **Ожидается:** подтверждение неизменности, событие `event=after_restart id=7`, семь общих и четыре критические записи.

Проверка подтверждает сохранность между двумя запусками отдельного сборщика и дописывание файла. Она не проверяет переживание аварийного отключения питания, перезагрузку всей ОС и применение настроек journald.

### 13. Создайте отдельное некритическое событие в journald

Для знакомства с настоящим journal добавим только информационную учебную запись:

```bash
printf '%s\n' 'event=point3_journal_demo result=training' |
    systemd-cat --identifier="$LAB_TAG_J" --priority=info
sudo journalctl --identifier="$LAB_TAG_J" --since="$LAB_SINCE" --no-pager --output=short-iso
```

`systemd-cat` принимает текст из канала и отправляет в journald. `--identifier` задаёт собственную метку, `--priority=info` — некритический уровень. В `journalctl` та же метка и `--since` выбирают наши события после начала работы; `--no-pager` отключает постраничный просмотр, `--output=short-iso` выбирает текстовый формат времени.

**Ожидается:** строка с `event=point3_journal_demo result=training`. Если сразу пусто, повторите только команду чтения через секунду. Информационная запись останется в journal до удаления по действующим правилам хранения сервера.

Сохраните свою выборку на диск:

```bash
sudo journalctl --identifier="$LAB_TAG_J" --since="$LAB_SINCE" --no-pager --output=json \
    > "$LAB_ROOT/report/journal-training.jsonl"
wc -l -- "$LAB_ROOT/report/journal-training.jsonl"
```

`--output=json` формирует по одному JSON-объекту на строку; `>` направляет их в наш файл от имени текущей оболочки. **Ожидается:** как минимум одна строка. При нуле строк сначала проверьте доставку события.

Это экспорт выбранных записей, а не собственный бинарный journal и не применение `Storage=persistent`. Он сохраняет учебный результат независимо от дальнейшего режима хранения системной службы.

### 14. Подготовьте результаты проекта

#### 3.1. Шаблон конфигурации systemd-journald

Готовый фрагмент:

```ini
[Journal]
Storage=persistent
SystemMaxUse=50M
```

Фактически в упражнении он записан в `/var/lib/astra-point3-UID/model/etc/systemd/journald.conf`. В отчёте подпишите: «Подготовлен учебный файл; параметры к рабочему systemd-journald не применялись». Не указывайте, что системная служба уже переведена в постоянный режим.

#### 3.2. Шаблон конфигурации syslog-ng

Существенные части реально использованного файла можно показать командой:

```bash
sed -n '1,90p' "$LAB_CONFIG"
```

**Ожидается:** источник с собственным сокетом, фильтр `level(crit..emerg)`, два назначения и маршруты. `sed -n` и диапазон строк работают так же, как в разделе 6.

В исходной формулировке рабочий фрагмент выглядел бы так:

```syslog-ng
filter f_critical { level(crit..emerg); };
destination d_critical_alerts { file("/var/log/critical_alerts.log"); };
log { source(s_src); filter(f_critical); destination(d_critical_alerts); };
```

Это **справочный фрагмент для сопоставления**, не дополнительный шаг установки. Перед применением в рабочем файле нужно проверить объявление `s_src`, существующие имена и маршруты, права, ротацию и политику системы. В нашем запуске путь назначения другой и находится внутри стенда.

#### 3.3. Подтверждение выполнения

Для скриншота выполните:

```bash
printf 'Учебная конфигурация journald: %s\n' "$LAB_ROOT/model/etc/systemd/journald.conf"
cat "$LAB_ROOT/model/etc/systemd/journald.conf"
printf '\nКритические события: %s\n' "$LAB_CRIT"
cat "$LAB_CRIT"
wc -l -- "$LAB_ALL" "$LAB_CRIT"
```

**Ожидается:** настройки `persistent` и `50M` в учебном файле, четыре критические записи от двух отправителей, семь общих записей. Фраза «учебная конфигурация» нужна для точного описания выполненного моделирования.

Сохраните также снимок вывода проверки синтаксиса из раздела 9 и подтверждения сохранности трёх строк из раздела 12. Для системного journal подойдёт собственная информационная запись из раздела 13; она показывает другой маршрут, а не работу критического фильтра.

| Проверка | Ожидаемый итог |
| --- | --- |
| Учебный `journald.conf` | `Storage=persistent`, `SystemMaxUse=50M` |
| Проверка syslog-ng | Успешный синтаксический разбор |
| Первый запуск | 6 общих, 3 критические записи |
| Нижние уровни | `info`, `warning`, `err` исключены из критического файла |
| Два отправителя | Обе метки присутствуют в критическом файле |
| Повторный запуск | 7 общих, 4 критические записи |
| Исходные три записи | Контрольная сумма совпадает |
| Рабочие системные настройки | Не изменялись |

### 15. Зафиксируйте файлы отчёта

```bash
cp -- "$LAB_ROOT/model/etc/systemd/journald.conf" "$LAB_ROOT/report/journald.conf"
cp -- "$LAB_CONFIG" "$LAB_ROOT/report/syslog-ng.conf"
cp -- "$LAB_CRIT" "$LAB_ROOT/report/critical-final.log"
sha256sum "$LAB_ROOT/report/journald.conf" "$LAB_ROOT/report/syslog-ng.conf" \
    "$LAB_ROOT/report/critical-final.log" "$LAB_ROOT/report/journal-training.jsonl" \
    > "$LAB_ROOT/report/SHA256SUMS"
sha256sum --check "$LAB_ROOT/report/SHA256SUMS"
```

`cp` копирует явно указанные учебные файлы; `--` завершает флаги. Суммы считаются для итоговых копий и экспорта journal. **Ожидается:** четыре строки с `OK`. Первоначальный файл `critical-before.sha256` относится к трём исходным строкам, поэтому к дописанному журналу из четырёх строк он больше не подходит.

Перед очисткой сохраните нужные скриншоты и результаты. После удаления стенда его файлы отчёта тоже исчезнут. Отчёт не содержит чужих журналов: выборка journal ограничена нашей меткой.

### 16. Если SSH оборвался или запуск завершился ошибкой

1. Подключитесь к той же Astra под тем же пользователем. Повторите блок присваивания переменных из раздела 3, но **не блок создания каталога**. Новое `LAB_SINCE` будет временем повторного входа; для чтения старой собственной записи временно уберите фильтр `--since`.
2. Восстановите `LAB_CMD` по использованному маршруту раздела 4 и повторно определите функцию из раздела 10. Это само по себе не запускает сборщик.
3. Подождите не менее 25 секунд после последнего старта. Учебный процесс ограничен `timeout` значением 15 секунд с дополнительными пятью на завершение. Разрыв SSH может завершить его и раньше.
4. Прочитайте журнал запуска и проверьте собственные процессы:

```bash
tail -n 30 -- "$LAB_ROOT/report/console-first.log"
ps -u "$LAB_UID" -o pid,args | grep -F -- "$LAB_CONFIG"
```

`tail -n 30` показывает последние 30 строк. `ps -u` выбирает процессы вашего UID, `-o pid,args` — PID и командную строку. `grep -F` ищет точный путь конфигурации; сама команда `grep` тоже может попасть в вывод. **Ожидается:** после штатного завершения нет `timeout` и syslog-ng с этим файлом. При разборе смотрите название команды, а не только наличие строки.

Не используйте `killall syslog-ng`, `pkill syslog-ng` и остановку системной службы. Если собственный процесс всё ещё работает, не удаляйте его файлы; сначала разберите вывод и причину с администратором. При ошибке `137` не считайте записи гарантированно сохранёнными.

Только после проверки отсутствия учебных процессов можно удалить оставшиеся служебные файлы и пустой замок:

```bash
if [ "$LAB_ROOT" = "/var/lib/astra-point3-$(id -u)" ]; then
    rm -f -- "$LAB_ROOT/run/syslog-ng.pid" "$LAB_SOCKET" "$LAB_ROOT/run/syslog-ng.ctl"
    if [ -d "$LAB_ROOT/run/busy" ]; then rmdir -- "$LAB_ROOT/run/busy"; fi
else
    printf '%s\n' 'STOP: неожиданный путь стенда.'
fi
```

**Ожидается:** отсутствие сообщений. `syslog-ng.persist` и учебные журналы сохраняются. Этот блок выполняется только при выполненном условии выше — проверке отсутствия процессов. Если первая отправка была прервана, числа могут отличаться от образца: сначала изучите содержимое, не повторяйте пакет `first` поверх неполных результатов с ожиданием тех же чисел.

| Проблема | Что проверить |
| --- | --- |
| `Permission denied` | Владельца каталогов, доступ обычного пользователя, политики Astra; не ставьте `777` |
| Ошибка модуля | Версию программы, `--module-path` в запасном маршруте, зависимости модуля |
| Нет сокета | `console-first.log`, синтаксис и доступность каталога `run` |
| Сокет есть, файл пуст | Результат `logger`, правильность назначения, журнал процесса |
| Попал `err` | Фильтр должен быть `crit..emerg`, а не `err..emerg` |
| Не видно события в `journalctl` | Критические сообщения шли в отдельный сокет; проверяйте учебный файл |
| В journal отсутствует новая `info` | Метку, время, политики ограничения скорости и хранения; повторите чтение |
| Нет прежних journal-загрузок | Это не доказывает неисправность стенда: системный режим хранения здесь не менялся |

### 17. Очистите только учебный стенд

После успешных двух запусков функция уже завершила процессы. Если работа прерывалась, сначала выполните проверки раздела 16. Перед удалением обязательно сохраните нужные результаты.

```bash
if [ "$LAB_ROOT" = "/var/lib/astra-point3-$(id -u)" ] &&
    [ ! -d "$LAB_ROOT/run/busy" ] &&
    [ ! -e "$LAB_ROOT/run/syslog-ng.pid" ] &&
    [ ! -S "$LAB_SOCKET" ]; then
    cd "$HOME" && find "$LAB_ROOT" -mindepth 1 -maxdepth 1 -exec rm -rI -- {} +
else
    printf '%s\n' 'STOP: проверьте путь и отсутствие незавершённого запуска.'
fi
```

`!` отрицает проверку, цепочка `&&` требует соблюдения всех условий. `cd "$HOME"` уводит текущий каталог из удаляемого дерева. `find -mindepth 1 -maxdepth 1` выбирает только непосредственное содержимое стенда, сохраняя верхний каталог. `-exec ... {} +` передаёт найденные пути команде: `{}` обозначает их место, `+` объединяет несколько путей в один вызов. `rm -r` удаляет выбранные деревья рекурсивно; заглавная `-I` запрашивает подтверждение перед рекурсивным удалением или удалением множества файлов. Здесь используется обычная учётная запись, а не root.

**Ожидается:** вопрос о подтверждении удаления содержимого вашего стенда. Проверьте, что перед этим выполнена проверка пути `/var/lib/astra-point3-ваш_UID`, и подтвердите. Пустой верхний каталог удалите отдельно: его родитель `/var/lib` принадлежит root, поэтому на последнем шаге нужен `sudo`.

```bash
if [ "$LAB_ROOT" = "/var/lib/astra-point3-$(id -u)" ]; then
    sudo rmdir -- "$LAB_ROOT"
fi
```

`rmdir` удаляет только пустой каталог и откажется удалять его содержимое. **Ожидается:** отсутствие вывода. Если на предыдущем шаге вы отказались от удаления, `rmdir` сообщит, что каталог непустой; это не повод добавлять рекурсивное удаление с `sudo`. Системные пакеты, службы и реальные журналы остаются на месте; информационная метка из раздела 13 хранится по обычным правилам сервера.

### 18. Ответы на частые вопросы

**Можно ли идти сразу с части 2?** Только если уже выполнены проверки части 1, создан стенд и заполнены переменные, включая массив `LAB_CMD`. Для первого прохождения начинайте с раздела 1 и выполняйте командные блоки с раздела 2; запасной маршрут 4.2 нужен только при отсутствии программы.

**Можно ли просто копировать блоки по порядку?** Да, в Bash удалённой Astra, соблюдая условия перед блоками и проверяя результат каждого шага. Пример вывода не является командой. Не выполняйте запасной маршрут и восстановление, если они не нужны.

**Почему `50M` не ограничивает `critical_alerts.log`?** Параметр принадлежит journald. Текстовому журналу syslog-ng нужна своя политика ротации и хранения. Здесь отправляются только семь коротких сообщений, и фоновый сборщик после пакета останавливается.

**Почему нет перезагрузки?** Для проверки дописывания файла достаточно остановки и повторного запуска собственного процесса. Перезагрузка удалённого сервера затронула бы SSH и другие службы, поэтому в маршрут не включена.

**Можно ли считать исходное задание выполненным буквально?** Это адаптированная лабораторная работа: подготовлен образец настроек journald, реально проверены syslog-ng, фильтрация и сохранение файлов. Перевод рабочего journald в постоянный режим и сбор логов настоящих удалённых узлов не выполнялись. Если требуется именно применение к системной службе, нужен отдельный согласованный сценарий с анализом действующей истории и требований хранения.
