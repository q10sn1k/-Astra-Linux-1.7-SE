# Модуль 3. Настройка системного журналирования и анализ лог-файлов

Вся практика выполняется **на одной удалённой Astra Linux Special Edition 1.7**, к которой вы уже подключились по SSH. Команды вводятся в Bash этой машины. Второй сервер, графическая среда и действия в локальном терминале вашего компьютера не требуются.

Сначала научимся читать системный журнал, находить события службы и различать уровни важности. Затем настроим отдельный экземпляр rsyslog под своей учётной записью: собственный Unix-сокет, свой формат строк и два файла для разных событий. Разберём поиск, подсчёт сообщений, изменение правила, проверку ошибки конфигурации и ротацию с logrotate.

Рабочие службы `systemd-journald`, rsyslog и SSH не перезапускаются. Системные конфигурации читаются для изучения; настройки упражнения находятся в отдельном каталоге. Учебный rsyslog не слушает `/dev/log` и сетевые порты. Системный журнал не очищается, правила хранения реальных журналов не меняются.

Для проверки journald отправим три коротких вымышленных сообщения со своим идентификатором. Они останутся в системном журнале до удаления по обычным правилам хранения этой машины. Все остальные тренировочные события поступят только в наш отдельный сокет.

Примеры вывода условные. В них пользователь называется `student`, узел — `astra-lab`, UID равен `1000`. На вашей машине будут другие имена, даты и PID. Значения из примеров вручную подставлять не нужно. Пароли, ключи, настоящие данные пользователей и рабочие секреты в сообщения не включаются.

## 1. Как проходить практику в SSH-терминале

Копируйте команды по одному блоку, в указанном порядке. Блоки `bash` — команды для выполнения, блоки с примерами результатов — только для чтения. Не добавляйте приглашение вида `student@astra:~$` к команде.

Многострочный блок с `<<EOF` вставляйте целиком, включая отдельную завершающую строку `EOF`. Если из-за неполного ввода Bash показывает `>`, Ctrl+C отменяет незавершённую команду; затем вставьте блок заново. При `STOP` или неожиданной ошибке следующий шаг не выполняйте.

Несколько обычных строк выполняются последовательно: ошибка первой не отменяет следующие автоматически. Зависимые изменения ниже соединены через `&&` и условия. Не включайте общий `set -e` в своей SSH-оболочке: неожиданная ошибка может завершить её.

Основной маршрут — разделы 2–14, затем сохранение результата по разделу 15 и завершение по разделу 17. Раздел 16 нужен только после разрыва SSH. Установку пакетов выполняйте только при отсутствии программ. Непрерывное наблюдение останавливается Ctrl+C; это завершает команду просмотра, а не выключает сервер.

## 2. Как устроено журналирование Linux

### 2.1. Источник, получатель, хранилище и просмотр

| Компонент | Простое объяснение | В этой практике |
| --- | --- | --- |
| Приложение или служба | Создаёт сообщение о событии | Мы отправим вымышленные события |
| systemd-journald | Собирает структурированные записи от служб и других источников | Прочитаем журнал и добавим три своих сообщения |
| journalctl | Показывает записи journal с фильтрами | Выберем загрузку, службу, время, важность и идентификатор |
| rsyslog | Принимает сообщения, проверяет правила и направляет их в файлы или другие назначения | Настроим отдельный процесс и отдельный сокет |
| Текстовый лог | Обычный файл со строками событий | `all.log` и `alerts.log` в личном стенде |
| logrotate | Переименовывает старые журналы, создаёт новые, хранит и сжимает архивы по правилам | Обработает только два учебных файла |

Journal обычно хранится не как обычный текстовый файл. Его читают через `journalctl`, а не редактируют текстовым редактором. Текстовые журналы можно исследовать `tail`, `grep` и `awk`.

Journald и rsyslog могут работать совместно, но конкретная схема передачи событий зависит от настроек системы. Не каждая запись обязана одновременно присутствовать и в journal, и в `/var/log/syslog`. Наш отдельный rsyslog получит только сообщения, явно отправленные в его сокет.

### 2.2. Уровень важности и facility

Чем меньше числовой уровень, тем выше важность:

| Число | Имя | Смысл |
| --- | --- | --- |
| 0 | `emerg` | Аварийная недоступность системы |
| 1 | `alert` | Требуется немедленное действие |
| 2 | `crit` | Критическое состояние |
| 3 | `err` | Ошибка |
| 4 | `warning` | Предупреждение |
| 5 | `notice` | Существенное обычное событие |
| 6 | `info` | Информационное событие |
| 7 | `debug` | Отладочная информация |

Важность выбирает отправитель сообщения. Строка с уровнем `err` — повод исследовать ситуацию, но не самостоятельное доказательство причины сбоя.

Facility — категория сообщения, например `auth`, `daemon`, `user` или `local0`–`local7`. Это не имя файла и не уровень важности. Для собственного сокета выберем `local5`, числовое значение `21`. Например, `local5.err` означает категорию `local5` и важность `err`.

Не отправляйте вымышленные попытки входа с категорией `authpriv` в рабочие журналы авторизации. Для обучения достаточно собственных меток и категорий.

### 2.3. Время, порядок событий и ограничения выводов

Для анализа важны время, часовой пояс, узел, приложение, важность и само сообщение. Записи из разных источников могут приходить с задержкой. Похожие строки не обязательно относятся к одному запросу, а отсутствие строки не всегда доказывает отсутствие события.

В учебном текстовом формате используем время приёма rsyslog с часовым поясом. Действующие журналы могут иметь другой формат и другую временную зону. Уровни, имена полей и даты нужно учитывать при сопоставлении.

## 3. Подготовка удалённой Astra Linux

### 3.1. Проверьте ОС, Bash и полномочия

```bash
whoami
hostname
cat /etc/os-release
cat /etc/astra_version
printf '%s\n' "$BASH_VERSION"
sudo -v
```

`whoami` показывает пользователя, `hostname` — имя машины. `cat` читает указанные текстовые файлы, флагов нет. `/etc/os-release` и `/etc/astra_version` содержат сведения об ОС.

`printf` выводит строковое значение `%s`, `\n` добавляет перевод строки. `$BASH_VERSION` — версия текущей Bash. Двойные кавычки сохраняют значение одним аргументом.

`sudo -v` проверяет разрешённые административные полномочия и обновляет срок их подтверждения. При запросе введите пароль своей учётной записи; символы не показываются. Повышенные права понадобятся для чтения части системных журналов, а не для запуска учебного rsyslog.

**Пример сокращённого результата:**

```text
student
astra-lab
PRETTY_NAME="Astra Linux"
...
1.7.x
5.0.3(1)-release
```

После возможного запроса пароля `sudo -v` обычно молчит. Если версия Bash пустая или выпуск ОС другой, уточните окружение перед продолжением.

### 3.2. Проверьте пакетную базу и программы

```bash
sudo dpkg --audit
command -v journalctl systemd-cat logger grep awk sed sort cut tail gzip zcat nohup readlink
sudo sh -c 'command -v rsyslogd logrotate'
```

`dpkg --audit` ищет незавершённые состояния пакетов, ничего не исправляя. Нормальный результат — отсутствие сообщений.

`command -v` выводит путь к найденной программе. В последней строке `sudo sh -c` выполняет только строку проверки с административным путём поиска: rsyslogd и logrotate могут лежать в `/usr/sbin`, которого нет в обычном `PATH`. Одинарные кавычки сохраняют строку одним аргументом.

**Пример сокращённого результата:**

```text
/usr/bin/journalctl
/usr/bin/systemd-cat
/usr/bin/logger
...
/usr/sbin/rsyslogd
/usr/sbin/logrotate
```

Если какой-то путь отсутствует, программа не найдена. Различие `/bin` и `/usr/bin` либо `/sbin` и `/usr/sbin` допустимо. Если `dpkg` сообщает о проблемных пакетах, не начинайте новую установку поверх них.

### 3.3. Если отсутствуют rsyslog или logrotate

При уже доступных программах этот подраздел пропустите. Для подготовки используйте только разрешённые источники вашей Astra Linux; наличие SSH не означает наличие Интернета или доступа к репозиторию.

```bash
apt-cache policy rsyslog logrotate
sudo apt-get --simulate --no-remove --no-upgrade --no-install-recommends install rsyslog logrotate
```

`apt-cache policy` показывает установленные и доступные версии по имеющимся индексам, не устанавливает ПО. `apt-get install` выбирает пакеты, а `--simulate` только рассчитывает план.

| Параметр | Значение |
| --- | --- |
| `--no-remove` | Прервать операцию, если она требует удаления пакетов |
| `--no-upgrade` | Не обновлять уже установленный явно названный пакет; это не общий запрет изменений всех зависимостей |
| `--no-install-recommends` | Не добавлять необязательные рекомендации |

**Пример структуры результата:**

```text
rsyslog:
  Installed: ...
  Candidate: ...
logrotate:
  Installed: ...
  Candidate: ...
...
0 upgraded, ... newly installed, 0 to remove ...
```

Если индексы отсутствуют или устарели, их получают из уже настроенных источников:

```bash
sudo apt-get update
```

`update` загружает описания пакетов, но не обновляет установленные программы. Флагов нет. **Пример результата:** строки получения индексов и `Reading package lists... Done`. При ошибках доступа не заменяйте источники на Debian или Ubuntu и не меняйте сеть ради упражнения.

Установка rsyslog, если его раньше не было, может подготовить и запустить системную службу. Поэтому на общей ВМ такую подготовку нужно выполнять только в разрешённом порядке. Основной стенд далее использует отдельный процесс и не требует перезапуска рабочего rsyslog.

При ожидаемом плане и разрешённой установке:

```bash
sudo apt-get --no-remove --no-upgrade --no-install-recommends install rsyslog logrotate
```

Убран только `--simulate`: установка настоящая. Ограничивающие параметры сохраняют прежний смысл; до подтверждения снова прочитайте план. Если он затрагивает неожиданные службы или системные пакеты, инструменты должен подготовить администратор.

**Пример сокращённого результата:**

```text
Setting up rsyslog (...) ...
Setting up logrotate (...) ...
```

### 3.4. Посмотрите состояние служб и свободное место

```bash
systemctl is-active systemd-journald.service
systemctl is-active rsyslog.service
df -hT /var /var/tmp
date --iso-8601=seconds
```

`systemctl is-active` только проверяет состояние указанной службы. `active` означает активна, `inactive` — неактивна; при неактивном или неизвестном юните код завершения может быть ненулевым. Здесь ничего не запускается и не останавливается.

`df -hT` показывает использование файловых систем в удобных единицах и их тип. `date --iso-8601=seconds` печатает время сервера с часовым поясом и точностью до секунд, не изменяя часы.

**Пример результата:**

```text
active
active
Filesystem     Type Size Used Avail Use% Mounted on
...            ext4 ...  ...   ...  ... /
2026-10-29T11:00:00+03:00
```

Для упражнения достаточно небольшого объёма места, но на заполненной файловой системе работу не начинайте. Если journald недоступен, его часть нельзя заменить выдуманным выводом. При запрете операций политикой Astra Linux не отключайте защиту; уточните доступ учебной учётной записи.

## 4. Подготовьте собственный каталог

### 4.1. Сохраните пути и метку в переменные

```bash
LAB_UID="$(id -u)"
LAB_BASE="/var/tmp/astra-logging-$LAB_UID"
LAB_TAG="astra-log-$LAB_UID"
LAB_CONFIG="$LAB_BASE/rsyslog.conf"
LAB_CANDIDATE="$LAB_BASE/rsyslog.changed.conf"
LAB_SOCKET="$LAB_BASE/input.sock"
LAB_PIDFILE="$LAB_BASE/rsyslog.pid"
LAB_CONSOLE="$LAB_BASE/daemon-console.log"
LAB_ALL="$LAB_BASE/logs/all.log"
LAB_ALERTS="$LAB_BASE/logs/alerts.log"
LAB_REPORT="$LAB_BASE/report"
LAB_ROTATE_CONF="$LAB_BASE/logrotate.conf"
LAB_ROTATE_STATE="$LAB_BASE/logrotate.state"
LAB_RSYSLOG_BIN="$(sudo sh -c 'command -v rsyslogd')"
LAB_LOGROTATE_BIN="$(sudo sh -c 'command -v logrotate')"
printf '%s\n' "$LAB_BASE" "$LAB_TAG" "$LAB_SOCKET" "$LAB_RSYSLOG_BIN" "$LAB_LOGROTATE_BIN"
```

`id -u` получает UID. `$(...)` подставляет вывод команды; присваивания пишутся без пробелов вокруг `=`. Переменные сохраняют значения для следующих шагов, их не нужно вручную заменять.

| Переменная | Назначение |
| --- | --- |
| `LAB_BASE` | Только наш новый каталог в `/var/tmp` |
| `LAB_TAG` | Идентификатор сообщений, отличающий их от рабочих событий |
| `LAB_CONFIG`, `LAB_CANDIDATE` | Основная и проверяемая конфигурации своего процесса |
| `LAB_SOCKET` | Собственный Unix-сокет для приёма сообщений |
| `LAB_PIDFILE` | Файл с PID только учебного rsyslog |
| `LAB_CONSOLE` | Диагностика запуска самого учебного процесса |
| `LAB_ALL`, `LAB_ALERTS` | Все наши события и отдельно важные |
| `LAB_REPORT` | Сохранённые выборки и результаты анализа |
| `LAB_ROTATE_CONF`, `LAB_ROTATE_STATE` | Собственная политика ротации и её состояние |
| `LAB_RSYSLOG_BIN`, `LAB_LOGROTATE_BIN` | Найденные пути программ |

`sudo sh -c 'command -v ...'` лишь определяет пути. Далее программы запускаются без `sudo`, с вашей учётной записью. `printf '%s\n'` показывает значения по одному на строку.

**Пример результата:**

```text
/var/tmp/astra-logging-1000
astra-log-1000
/var/tmp/astra-logging-1000/input.sock
/usr/sbin/rsyslogd
/usr/sbin/logrotate
```

Если пути программ пусты, подготовка не завершена. Фиксированный короткий путь в `/var/tmp` также позволяет не упереться в ограничение длины пути Unix-сокета.

### 4.2. Проверьте отсутствие каталога и создайте его

```bash
ls -ld "$LAB_BASE"
```

`ls -l` показывает свойства, `-d` — сам каталог. **Ожидаемый результат первого запуска:** сообщение `No such file or directory`. Если каталог уже есть, не перезаписывайте его: восстановите прежний стенд по разделу 16.

```bash
mkdir -m 0700 -- "$LAB_BASE" &&
mkdir -m 0700 -- "$LAB_BASE/work" "$LAB_BASE/logs" "$LAB_REPORT"
ls -ld "$LAB_BASE" "$LAB_BASE/logs" "$LAB_REPORT"
```

`mkdir` создаёт каталоги. `-m 0700` разрешает чтение, запись и проход только владельцу. `--` завершает список параметров. Флага `-p` нет: существующий путь обнаруживается как ошибка. `&&` не создаёт вложенные каталоги при ошибке создания основного.

**Пример результата:**

```text
drwx------ ... student student ... /var/tmp/astra-logging-1000
drwx------ ... student student ... /var/tmp/astra-logging-1000/logs
drwx------ ... student student ... /var/tmp/astra-logging-1000/report
```

В этих действиях `sudo` не используется. Родительский каталог защищает сокет и учебные файлы от других обычных пользователей. Политики безопасности Astra Linux продолжают действовать дополнительно.

## 5. Чтение системного журнала journalctl

### 5.1. Посмотрите последние события текущей загрузки

```bash
sudo journalctl --boot=0 --lines=20 --no-pager --output=short-iso
```

| Параметр | Что делает |
| --- | --- |
| `--boot=0` | Выбирает текущую загрузку ОС |
| `--lines=20` | Ограничивает вывод последними 20 подходящими записями |
| `--no-pager` | Выводит сразу в терминал, без программы постраничного просмотра |
| `--output=short-iso` | Время и короткая строка события в формате, удобном для сопоставления |
| `sudo` | Даёт доступ к системным записям в пределах разрешённых полномочий |

**Пример структуры результата:**

```text
2026-10-29T11:00:00+0300 astra-lab systemd[1]: ...
2026-10-29T11:00:01+0300 astra-lab ...: ...
```

Записи будут настоящими для вашей машины. Не ожидайте буквального совпадения текста с примером. Чтение журнала не перезапускает службы.

### 5.2. Посмотрите известные загрузки и объём журнала

```bash
sudo journalctl --list-boots --no-pager
sudo journalctl --disk-usage
```

`--list-boots` показывает доступные загрузки с их идентификаторами и временными границами. `--no-pager` отключает постраничный просмотр. `--disk-usage` показывает объём доступных файлов journal, а не очищает их.

**Пример сокращённого результата:**

```text
 0 ... Thu 2026-10-29 ... — Thu 2026-10-29 ...
Archived and active journals take up ... in the file system.
```

Если видна только текущая загрузка, старые записи могли не сохраняться, уже удалиться по политике или быть недоступны. Это не повод перезагружать машину для упражнения.

### 5.3. Отберите события SSH без изменения SSH

```bash
sudo journalctl --unit=ssh.service --boot=0 --lines=20 --no-pager --output=short-iso
```

`--unit=ssh.service` выбирает записи, связанные с указанным юнитом. Остальные параметры означают текущую загрузку, ограничение числа строк, прямой вывод и короткий формат времени.

**Пример структуры результата:**

```text
2026-10-29T... astra-lab sshd[...]: ...
```

Если появляется `No entries`, подходящих записей в доступной выборке нет. Имя службы и направление журналирования зависят от установки. Команда не проверяет пароль заново и не меняет состояние уже открытого SSH-сеанса.

### 5.4. Отберите предупреждения и более важные сообщения за период

```bash
sudo journalctl --boot=0 --since="30 minutes ago" --priority=warning --lines=30 --no-pager
```

`--since` задаёт начало периода относительно времени сервера. `--priority=warning` выбирает **warning и более важные уровни**, то есть числа 0–4, а не только предупреждения. `--lines=30` ограничивает количество строк, `--boot=0` — загрузку, `--no-pager` — способ просмотра.

**Пример результата:** до 30 строк предупреждений и ошибок либо `No entries`. Пустая выборка сама по себе не доказывает, что за пределами периода ошибок не было.

Для ровно одного уровня используйте поле записи:

```bash
sudo journalctl --boot=0 PRIORITY=4 --lines=10 --no-pager
```

`PRIORITY=4` — точное условие по полю journal, а не параметр Bash. Оно оставляет только warning. Другие параметры имеют прежний смысл.

**Ожидаемый результат:** только записи уровня 4, если они есть. Отличие точного поля от порога важно и для правил rsyslog.

### 5.5. Посмотрите сообщения ядра

```bash
sudo journalctl --dmesg --boot=0 --lines=20 --no-pager
```

`--dmesg` выбирает сообщения ядра; `--boot=0` явно указывает текущую загрузку, `--lines=20` ограничивает число строк, `--no-pager` отключает просмотрщик.

**Пример структуры результата:** строки от `kernel` о событиях устройств или работе ядра. Отсутствие доступа может быть связано с разрешениями и политикой безопасности; обходить ограничения в этой практике не требуется.

## 6. Добавьте и найдите собственные события в journal

### 6.1. Отправьте три сообщения разной важности

```bash
printf '%s\n' 'event=journal_test stage=start' | systemd-cat --identifier="$LAB_TAG" --priority=info
printf '%s\n' 'event=journal_test stage=check result=warning' | systemd-cat --identifier="$LAB_TAG" --priority=warning
printf '%s\n' 'event=journal_test stage=simulation result=error' | systemd-cat --identifier="$LAB_TAG" --priority=err
```

`printf` создаёт строку; `|` передаёт её на вход `systemd-cat`. `--identifier` задаёт метку отправителя, `--priority` — важность записи. Это вымышленные сообщения: последняя строка моделирует ошибку, а не вызывает сбой службы.

**Ожидаемый результат:** команды обычно ничего не печатают и возвращают приглашение. При ошибке соединения с journal не подменяйте результат обычным текстовым файлом — сначала проверьте доступность journald.

### 6.2. Найдите свои записи

```bash
sudo journalctl --identifier="$LAB_TAG" --since="10 minutes ago" --no-pager --output=short-iso
```

`--identifier` выбирает нашу метку, `--since` — период, `--output=short-iso` — формат. `--no-pager` выводит прямо в терминал.

**Пример результата:**

```text
2026-10-29T... astra-lab astra-log-1000[...]: event=journal_test stage=start
2026-10-29T... astra-lab astra-log-1000[...]: event=journal_test stage=check result=warning
2026-10-29T... astra-lab astra-log-1000[...]: event=journal_test stage=simulation result=error
```

Если повторить отправку, появятся дополнительные записи. Если с предыдущего шага прошло больше десяти минут, расширьте именно период поиска. При необходимости повторите команду чтения: обработка поступивших сообщений может занимать время.

### 6.3. Сохраните только свои события в текст и JSON

```bash
sudo journalctl --identifier="$LAB_TAG" --since="10 minutes ago" --no-pager --output=short-iso > "$LAB_REPORT/journal-events.txt"
sudo journalctl --identifier="$LAB_TAG" --since="10 minutes ago" --no-pager --output=json > "$LAB_REPORT/journal-events.jsonl"
ls -lh "$LAB_REPORT/journal-events.txt" "$LAB_REPORT/journal-events.jsonl"
```

`>` записывает вывод в файл, заменяя его содержимое. Перенаправление выполняет ваша оболочка: файлы принадлежат вам, хотя чтение журнала выполняется через `sudo`. `--output=json` выдаёт по JSON-объекту на запись; поэтому расширение `.jsonl` обозначает последовательность JSON-строк.

`ls -lh` показывает подробности и удобные размеры. **Пример результата:** два непустых файла в вашем каталоге отчёта. JSON содержит и служебные поля события, например время и UID, а не только текст сообщения. Выборка ограничена нашей меткой, не всеми журналами сервера.

## 7. Прочитайте настройки действующего журналирования

### 7.1. Посмотрите journald.conf и каталоги дополнений

```bash
sed -n '1,180p' /etc/systemd/journald.conf
ls -ld /etc/systemd/journald.conf.d /run/systemd/journald.conf.d /usr/lib/systemd/journald.conf.d
```

`sed -n` отключает обычную печать всех строк, диапазон `1,180p` выводит строки с первой по 180-ю. Файл не меняется. `ls -ld` показывает сами каталоги и их свойства.

**Пример структуры результата:**

```text
[Journal]
#Storage=auto
#SystemMaxUse=
...
```

Часть каталогов может отсутствовать: `No such file or directory` здесь не означает повреждения системы. Закомментированная строка с `#` не является явно заданным параметром. Значения могут переопределяться дополнениями; один основной файл не всегда показывает всю эффективную конфигурацию.

| Параметр | Смысл |
| --- | --- |
| `Storage=auto` | Постоянное хранение используется при наличии подходящего каталога `/var/log/journal`, иначе журнал хранится временно |
| `Storage=persistent` | Настройка постоянного хранения с учётом доступности файловых систем |
| `Storage=volatile` | Хранение в `/run`, обычно до перезагрузки |
| `SystemMaxUse` | Ограничение использования места постоянным журналом |
| `RuntimeMaxUse` | Ограничение временного журнала |
| `MaxRetentionSec` | Ограничение по возрасту записей |
| `ForwardToSyslog` | Управление пересылкой в совместимый syslog-получатель |

Эти настройки изучаем для понимания. Изменение глобального хранения и очистка существующего journal затрагивают рабочую историю сервера. В упражнении сохраняем её, а настройку правил и хранения отрабатываем на своих файлах.

### 7.2. Посмотрите файлы обычного rsyslog

```bash
sed -n '1,180p' /etc/rsyslog.conf
ls -l /etc/rsyslog.d/
```

`sed -n '1,180p'` читает ограниченный диапазон основного файла. `ls -l` показывает дополнительные файлы и их свойства. Команды не включают и не изменяют эти настройки.

**Пример структуры результата:** загрузка модулей, правила направлений, включение файлов из `/etc/rsyslog.d/`. Набор зависит от установки. Ни один из этих файлов дальше не используется как путь записи нашего стенда.

При необходимости прочитайте последние строки журнала авторизации, если он существует и доступен:

```bash
sudo tail -n 20 /var/log/auth.log
```

`tail -n 20` выводит последние 20 строк. **Пример результата:** строки авторизации либо сообщение об отсутствии файла. Схема хранения может отличаться; не создавайте фиктивный `/var/log/auth.log`. Не переносите реальные адреса и учётные данные из таких журналов в учебные примеры или общедоступный отчёт.

## 8. Настройте отдельный rsyslog

### 8.1. Создайте конфигурацию собственного процесса

```bash
cat > "$LAB_CONFIG" <<EOF
global(workDirectory="$LAB_BASE/work")
module(load="imuxsock" SysSock.Use="off")

template(name="LabLine" type="string" string="%timegenerated:::date-rfc3339%|%hostname%|%programname%|%syslogseverity%|%syslogfacility%|%msg%\n")

ruleset(name="lab") {
    if (\$programname == "$LAB_TAG") then {
        action(type="omfile" file="$LAB_ALL" template="LabLine" fileCreateMode="0600")
        if (\$syslogseverity <= 4) then {
            action(type="omfile" file="$LAB_ALERTS" template="LabLine" fileCreateMode="0600")
        }
        stop
    }
}

input(type="imuxsock" Socket="$LAB_SOCKET" CreatePath="off" Ruleset="lab")
EOF
```

`cat > файл <<EOF` записывает текст до отдельной строки `EOF`. Незакавыченный маркер позволяет подставить наши пути и метку. Перед `$programname` и `$syslogseverity` стоит `\`: он сохраняет знак `$` для rsyslog вместо попытки подставить переменную Bash.

| Запись | Зачем нужна |
| --- | --- |
| `global(workDirectory=...)` | Рабочий каталог только этого процесса |
| `module(load="imuxsock" ...)` | Модуль приёма через Unix-сокеты |
| `SysSock.Use="off"` | Не слушать системный сокет `/dev/log` или его системный аналог |
| `template` | Определение формата каждой строки |
| `%timegenerated:::date-rfc3339%` | Время приёма сообщения с часовым поясом |
| `%hostname%`, `%programname%` | Узел и метка программы |
| `%syslogseverity%`, `%syslogfacility%` | Числовые важность и категория |
| `%msg%` | Текст сообщения |
| `\n` в шаблоне | Новая строка после сообщения |
| `ruleset(name="lab")` | Отдельный набор правил |
| Условие по `$programname` | Принимать в учебные файлы только нашу метку |
| `action(type="omfile" ...)` | Записать в указанный файл |
| `fileCreateMode="0600"` | Дать доступ к новому файлу только владельцу |
| `$syslogseverity <= 4` | Дополнительно сохранить предупреждения и более важные события |
| `stop` | Завершить обработку принятого сообщения этими правилами |
| `Socket=...`, `Ruleset="lab"` | Связать собственный сокет с нашим набором правил |
| `CreatePath="off"` | Не создавать каталоги сокета автоматически; мы уже подготовили их |

**Ожидаемый результат:** команда молчит, создан `$LAB_CONFIG`. Системные файлы не включаются, сетевые модули не загружаются. Это настоящая конфигурация отдельного rsyslog, но не изменение рабочего экземпляра.

### 8.2. Проверьте синтаксис без запуска демона

```bash
"$LAB_RSYSLOG_BIN" -N1 -f "$LAB_CONFIG" -i "$LAB_PIDFILE"
```

`-N1` включает проверку конфигурации уровня 1, а не обычный запуск. `-f` выбирает только наш конфигурационный файл, `-i` задаёт свой PID-файл для этого экземпляра. Путь программы взят из подготовленной переменной; `sudo` отсутствует.

**Пример сокращённого результата:**

```text
rsyslogd: version ... config validation run (level 1), master config .../rsyslog.conf
rsyslogd: End of config validation run. Bye.
```

Продолжайте только при успешном завершении без ошибок. В этой проверке демон ещё не принимает сообщения. При недостающем модуле или запрете политики не переносите конфигурацию в рабочий rsyslog как обходной способ.

### 8.3. Определите проверку личности учебного процесса

```bash
lab_check_daemon() {
    local pid owner exe expected
    if ! read -r pid < "$LAB_PIDFILE"; then
        printf '%s\n' 'STOP: training PID file is unavailable.' >&2
        return 1
    fi
    if [[ ! "$pid" =~ ^[1-9][0-9]*$ || "$pid" -le 1 || "$pid" -eq "$$" ]]; then
        printf '%s\n' 'STOP: unexpected PID value.' >&2
        return 1
    fi
    kill -0 "$pid" 2>/dev/null || return 1
    owner="$(awk '/^Uid:/ { print $2 }' "/proc/$pid/status")" || return 1
    exe="$(readlink -f "/proc/$pid/exe")" || return 1
    expected="$(readlink -f "$LAB_RSYSLOG_BIN")" || return 1
    if [[ "$owner" != "$LAB_UID" || "$exe" != "$expected" ]]; then
        printf '%s\n' 'STOP: PID belongs to another user or program.' >&2
        return 1
    fi
    if ! tr '\0' '\n' < "/proc/$pid/cmdline" | grep -F -x -- "$LAB_CONFIG" > /dev/null; then
        printf '%s\n' 'STOP: process uses another configuration.' >&2
        return 1
    fi
    LAB_DAEMON_PID="$pid"
    printf '%s\n' "OK: training rsyslog PID=$pid"
}
```

Функция не отправляет сигнал завершения. Она проверяет PID перед последующим управлением процессом, чтобы не затронуть рабочий rsyslog или другую программу.

| Элемент | Объяснение |
| --- | --- |
| `local` | Временные переменные внутри функции |
| `read -r` | Прочитать строку без специальной обработки обратных косых черт |
| `< файл` | Передать файл на вход команды |
| `[[ ... ]]` | Условие Bash |
| `=~ ^[1-9][0-9]*$` | Положительное число без ведущего нуля |
| `-le 1`, `-eq "$$"` | Запретить PID 0/1 и PID нашей оболочки |
| `kill -0` | Проверить существование процесса и возможность отправки сигнала, не завершая его |
| `awk '/^Uid:/ { print $2 }'` | Получить реальный UID процесса из `/proc`; `$2` — второе поле awk |
| `readlink -f` | Разрешить ссылки и получить сопоставимые пути программ |
| `tr '\0' '\n'` | Превратить разделители аргументов процесса в переводы строк |
| `grep -F -x` | Найти буквальное совпадение всей строки с путём нашей конфигурации |
| `--` | Закончить список параметров grep |
| `2>/dev/null`, `> /dev/null` | Скрыть ожидаемую диагностику проверки или обычный вывод |
| `return 1` | Прекратить функцию с признаком ошибки |
| `>&2` | Направить сообщение в поток ошибок |

**Ожидаемый результат определения:** текста нет. Когда процесс будет запущен, успешный вызов напечатает `OK: training rsyslog PID=...`. При запрете чтения собственных данных `/proc` проверка не разрешит управление; ограничения Astra Linux не отключаются.

### 8.4. Определите запуск своего экземпляра

```bash
lab_start_logging() {
    local attempt
    "$LAB_RSYSLOG_BIN" -N1 -f "$LAB_CONFIG" -i "$LAB_PIDFILE" || return 1
    if [[ -e "$LAB_PIDFILE" || -e "$LAB_SOCKET" ]]; then
        printf '%s\n' 'STOP: inspect existing PID file or socket before starting.' >&2
        return 1
    fi
    nohup "$LAB_RSYSLOG_BIN" -n -i "$LAB_PIDFILE" -f "$LAB_CONFIG" >> "$LAB_CONSOLE" 2>&1 < /dev/null &
    LAB_DAEMON_PID=$!
    for attempt in {1..50}; do
        if [[ -s "$LAB_PIDFILE" && -S "$LAB_SOCKET" ]]; then
            lab_check_daemon && return 0
        fi
        sleep 0.1
    done
    printf '%s\n' 'STOP: training daemon did not become ready; inspect its console log.' >&2
    tail -n 20 "$LAB_CONSOLE"
    return 1
}
```

Перед запуском снова проверяется конфигурация. `-e` означает существование пути; старый PID-файл или сокет нужно сначала исследовать, а не заменять автоматически.

`nohup` делает запуск устойчивым к обычному сигналу завершения терминальной сессии. `rsyslogd -n` не уходит в фон самостоятельно; символ `&` запускает его в фоне оболочки. `-i` и `-f` выбирают наши PID-файл и конфигурацию. Это запуск от вашей учётной записи, без `sudo`.

`>>` добавляет диагностику в `daemon-console.log`, `2>&1` направляет ошибки туда же, `< /dev/null` отключает ввод с терминала. `$!` — PID последней фоновой команды.

`for attempt in {1..50}` ограничивает число проверок. `-s` требует непустой PID-файл, `-S` — Unix-сокет. `sleep 0.1` делает небольшую паузу. При готовности выполняется проверка процесса и `return 0`; при тайм-ауте выводится `STOP` и последние 20 строк диагностики через `tail -n 20`.

**Ожидаемый результат определения:** текста нет. Функция запуска ещё не вызвана. `nohup` не гарантирует сохранение процесса при перезагрузке или административном завершении пользовательских процессов; восстановление после SSH разобрано отдельно.

### 8.5. Определите штатную остановку только учебного процесса

```bash
lab_stop_logging() {
    local attempt
    lab_check_daemon || return 1
    kill -TERM "$LAB_DAEMON_PID" || return 1
    for attempt in {1..50}; do
        if ! kill -0 "$LAB_DAEMON_PID" 2>/dev/null; then
            if [[ ! -e "$LAB_PIDFILE" && ! -e "$LAB_SOCKET" ]]; then
                printf '%s\n' 'OK: training rsyslog stopped.'
                return 0
            fi
        fi
        sleep 0.1
    done
    printf '%s\n' 'STOP: shutdown is incomplete; do not rotate or delete files yet.' >&2
    return 1
}
```

`lab_check_daemon` сначала подтверждает пользователя, программу и конфигурацию. `kill -TERM` отправляет выбранному PID штатный запрос завершения, не затрагивая другие процессы. `kill -0` затем проверяет, исчез ли процесс; `!` отрицает результат. `-e` проверяет оставшиеся файлы, `&&` требует отсутствия обоих.

Цикл и паузы ограничивают ожидание. Если завершение не подтверждено, функция возвращает ошибку. Принудительное завершение `kill -9`, остановка системной службы и удаление чужих PID-файлов здесь не используются.

**Ожидаемый результат определения:** текста нет. При последующем успешном вызове будут показаны проверенный PID и `OK: training rsyslog stopped.`

### 8.6. Запустите стенд

```bash
lab_start_logging
ls -l "$LAB_SOCKET" "$LAB_PIDFILE"
```

Первая команда вызывает разобранную функцию. `ls -l` показывает свойства созданных объектов; в начале строки сокета будет `s`, это не обычный текстовый файл.

**Пример сокращённого результата:**

```text
rsyslogd: ... config validation ...
OK: training rsyslog PID=12345
srw-... student student ... /var/tmp/astra-logging-1000/input.sock
-rw-... student student ... /var/tmp/astra-logging-1000/rsyslog.pid
```

Лог-файлы могут появиться только после первого подходящего сообщения. Если запуск не удался, прочитайте `$LAB_CONSOLE`, не запускайте второй экземпляр поверх непонятного состояния.

## 9. Создайте учебные события

### 9.1. Отправьте шесть сообщений в собственный сокет

```bash
lab_check_daemon &&
logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG" --priority local5.info -- 'event=start session=alpha' &&
logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG" --priority local5.notice -- 'event=login user=student result=ok' &&
logger --socket "$LAB_SOCKET" --socket-errors=on --tag "$LAB_TAG" --priority local5.warning -- 'event=login user=student result=failed' &&

```

| Параметр | Значение |
| --- | --- |
| `--socket` | Отправить в наш Unix-сокет вместо системного `/dev/log` |
| `--socket-errors=on` | Показывать ошибки соединения с сокетом |
| `--tag` | Задать метку программы, совпадающую с нашим правилом |
| `--priority local5.уровень` | Задать категорию и важность |
| `--` | Дальше передаётся текст сообщения, а не параметры logger |
| Одинарные кавычки | Передать сообщение буквально одним аргументом |

**Ожидаемый результат:** проверка покажет наш PID, успешные вызовы logger обычно молчат. `&&` прекращает дальнейшую отправку при ошибке предыдущего вызова. Все имена и события вымышлены. Не повторяйте блок без необходимости: повтор создаст дополнительные записи и изменит ожидаемые количества.

### 9.2. Дождитесь обработки и посчитайте строки


### 10.1. Посмотрите строки с номерами, начало и конец

`nl -ba` нумерует все строки, включая пустые. `head -n 2` показывает первые две строки, `tail -n 2` — последние две. Файлы не меняются.

### 10.2. Найдите неуспешные события и посчитайте их

```bash
grep -n -F 'result=failed' "$LAB_ALL"

```

`grep -F` ищет текст буквально, не интерпретируя регулярное выражение. `-n` добавляет номер строки, `-c` выводит число совпавших строк.

**Ожидаемый результат:** две строки — неуспешный учебный вход и ошибка учебного хранилища, затем число `2`. `-c` считает строки, а не количество повторений текста внутри каждой строки.

### 10.3. Выберите ошибки по полю важности


`awk -F '|'` делит строку по нашему разделителю. `$4` — четвёртое поле, `$0` — вся строка. Первая программа выбирает только уровень 3, вторая — уровни 0–4. Одинарные кавычки защищают поля awk от подстановки Bash.

**Ожидаемый результат:** сначала одна ошибка хранилища, затем две строки — warning и err. Наличие слова `error` в тексте не заменяет анализ числовой важности.

### 10.4. Получите сводку по важности

```bash
awk -F '|' '{ count[$4]++ } END { for (level in count) print level, count[level] }' "$LAB_ALL" | sort -n
```

`count[$4]++` увеличивает счётчик для уровня текущей строки. `END` выполняет итоговый блок после чтения файла; `for` перебирает накопленные уровни, `print` выводит уровень и число. `|` передаёт результат в `sort -n`, где `-n` включает числовую сортировку.

**Ожидаемый результат для первых шести событий:**

```text
3 1
4 1
5 1
6 2
7 1
```

Сумма — шесть. Если вы уже отправляли дополнительные сообщения, количества закономерно будут другими.

### 10.5. Извлеките сообщения входа и проверьте структуру

```bash
grep -F 'event=login' "$LAB_ALL" | cut -d '|' -f 6
awk -F '|' 'NF != 6 || $4 !~ /^[0-7]$/ { print NR ":" $0 }' "$LAB_ALL"
```

`grep -F` оставляет сообщения входа. `cut -d '|'` задаёт разделитель, `-f 6` выбирает шестое поле — текст. Конвейер не меняет файл.

Во второй программе `NF` — количество полей, `NR` — номер строки, `!=` — неравенство, `||` — «или», `!~` — отсутствие совпадения с шаблоном. `^[0-7]$` допускает ровно одну цифру от 0 до 7. Программа печатает только строки с неожиданной структурой.

**Ожидаемый результат:** два текста учебного входа; затем от проверки структуры — пустой вывод. Пустой вывод этой проверки означает, что она не нашла нарушений заданного учебного формата.

## 13. Настройте ротацию только учебных файлов

### 13.1. Создайте собственную политику logrotate

```bash
cat > "$LAB_ROTATE_CONF" <<EOF
"$LAB_ALL" "$LAB_ALERTS" {
    size 1k
    rotate 2
    missingok
    notifempty
    compress
    delaycompress
    create 0600
}
EOF
```

`cat` с `<<EOF` записывает конфигурацию с подстановкой наших путей. Кавычки окружают имена двух файлов.

| Директива | Значение |
| --- | --- |
| `size 1k` | Рассматривать ротацию после достижения небольшого порога размера |
| `rotate 2` | Хранить две предыдущие версии для каждого файла |
| `missingok` | Отсутствие файла не считать ошибкой этой политики |
| `notifempty` | Не вращать пустой файл |
| `compress` | Сжимать старые версии |
| `delaycompress` | Отложить сжатие самой свежей старой версии до следующего цикла |
| `create 0600` | Создать новый активный файл с доступом только владельцу; владелец и группа берутся от исходного файла |

**Ожидаемый результат:** создан наш файл конфигурации, текста в терминале нет. Он не включён в системный планировщик и не меняет `/etc/logrotate.conf`.

Порог размера сам по себе не запускает программу. Logrotate выполняет действия только при своём запуске. В рабочей системе запуск обычно организован планировщиком; здесь вызываем программу вручную со своей политикой и состоянием.

### 13.2. Посмотрите план без изменения файлов

```bash

```

`--debug` показывает разбор и предполагаемые действия, не меняет логи и не обновляет состояние. `--state` выбирает собственный файл учёта вместо системного. Последний аргумент — только наша конфигурация.

**Пример структуры результата:** чтение двух учебных путей и решение, требуется ли им ротация. Короткие файлы могут ещё не достигнуть `1k`; это нормально. Ни одного рабочего пути из `/var/log` в плане быть не должно.

```bash
sha256sum -c "$LAB_REPORT/SHA256SUMS"
```

`awk` выбирает числовые уровни 0–4. `>` сохраняет результат. `sha256sum` вычисляет суммы трёх файлов; `-c` проверяет их по ведомости. Контрольная сумма помогает обнаружить изменение, но не подтверждает подлинность отчёта, если один пользователь может изменить и данные, и ведомость.

**Пример результата:** три строки с полными путями и `OK`. В итоговой выборке важных событий будет четыре строки, тогда как архив `alerts.log.1` содержит три: одно warning пришло уже после изменения правила. Это показывает различие полного потока, текущего правила маршрутизации и анализа истории.

### 15.3. Что показать в отчёте или на скриншотах

| Результат | Подтверждение |
| --- | --- |
| Понимание текущей загрузки и фильтра службы | Выборка `journalctl` с пояснением параметров |
| Собственные записи journald | Три сообщения с вашим `LAB_TAG` |
| Проверенная конфигурация rsyslog | Успешный `-N1` |
| Отдельный экземпляр | Свой PID, конфигурация и путь сокета |
| Первоначальная фильтрация | Шесть строк в all и две в alerts |
| Поиск и подсчёт | Выборка failed и сводка по важности |
| Изменение правила | Две policy_check в all, одна в alerts |
| Обнаружение ошибки до запуска | Неуспешная проверка отдельного плохого примера |
| Ротация и сжатие | Имена `.1`, `.2.gz` и запись нового события в новый файл |
| Итоговый анализ | Сводка десяти событий, важная выборка и суммы `OK` |

Не включайте в общедоступный отчёт настоящие записи авторизации с адресами, ключами или чувствительными сведениями. Для иллюстрации достаточно собственных событий. Скриншоты делаются средствами вашего компьютера, графическую оболочку сервера устанавливать не нужно.

## 16. Если SSH-соединение разорвалось

После входа в новую Bash повторите только присваивания переменных из раздела 4.1. Не создавайте заново каталог и конфигурацию поверх существующих файлов.

Заново определите функции из разделов 8.3–8.5. В этих блоках содержатся только определения, а не запуск или остановка.

```bash
ls -l "$LAB_CONFIG" "$LAB_PIDFILE" "$LAB_SOCKET" "$LAB_CONSOLE"
ps -u "$(id -u)" -o pid,stat,args | grep '[r]syslogd'
```

`ls -l` показывает объекты стенда; отдельные PID-файл и сокет могут отсутствовать, если процесс уже штатно остановлен. `ps -u` выбирает ваши процессы по UID, `-o` задаёт столбцы PID, состояние и аргументы. `id -u` получает UID заново.

`grep '[r]syslogd'` ищет имя программы так, чтобы обычно не включать строку самого grep. Среди процессов root может быть и рабочий rsyslog, если ваша сессия root; ориентироваться только на имя программы нельзя.

**Возможный результат:** отдельная строка с `-f /var/tmp/astra-logging-ваш_UID/rsyslog.conf`. Подтвердите её через `lab_check_daemon`, прежде чем управлять процессом. Если он действует, не запускайте второй поверх него.

Если процесс отсутствует, а собственные PID-файл или сокет остались, сначала убедитесь, что это именно остатки вашего стенда, а не действующий экземпляр. В этом случае удаляются только эти два файла внутри `LAB_BASE`, после чего можно повторить `lab_start_logging`. При неоднозначности или запрете чтения `/proc` остановитесь и разберите состояние; чужие PID и системные сокеты не удаляются.

Продолжайте с фактически завершённого шага. Перед ротацией обязательно подтвердите остановку, а при сравнении количества строк учитывайте уже отправленные сообщения. Повторная отправка всего блока создаёт дубликаты, а не восстанавливает прежнее состояние.

## 17. Завершение и очистка

В нормальном маршруте после второго цикла ротации учебный rsyslog уже остановлен. Если вы остановились раньше и он ещё действует, завершите только его:

```bash
if [[ -e "$LAB_PIDFILE" ]]; then
    lab_stop_logging
else
    printf '%s\n' 'No training PID file; confirm that the daemon is already stopped.'
fi
```

`-e` проверяет существование файла; функция при наличии файла проверит личность процесса до отправки `TERM`. **Ожидаемый результат:** подтверждение штатной остановки либо сообщение, что PID-файла уже нет. Отсутствие файла при непонятном состоянии требует просмотра по разделу 16, а не завершения всех rsyslog-процессов.

Сначала сохраните нужные результаты из `LAB_REPORT`. Затем проверьте путь:

```bash
printf '%s\n' "$LAB_BASE"
ls -ld "$LAB_BASE"
```

`printf` показывает значение, `ls -ld` — сам каталог и владельца. **Ожидаемый результат:** только ваш `/var/tmp/astra-logging-UID`, доступный владельцу. Не удаляйте его, если ещё нужен отчёт.

```bash
if [[ "$LAB_BASE" = "/var/tmp/astra-logging-$(id -u)" && "$LAB_PIDFILE" = "$LAB_BASE/rsyslog.pid" && "$LAB_SOCKET" = "$LAB_BASE/input.sock" ]]; then
    if [[ -e "$LAB_PIDFILE" || -e "$LAB_SOCKET" ]]; then
        printf '%s\n' 'STOP: inspect remaining PID file or socket before deleting the directory.'
    else
        cd "$HOME" && rm -rI -- "$LAB_BASE"
    fi
else
    printf '%s\n' 'STOP: paths do not match this practice.'
fi
```

`[[ ... ]]` сверяет пути, `=` проверяет равенство, `&&` требует всех совпадений. `$(id -u)` заново получает UID. `||` обнаруживает хотя бы один оставшийся объект.

`cd "$HOME"` выводит оболочку из удаляемого дерева. `rm -rI` удаляет содержимое каталога рекурсивно (`-r`) после общего запроса подтверждения (`-I`, заглавная i). `--` заканчивает параметры. `sudo` отсутствует; удаляется только собственный каталог.

**Пример результата:** запрос вида `rm: remove 1 argument recursively?`. Подтверждайте только ожидаемый учебный путь. Системные журналы и конфигурации не удаляются. Три сообщения с вашей меткой в journal остаются под обычной политикой хранения ОС.

## 18. Частые ошибки и самостоятельная проверка

| Симптом | Возможный смысл | Что проверить |
| --- | --- | --- |
| `No entries` в journalctl | Нет доступных совпадений | Метку, загрузку, период и права чтения |
| Видны записи info при ожидании только warning | Неверно выбран фильтр | Для точного warning использовать `PRIORITY=4`; порог warning выбирает 0–4 |
| Нет `/var/log/auth.log` | Другая схема хранения | Доступные конфигурации и journal; не создавать фиктивный системный файл |
| `command not found` | Нет программы в пути поиска | Подготовку пакета и найденные пути административных программ |
| Ошибка `-N1` | Конфигурация не прошла проверку | Путь, строку ошибки, модуль и синтаксис; не активировать такой файл |
| Сокет не появился | Учебный процесс не запущен или не смог создать вход | Собственный `daemon-console.log`, права каталога и политику Astra Linux |
| Logger сообщает об ошибке сокета | Нет доступного получателя | Правильность `--socket` и готовность процесса |
| Логи пусты | Метка не совпала, вход не привязан к правилам или ещё не обработана очередь | `LAB_TAG`, `Ruleset`, диагностику и короткое ожидание |
| В alerts остались старые warning | Правило изменено только для новых событий | Время сообщения; история не переписывается автоматически |
| Получилось больше событий | Блок отправки был повторён | Текст и время записей; не удалять строки ради совпадения с примером |
| Tail не возвращает приглашение | Включено непрерывное наблюдение | Ctrl+C для завершения просмотра |
| Logrotate не вращает файл | Он пустой, мал или уже обработан | `notifempty`, порог, собственный state и режим debug |
| После ротации запись идёт в старый файл | Писатель не переоткрыл журнал | Правильную остановку/запуск собственного процесса; не трогать рабочие службы |
| Нет `.2.gz` для alerts | Пустой активный файл пропущен | Действие `notifempty` и `delaycompress` |
| Проверка PID возвращает STOP | Файл устарел, PID переиспользован, иной процесс или запрет доступа | Раздел 16; не заменять проверку произвольным kill |

Проверьте, что можете объяснить:

1. Чем отличаются journald, journalctl, rsyslog и logrotate?
2. Почему уровень 3 важнее уровня 6?
3. Почему `--priority=warning` не означает ровно warning?
4. Почему наш rsyslog не получает все события системы?
5. Чем Unix-сокет отличается от текстового файла и сетевого порта?
6. Почему конфигурацию сначала проверяют через `-N1`?
7. Почему одного имени процесса недостаточно для безопасного завершения?
8. Почему изменение фильтра не убирает старые записи?
9. Почему нельзя складывать all и alerts как независимые события?
10. Почему переименование файла не заставляет программу закрыть старый дескриптор?
11. Почему после первого цикла ещё нет сжатого `.1.gz`?
12. Почему контрольная сумма не является доказательством подлинности журнала?
