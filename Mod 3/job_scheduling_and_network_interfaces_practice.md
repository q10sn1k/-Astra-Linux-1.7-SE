# Модуль 3. Планировщики заданий и конфигурация сетевых интерфейсов

Вся практика выполняется **на одной удалённой Astra Linux Special Edition 1.7 по SSH**, в Bash обычного пользователя с доступом к `sudo`. Команды вводятся после подключения к серверу. Второй компьютер для сетевых опытов, ещё одна виртуальная машина и графическая среда не нужны.

Настроим две виртуальные сетевые среды внутри этой же ОС, соединим их виртуальным кабелем, назначим адреса и добавим маршрут. Затем systemd-таймер будет проверять связь, а Cron — раз в минуту сохранять короткий отчёт. Отключим только учебный интерфейс, увидим отказ в журнале и восстановим связь.

Сетевой интерфейс SSH, маршруты основной системы, её DNS и рабочие сетевые настройки не меняются. Сетевые службы не перезапускаются. Дополнительные интерфейсы создаются **сразу внутри отдельных пространств имён**, поэтому даже временно не подключаются к основной сети сервера.

Учебные service- и timer-файлы размещаются в `/run/systemd/system`: они предназначены для текущей загрузки и не включаются в автозапуск. Cron использует отдельный файл в `/etc/cron.d`; его нужно удалить при завершении. Записи своих служб останутся в journal до удаления по обычной политике хранения системы.

Примеры вывода условные: пользователь `student`, UID `1000`, имя узла `astra-lab`. Команды сами определяют ваш UID. Адреса `192.0.2.0/24` и `203.0.113.0/24` взяты из диапазонов для документации и используются только в изолированной учебной сети.

## 1. Как проходить практику

Сначала прочитайте объяснение раздела, затем копируйте его командные блоки по порядку. При `STOP`, ошибке или неожиданном результате дальше не идите. Блоки с примерами вывода предназначены для чтения.

Многострочные определения функций и блоки `<<'EOF'` вставляйте целиком, включая завершающий `EOF` на отдельной строке. Если Bash показывает приглашение `>` после неполного ввода, Ctrl+C отменяет незавершённую команду; затем вставьте блок заново.

Несколько обычных строк не отменяют друг друга при ошибке. Поэтому связанные изменения ниже соединены через `&&` и условия. Общий `set -e` в SSH-терминале не включайте: ошибка могла бы закрыть оболочку. В отдельных создаваемых сценариях эта настройка действует только на сам сценарий.

Основной маршрут — разделы 2–18. Затем сохраните скриншоты и выполните очистку по разделу 20. Раздел 19 нужен при разрыве SSH. Запасная установка пакетов выполняется только при отсутствии инструментов. В течение практики не перезагружайте сервер и не создавайте стенд заново поверх существующего.

## 2. Что именно будем настраивать

### 2.1. Сетевые понятия

| Понятие | Объяснение | В этой практике |
| --- | --- | --- |
| Интерфейс | Точка подключения ОС к сети: физическая или виртуальная | Виртуальные `lab0` и `lab1` |
| IP-адрес | Адрес интерфейса в IP-сети | `192.0.2.1` и `192.0.2.2` |
| Префикс | Число битов, определяющих сеть | `/30`, маска `255.255.255.252` |
| Маршрут | Правило выбора следующего узла или интерфейса | Путь к `203.0.113.10/32` через учебного соседа |
| Шлюз | Следующий узел, которому передаётся пакет | `192.0.2.2` для дополнительного адреса |
| DNS | Преобразование имён в адреса | Изучим текущие настройки; изменять их не потребуется |
| MAC-адрес | Канальный адрес сетевого интерфейса | Автоматически создаётся для veth |
| MTU | Максимальный размер сетевого пакета на интерфейсе без фрагментации на этом уровне | Посмотрим в выводе `ip link` |
| Network namespace | Отдельный сетевой стек со своими интерфейсами и маршрутами | Две роли: клиент и сервер |
| veth | Пара связанных виртуальных интерфейсов | «Кабель» между клиентом и сервером |

В сети `192.0.2.0/30` адрес `.0` обозначает сеть, `.3` — широковещательный адрес; `.1` и `.2` подходят двум узлам. `/32` обозначает один IPv4-адрес, а не подсеть с несколькими узлами.

Статическая настройка означает, что адрес назначается явно; при DHCP параметры выдаёт сервер автоматически. В нашей изолированной паре DHCP-сервера нет, поэтому адреса задаются вручную. Рабочая DHCP-настройка основного интерфейса при этом сохраняется.

Пространство имён сети не является полноценной виртуальной машиной: ядро и многие ресурсы общие. Отдельной становится сетевая среда. Сценарии этой практики не подключают её к физической сети, не создают NAT и не включают пересылку пакетов в основной ОС.

### 2.2. Планировщики

| Инструмент | Когда полезен | Что выполняем |
| --- | --- | --- |
| Cron | Простые периодические команды по календарю | Отчёт обычного пользователя каждую минуту |
| systemd timer | Запуск службы по времени с журналом и управлением через systemctl | Проверку учебной сети через короткие интервалы |
| at | Однократный запуск на заданное время | Упоминается для сравнения; устанавливать не нужно |

У systemd файл `.service` описывает **что запускать**, а `.timer` — **когда**. В Cron время и команда находятся в одной строке таблицы.

Закрытие SSH не отменяет установленные задания. Cron и systemd работают как службы сервера. Поэтому завершение практики включает явное удаление своего расписания и остановку своего таймера.

## 3. Проверьте систему, права и инструменты

```bash
whoami
hostname
cat /etc/astra_version
printf '%s\n' "$BASH_VERSION"
sudo -v
sudo dpkg --audit
```

`whoami` показывает пользователя, `hostname` — машину, `cat` читает файл версии Astra. `printf '%s\n'` выводит строку и перевод строки; `$BASH_VERSION` содержит версию Bash. `sudo -v` проверяет административные полномочия и при необходимости запрашивает пароль без отображения символов. `dpkg --audit` ищет незавершённые состояния пакетов без исправлений.

**Пример результата:** `student`, `astra-lab`, `1.7.4`, версия Bash. После успешных `sudo -v` и `dpkg --audit` сообщений обычно нет. Если аудит выявил проблему, сначала разберите её.

```bash
export PATH="/usr/sbin:/usr/bin:/sbin:/bin:$PATH"
command -v ip ping systemctl systemd-analyze journalctl crontab
command -v stat grep awk sed date tee cmp diff sha256sum
ip -Version
systemctl --version
systemctl is-active cron.service
```

`export PATH=...` добавляет стандартные системные каталоги в начало поиска программ, сохраняя прежний путь после них. Это помогает найти `ip` из `/usr/sbin` и в обычных командах чтения. `command -v` ищет программы в этом пути; `ip -Version` и `systemctl --version` показывают версии. `systemctl is-active` только проверяет состояние Cron. Если `ip` всё равно не найден, нужна подготовка пакета `iproute2`.

**Ожидается:** пути к программам, версии и `active` для Cron. Пакет `iproute2` предоставляет `ip`, `iputils-ping` — `ping`, `cron` — планировщик и `crontab`; systemd обычно уже установлен.

### Если нужного пакета нет

APT читает доступные пакеты из уже настроенных репозиториев Astra. `update` обновляет индексы, а `install` устанавливает программы. Сторонние репозитории и общий `upgrade` для упражнения не нужны.

Только при отсутствии инструментов сначала посмотрите план:

```bash
sudo apt-get --simulate install --no-install-recommends --no-upgrade iproute2 iputils-ping cron
```

`--simulate` не применяет изменения; `--no-install-recommends` исключает необязательные рекомендации; `--no-upgrade` запрещает обновление уже установленных явно запрошенных пакетов, но не всех зависимостей. **Ожидается:** план, который необходимо прочитать целиком.

Если план не требует удаления или нежелательных изменений существующих пакетов:

```bash
sudo apt-get install --no-install-recommends --no-upgrade --no-remove iproute2 iputils-ping cron
```

`--no-remove` запрещает удаления. Перед подтверждением ещё раз прочитайте действия APT. **Ожидается:** успешная установка. При недоступном репозитории сначала восстановите доступ к разрешённому источнику пакетов своего выпуска Astra.

Установка Cron может запустить его и тем самым активировать уже существующие задания. Если Cron установлен, но намеренно остановлен, не запускайте его ради упражнения без выяснения причины. На учебной ВМ, где он должен работать, после проверки причины остановки можно выполнить:

```bash
sudo systemctl start cron.service && systemctl is-active cron.service
```

`start` запускает только указанную службу; `&&` выполняет проверку при успешном запуске. **Ожидается:** `active`. Рабочие сетевые службы этим не затрагиваются.

## 4. Посмотрите текущую сеть и соединение SSH

```bash
ip -brief address show
ip route show
ip -6 route show
printf 'SSH_CONNECTION=%s\n' "$SSH_CONNECTION"
```

`ip -brief address show` выводит кратко интерфейсы и адреса; `route show` — маршруты IPv4; `-6` выбирает IPv6. `$SSH_CONNECTION` обычно содержит четыре значения: адрес клиента, его порт, адрес сервера и порт SSH. Служебная переменная относится к текущему подключению, её не нужно задавать вручную.

**Пример сокращённого результата:**

```text
lo               UNKNOWN        127.0.0.1/8 ::1/128
ens3             UP             10.20.30.40/24
default via 10.20.30.1 dev ens3
10.20.30.0/24 dev ens3 proto kernel scope link src 10.20.30.40
SSH_CONNECTION=10.20.30.10 53000 10.20.30.40 22
```

Это пример, а не адреса для подстановки. `UNKNOWN` у loopback не означает неисправность. Основной интерфейс может называться иначе, а путь SSH может проходить через VPN.

Проверьте маршрут ответа клиенту без отправки пакетов:

```bash
read -r LAB_SSH_CLIENT LAB_SSH_PORT LAB_SSH_SERVER LAB_SSH_SERVER_PORT <<< "$SSH_CONNECTION"
if [[ -z "$LAB_SSH_CLIENT" ]]; then
    printf '%s\n' 'STOP: не удалось определить клиента SSH; проверьте текущий сеанс.'
elif [[ "$LAB_SSH_CLIENT" = *:* ]]; then
    ip -6 route get "$LAB_SSH_CLIENT"
else
    ip -4 route get "$LAB_SSH_CLIENT"
fi
```

`read -r` делит строку на переменные без обработки обратных косых черт, `<<<` передаёт строку на ввод. `-z` проверяет пустую строку. Наличие `:` выбирает IPv6; `-4` явно выбирает IPv4. `route get` показывает решение маршрутизации к клиенту. **Ожидается:** имя интерфейса, исходный адрес и, возможно, шлюз. В этой практике они остаются под управлением существующей настройки сервера.

## 5. Подготовьте имена и каталоги стенда

```bash
LAB_UID="$(id -u)"
LAB_USER="$(id -un)"
LAB_BASE="/var/tmp/astra-schednet-$LAB_UID"
LAB_RUN="/run/astra-schednet-$LAB_UID"
LAB_NS_A="astra_snet_a_$LAB_UID"
LAB_NS_B="astra_snet_b_$LAB_UID"
LAB_SERVICE="astra-schednet-$LAB_UID.service"
LAB_TIMER="astra-schednet-$LAB_UID.timer"
LAB_CRON="/etc/cron.d/astra-schednet-$LAB_UID"
```

`id -u` получает числовой UID; `id -un` — имя пользователя. `$(...)` подставляет результат команды. Переменные хранят только наши имена; двойные кавычки сохраняют значения целиком. **Ожидается:** отсутствие вывода.

Проверьте, что эти имена ещё не заняты:

```bash
LAB_READY=1
if [ "$LAB_UID" -eq 0 ] || [[ ! "$LAB_USER" =~ ^[a-zA-Z_][a-zA-Z0-9_-]*\$?$ ]]; then
    LAB_READY=0
    printf '%s\n' 'STOP: нужен обычный пользователь с простым локальным именем.'
fi
for LAB_PATH in "$LAB_BASE" "$LAB_RUN" "$LAB_CRON" "/run/systemd/system/$LAB_SERVICE" "/run/systemd/system/$LAB_TIMER"; do
    if sudo test -e "$LAB_PATH" || sudo test -L "$LAB_PATH"; then
        LAB_READY=0
        printf 'STOP: путь уже существует: %s\n' "$LAB_PATH"
    fi
done
for LAB_NS in "$LAB_NS_A" "$LAB_NS_B"; do
    if sudo ip netns list | awk '{print $1}' | grep -F -x -- "$LAB_NS"; then
        LAB_READY=0
        printf 'STOP: пространство имён уже существует: %s\n' "$LAB_NS"
    fi
done
for LAB_UNIT in "$LAB_SERVICE" "$LAB_TIMER"; do
    LAB_STATE="$(systemctl show --property=LoadState --value "$LAB_UNIT" 2>/dev/null || true)"
    if [ "$LAB_STATE" != not-found ]; then
        LAB_READY=0
        printf 'STOP: имя unit занято или состояние не определено: %s\n' "$LAB_UNIT"
    fi
done
printf 'Готовность к созданию: %s\n' "$LAB_READY"
```

`-eq` сравнивает числа. Шаблон имени допускает буквы, цифры, `_`, `-` и необязательный `$` в конце; сложные доменные имена в этот пример не входят. `test -e` находит существующий объект, `test -L` — ссылку. `for` перебирает значения. `awk '{print $1}'` получает первое поле; `grep -F -x` ищет буквальное полное совпадение строки.

`systemctl show --property=LoadState --value` читает состояние загрузки unit. `not-found` означает, что unit не найден. `2>/dev/null` скрывает диагностическое сообщение этой проверки, `|| true` позволяет обработать отсутствие unit как данные. **Ожидается:** `Готовность к созданию: 1` и отсутствие `STOP`. Иначе не создавайте стенд: изучите, не осталась ли предыдущая работа.

```bash
if [ "$LAB_READY" -eq 1 ]; then
    mkdir -m 700 -- "$LAB_BASE" &&
        mkdir -m 700 -- "$LAB_BASE/report" "$LAB_BASE/model" &&
        sudo mkdir -m 755 -- "$LAB_RUN"
else
    printf '%s\n' 'STOP: проверки готовности не пройдены.'
fi
ip -4 route show table main > "$LAB_BASE/report/host-routes-v4-before.txt"
ip -6 route show table main > "$LAB_BASE/report/host-routes-v6-before.txt"
```

`mkdir -m 700` создаёт личные каталоги; `755` у административного каталога позволяет читать учебные результаты, но писать в него может только владелец root. `>` сохраняет исходные таблицы маршрутизации основной системы. `table main` выбирает главную таблицу. **Ожидается:** отсутствие сообщений и созданные файлы снимков. При ошибке создания дальше не идите.

## 6. Создайте два пространства имён

```bash
sudo ip netns add "$LAB_NS_A" &&
    sudo ip netns add "$LAB_NS_B"
sudo ip netns list
```

`ip netns add` создаёт именованную сетевую среду; системные имена представлены через `/run/netns`. `list` выводит список. **Ожидается:** `astra_snet_a_1000` и `astra_snet_b_1000`, а также возможные чужие пространства, которые мы не трогаем.

Если создание запрещено политикой или ядром, например `Operation not permitted`, не отключайте защиту Astra. Для этой практики нужен сервер, где разрешены network namespaces и veth. Менять рабочую сеть вместо изолированной нельзя.

Зафиксируйте идентичность созданных пространств в файлах root:

```bash
sudo stat -L -c '%i' -- "/run/netns/$LAB_NS_A" | sudo tee "$LAB_RUN/ns-a.inode" > /dev/null
sudo stat -L -c '%i' -- "/run/netns/$LAB_NS_B" | sudo tee "$LAB_RUN/ns-b.inode" > /dev/null
sudo chmod 644 -- "$LAB_RUN/ns-a.inode" "$LAB_RUN/ns-b.inode"
```

`stat -L` читает сведения о целевом объекте, `-c '%i'` — его inode. `tee` записывает вход в указанный файл; перенаправление скрывает копию на экране. `chmod 644` разрешает всем чтение, запись — только root. **Ожидается:** отсутствие сообщений. Эти номера не копируются из примеров: их получает сама система.

Определите функцию проверки:

```bash
lab_check_namespaces() {
    local a b expected_a expected_b
    expected_a="$(cat "$LAB_RUN/ns-a.inode")" || return 1
    expected_b="$(cat "$LAB_RUN/ns-b.inode")" || return 1
    a="$(sudo stat -L -c '%i' -- "/run/netns/$LAB_NS_A")" || return 1
    b="$(sudo stat -L -c '%i' -- "/run/netns/$LAB_NS_B")" || return 1
    if [[ "$expected_a" =~ ^[0-9]+$ && "$expected_b" =~ ^[0-9]+$ &&
          "$a" = "$expected_a" && "$b" = "$expected_b" ]]; then
        return 0
    fi
    printf '%s\n' 'STOP: пространства имён не совпадают с созданным стендом.'
    return 1
}
lab_check_namespaces
```

`local` ограничивает переменные функцией. `return 0` означает успех, `return 1` — ошибку; функция не закрывает SSH. `[[ ... =~ ... ]]` проверяет числовой вид номера, `=` сравнивает строки, `&&` требует всех условий. **Ожидается:** отсутствие вывода. Перед последующими сетевыми изменениями будем вызывать эту проверку.

## 7. Соедините среды виртуальным кабелем

```bash
lab_check_namespaces &&
    sudo ip -n "$LAB_NS_A" link add lab0 type veth peer name lab1 &&
    sudo ip -n "$LAB_NS_A" link set dev lab1 netns "$LAB_NS_B"
```

`ip -n ИМЯ` выполняет сетевую операцию в выбранном пространстве. `link add lab0 type veth peer name lab1` создаёт **оба конца сразу в среде A**. Затем `link set dev lab1 netns ...` переносит второй конец в B. Ни один конец не создаётся в основной сетевой среде сервера.

**Ожидается:** отсутствие вывода. Проверьте результат:

```bash
sudo ip -n "$LAB_NS_A" -brief link show
sudo ip -n "$LAB_NS_B" -brief link show
```

**Пример:** в A видны `lo` и `lab0`, в B — `lo` и `lab1`. Состояние новых интерфейсов пока `DOWN`; число после `@if` — технический индекс соседа, его не нужно подставлять в команды.

Поднимите loopback и концы кабеля:

```bash
lab_check_namespaces &&
    sudo ip -n "$LAB_NS_A" link set dev lo up &&
    sudo ip -n "$LAB_NS_B" link set dev lo up &&
    sudo ip -n "$LAB_NS_A" link set dev lab0 up &&
    sudo ip -n "$LAB_NS_B" link set dev lab1 up
```

`link set dev ... up` административно включает интерфейс. `lo` — локальный интерфейс среды. **Ожидается:** отсутствие сообщений; после повторной краткой проверки оба veth имеют состояние `UP` при поднятом соседе.

## 8. Назначьте адреса и проверьте связь

```bash
lab_check_namespaces &&
    sudo ip -n "$LAB_NS_A" address add 192.0.2.1/30 dev lab0 &&
    sudo ip -n "$LAB_NS_B" address add 192.0.2.2/30 dev lab1
sudo ip -n "$LAB_NS_A" -brief -4 address show
sudo ip -n "$LAB_NS_B" -brief -4 address show
```

`address add` добавляет адрес с префиксом к `dev` — указанному устройству. `-4` оставляет IPv4. **Ожидается:** `192.0.2.1/30` у `lab0`, `192.0.2.2/30` у `lab1`. Повторное `add` того же адреса может дать `File exists`: это не повод удалять адреса основной системы.

```bash
sudo ip netns exec "$LAB_NS_A" ping -n -c 3 -W 1 192.0.2.2
sudo ip netns exec "$LAB_NS_B" ping -n -c 3 -W 1 192.0.2.1
```

`ip netns exec` запускает программу в выбранной среде. У `ping` флаг `-n` отключает преобразование адресов в имена, `-c 3` ограничивает число запросов тремя, `-W 1` задаёт ожидание ответа в секундах. **Ожидается:** ответы и итог `3 packets transmitted, 3 received`, обычно `0% packet loss`.

Это проверка ICMP-доступности, а не гарантия исправности любого приложения. Пакеты проходят внутри учебной пары, доступ в Интернет и работа DNS для них не нужны.

```bash
sudo ip -n "$LAB_NS_A" route show
sudo ip -n "$LAB_NS_A" neighbour show
sudo ip -n "$LAB_NS_A" -statistics link show dev lab0
```

`route show` показывает маршрут подключённой сети, который появился при назначении адреса. `neighbour show` — сопоставление соседнего IP и MAC. `-statistics link show` добавляет счётчики принятых и переданных пакетов; в обычном `link show` также виден MTU.

**Пример маршрута:** `192.0.2.0/30 dev lab0 proto kernel scope link src 192.0.2.1`. В таблице соседей ожидается `192.0.2.2` с MAC, состояние может быть `REACHABLE`, `STALE` или другим нормальным промежуточным состоянием.

## 9. Добавьте отдельный маршрут

Назначим серверной среде ещё один адрес на loopback:

```bash
lab_check_namespaces &&
    sudo ip -n "$LAB_NS_B" address add 203.0.113.10/32 dev lo &&
    sudo ip -n "$LAB_NS_A" route add 203.0.113.10/32 via 192.0.2.2 dev lab0
sudo ip -n "$LAB_NS_A" route get 203.0.113.10
sudo ip netns exec "$LAB_NS_A" ping -n -c 3 -W 1 203.0.113.10
```

`/32` здесь обозначает единственный дополнительный адрес. `route add ... via ... dev ...` говорит клиенту: передавать пакеты этому адресу через соседа `.2` и `lab0`. `route get` показывает выбранный путь.

**Ожидается:** маршрут через `192.0.2.2`, затем три ответа. Пересылку IP включать не нужно: целевой адрес принадлежит самой среде B, а не третьей сети за ней. Маршрут по умолчанию основной ОС не добавляется и не меняется.

Сохраните сетевые результаты:

```bash
sudo ip -n "$LAB_NS_A" -4 address show > "$LAB_BASE/report/client-addresses.txt"
sudo ip -n "$LAB_NS_B" -4 address show > "$LAB_BASE/report/server-addresses.txt"
sudo ip -n "$LAB_NS_A" route show > "$LAB_BASE/report/client-routes.txt"
```

`>` сохраняет вывод в файлы личного отчёта от имени вашей оболочки. **Ожидается:** отсутствие сообщений и три непустых файла.

## 10. Разберите постоянные сетевые настройки

Команда `ip` меняет текущую конфигурацию ядра. После удаления пространства или перезагрузки стенд исчезнет. Для постоянной настройки используются управляющие средства конкретной системы: например, ifupdown, NetworkManager или systemd-networkd.

Прочитайте состояние, ничего не переключая:

```bash
systemctl is-active networking.service NetworkManager.service systemd-networkd.service
if [ -f /etc/network/interfaces ]; then
    sudo sed -n '1,100p' /etc/network/interfaces
fi
sed -n '1,80p' /etc/resolv.conf
```

`is-active` выводит состояние каждого указанного unit; отсутствующие или неактивные службы могут дать ненулевой общий код, здесь это результат проверки. `-f` проверяет обычный файл. `sed -n '1,100p'` отключает общий вывод и печатает выбранный диапазон строк.

**Ожидается:** фактические состояния служб и доступная конфигурация. Наличие нескольких служб не означает, что всеми интерфейсами одновременно управляют все они. Файл `/etc/resolv.conf` может быть ссылкой или формироваться автоматически; ручная замена способна нарушить разрешение имён.

Подготовьте только учебный образец ifupdown:

```bash
cat > "$LAB_BASE/model/interfaces-client" <<'EOF'
auto lo
iface lo inet loopback

auto lab0
iface lab0 inet static
    address 192.0.2.1
    netmask 255.255.255.252
EOF
cat "$LAB_BASE/model/interfaces-client"
```

`cat > ... <<'EOF'` записывает буквальный текст до отдельного `EOF`. **Ожидается:** показанный файл. `auto` отмечает автоматическое включение при обработке такой конфигурации; `iface` описывает интерфейс; `inet` — IPv4, `static` — статические параметры; `address` и `netmask` задают адрес и маску.

Файл **не подключается** к сетевым службам. Он объясняет формат, но не обеспечивает автосоздание namespaces и veth. Рабочие `/etc/network/interfaces`, профили NetworkManager и DNS не редактируются. Команды `ifup` и `ifdown` по этому образцу не запускаются: у них есть собственное состояние и обработчики, которые здесь не нужны.

## 11. Создайте сценарий проверки учебной сети

Системная служба получит административные права, необходимые для входа в network namespace. Поэтому её сценарий будет установлен в каталог root, где обычный пользователь не может его изменить. Служба только проверяет связь и пишет учебный результат; она не перенастраивает сеть.

Сначала создайте исходный файл:

```bash
cat > "$LAB_BASE/check-network.sh" <<'EOF'
#!/bin/sh
set -eu
PATH=/usr/sbin:/usr/bin:/sbin:/bin
export PATH
uid_target="$1"
case "$uid_target" in ''|*[!0-9]*) exit 2 ;; esac
run_dir="/run/astra-schednet-$uid_target"
ns_a="astra_snet_a_$uid_target"
ns_b="astra_snet_b_$uid_target"
expected_a="$(cat "$run_dir/ns-a.inode")" || exit 2
expected_b="$(cat "$run_dir/ns-b.inode")" || exit 2
actual_a="$(stat -L -c '%i' "/run/netns/$ns_a")" || exit 2
actual_b="$(stat -L -c '%i' "/run/netns/$ns_b")" || exit 2
if [ "$expected_a" != "$actual_a" ] || [ "$expected_b" != "$actual_b" ]; then
    printf '%s\n' 'Namespace identity mismatch' >&2
    exit 2
fi
if ip netns exec "$ns_a" ping -n -c 1 -W 1 192.0.2.2 > /dev/null 2>&1; then
    result=ok
else
    result=failed
fi
printf 'time=%s target=192.0.2.2 result=%s\n' "$(date --iso-8601=seconds)" "$result" |
    tee -a "$run_dir/monitor.log" || exit 2
[ "$result" = ok ]
EOF
/bin/sh -n "$LAB_BASE/check-network.sh"
```

**Ожидается:** отсутствие сообщений, сценарий пока не запущен. `/bin/sh -n` проверяет синтаксис.

Разбор строк сценария:

- `#!/bin/sh` задаёт интерпретатор. `set -e` завершает отдельный сценарий при необработанной ошибке, `-u` — при обращении к незаданной переменной; это не настройка вашей SSH-оболочки.
- `PATH` задаёт поиск программ; `export` передаёт его дочерним командам. `$1` — UID из аргумента службы. `case` разрешает только непустую последовательность цифр; `exit 2` обозначает ошибку подготовки.
- Пути и имена выводятся из этого UID. `cat` и `stat` сравнивают созданные пространства с сохранёнными номерами. `!=` — неравенство, `||` — «или»; `>&2` выводит сообщение в поток ошибок.
- `ip netns exec ... ping` проверяет только клиента учебной сети. `-c 1` отправляет один запрос. `> /dev/null 2>&1` скрывает обычный вывод и ошибку ping, потому что итог записывается отдельно.
- `printf` создаёт запись с временем и `result=ok` либо `failed`. `tee -a` одновременно выводит её и дописывает в журнал; `-a` сохраняет прежнее содержимое. Ошибки чтения состояния или записи журнала завершают сценарий кодом `2` благодаря `|| exit 2`.
- Последняя проверка возвращает успех при `ok` и код `1` при отказе. Так systemd сможет отличить успешную проверку от неудачной.

Установите сценарий с владельцем root:

```bash
sudo install -o root -g root -m 644 -- "$LAB_BASE/check-network.sh" "$LAB_RUN/check-network.sh"
stat -c '%U %G %a %n' -- "$LAB_RUN" "$LAB_RUN/check-network.sh"
```

`install` копирует файл с явными параметрами: `-o` — владелец, `-g` — группа, `-m` — права. `stat -c` показывает владельца `%U`, группу `%G`, права `%a`, имя `%n`. Исполняемый бит не нужен, потому что службу запускает `/bin/sh`.

**Ожидается:** каталог `root root 755`, сценарий `root root 644`. Обычный пользователь может прочитать сценарий, но не заменить файл или изменить его. Если владелец другой или группа/остальные могут писать, службу пока не запускайте.

## 12. Опишите и проверьте службу systemd

```bash
cat > "$LAB_BASE/$LAB_SERVICE" <<EOF
[Unit]
Description=Astra training network check $LAB_UID

[Service]
Type=oneshot
ExecStart=/bin/sh $LAB_RUN/check-network.sh $LAB_UID
TimeoutStartSec=10s
UMask=0022
NoNewPrivileges=yes
ProtectHome=yes
PrivateTmp=yes
StandardOutput=journal
StandardError=journal
EOF

cat > "$LAB_BASE/$LAB_TIMER" <<EOF
[Unit]
Description=Astra training network timer $LAB_UID

[Timer]
OnActiveSec=5s
OnUnitInactiveSec=20s
AccuracySec=1s
Unit=$LAB_SERVICE
EOF
systemd-analyze verify "$LAB_BASE/$LAB_SERVICE" "$LAB_BASE/$LAB_TIMER"
```

Здесь `EOF` без кавычек, чтобы Bash подставил наши безопасные пути и UID. `systemd-analyze verify` проверяет unit-файлы до установки. **Ожидается:** отсутствие ошибок. Предупреждения о других unit системы нужно отличать от ошибок наших файлов; при сомнении сначала разберите вывод.

| Параметр | Для чего нужен |
| --- | --- |
| `[Unit]`, `Description` | Общая секция и описание |
| `[Service]`, `Type=oneshot` | Короткая работа, которая заканчивается после проверки |
| `ExecStart` | Команда, полный путь root-сценария и числовой UID стенда |
| `TimeoutStartSec=10s` | Ограничение времени одного запуска |
| `UMask=0022` | Создавать обычный учебный журнал с чтением для остальных, чтобы Cron обычного пользователя мог прочитать результат; писать в каталог и журнал может только root |
| `NoNewPrivileges=yes` | Запрет получения дополнительных привилегий через последующие запуски программ; уже имеющиеся права root не отнимает |
| `ProtectHome=yes` | Закрыть службе доступ к домашним каталогам |
| `PrivateTmp=yes` | Отдельное представление временных каталогов для службы |
| `StandardOutput/Error=journal` | Направить вывод и ошибки в журнал службы |
| `[Timer]`, `OnActiveSec=5s` | Первый запуск примерно через пять секунд после активации таймера |
| `OnUnitInactiveSec=20s` | Следующий запуск примерно через двадцать секунд после завершения службы |
| `AccuracySec=1s` | Окно группировки запуска, а не гарантия точности до секунды |
| `Unit` | Имя службы, запускаемой таймером |

Параметр `User` не задан, поэтому системная служба выполняется от root. Это нужно для `ip netns exec`; поэтому её исполняемый сценарий и рабочий каталог защищены от записи обычным пользователем. Оба unit не содержат `[Install]`: включать их при загрузке в этой практике не требуется.

Установите только свои два unit:

```bash
sudo install -o root -g root -m 644 -- "$LAB_BASE/$LAB_SERVICE" "/run/systemd/system/$LAB_SERVICE" &&
    sudo install -o root -g root -m 644 -- "$LAB_BASE/$LAB_TIMER" "/run/systemd/system/$LAB_TIMER" &&
    sudo systemctl daemon-reload
```

`daemon-reload` просит systemd перечитать определения unit. Он сам по себе не перезапускает сеть, SSH или все службы. **Ожидается:** отсутствие ошибок.

Проверьте путь загруженного определения и выполните один ручной запуск:

```bash
systemctl show "$LAB_SERVICE" --property=FragmentPath --property=User
lab_check_namespaces && sudo systemctl start "$LAB_SERVICE"
systemctl show "$LAB_SERVICE" --property=Result --property=ExecMainStatus --property=ActiveState
cat "$LAB_RUN/monitor.log"
```

`FragmentPath` показывает файл определения; пустое `User=` означает системного пользователя по умолчанию, root. `start` запускает нашу службу. `Result` — итог, `ExecMainStatus` — код завершения, `ActiveState` — текущее состояние.

**Ожидается:** путь `/run/systemd/system/astra-schednet-1000.service`, `Result=success`, `ExecMainStatus=0`, `ActiveState=inactive`, строка `result=ok`. Для завершившегося `oneshot` состояние `inactive` нормально: он не обязан постоянно работать.

## 15. Настройте отчёт через Cron

### 15.1. Как читать время Cron

В строке расписания идут минута, час, день месяца, месяц, день недели. Для файла `/etc/cron.d` затем обязательно указывается пользователь, а после него — команда.

| Расписание | Смысл |
| --- | --- |
| `* * * * *` | Каждую минуту |
| `*/5 * * * *` | В минуты 00, 05, 10 и так далее каждого часа |
| `30 9 * * 1-5` | В 09:30 с понедельника по пятницу |
| `0 2 1 * *` | В 02:00 первого числа каждого месяца |

`*` — любое значение, `/` задаёт шаг, `-` — диапазон, запятая — перечисление. Нумерация дней недели: 0 и 7 — воскресенье, 1 — понедельник. Если одновременно ограничены день месяца и день недели, между ними используется условие «или». Cron ориентируется на часы сервера и не воспроизводит все пропущенные обычные запуски после выключения.

### 15.2. Создайте сценарий обычного пользователя

```bash
cat > "$LAB_BASE/make-report.sh" <<'EOF'
#!/bin/sh
set -eu
PATH=/usr/bin:/bin
export PATH
umask 077
uid_target="$(id -u)"
source_file="/run/astra-schednet-$uid_target/monitor.log"
printf 'report_time=%s\n' "$(date --iso-8601=seconds)"
if [ -r "$source_file" ]; then
    tail -n 1 -- "$source_file"
else
    printf '%s\n' 'network_report=unavailable'
fi
EOF
chmod 600 -- "$LAB_BASE/make-report.sh"
/bin/sh -n "$LAB_BASE/make-report.sh"
/bin/sh "$LAB_BASE/make-report.sh"
```

**Ожидается:** две строки: время отчёта и последняя проверка сети. `umask 077` закрывает доступ остальных к новым файлам сценария; `-r` проверяет чтение источника. В остальном используются уже разобранные `set`, `PATH`, `id`, `printf` и `tail`.

Этот сценарий не вызывает `sudo` и не входит в namespace. Он только читает общедоступный учебный результат из каталога root. Файл с правами `600` не исполняется напрямую: Cron будет передавать его `/bin/sh`.

### 15.3. Подготовьте отдельный файл расписания

```bash
printf 'SHELL=/bin/sh\nPATH=/usr/bin:/bin\nMAILTO=""\n* * * * * %s /bin/sh "%s/make-report.sh" >> "%s/report/cron-reports.log" 2>&1\n' \
    "$LAB_USER" "$LAB_BASE" "$LAB_BASE" > "$LAB_BASE/cron.conf"
cat "$LAB_BASE/cron.conf"
```

`printf` подставляет значения вместо `%s`, `\n` завершает строки. Обратная косая черта продолжает команду Bash на следующей строке; в готовом файле задание находится на одной строке.

**Пример результата:**

```cron
SHELL=/bin/sh
PATH=/usr/bin:/bin
MAILTO=""
* * * * * student /bin/sh "/var/tmp/astra-schednet-1000/make-report.sh" >> "/var/tmp/astra-schednet-1000/report/cron-reports.log" 2>&1
```

`SHELL` выбирает оболочку команды; `PATH` — путь поиска; `MAILTO=""` отключает почту для этого файла расписания. `>>` дописывает результат, `2>&1` направляет ошибки в тот же журнал. Перевод строки в конце задания обязателен и уже добавлен `printf`.

Поле `student` соответствует вашей обычной учётной записи. В личном `crontab -e` такого поля нет; переносить эту строку туда без адаптации нельзя. Наши задания из `/etc/cron.d` команда `crontab -l` не показывает. `crontab -r` удаляет личную таблицу целиком и для упражнения не используется.

В строке Cron не размещается команда `date` с `%`: у неэкранированного процента там специальный смысл. Вычисление времени вынесено внутрь сценария.

### 15.4. Установите и проверьте задание

```bash
sudo sh -c 'umask 022; set -C; cat > "$1"' sh "$LAB_CRON" < "$LAB_BASE/cron.conf" &&
    sudo stat -c '%U %a %n' -- "$LAB_CRON"
```

`sudo sh -c` записывает только подготовленный файл с правами администратора. Первый `sh` после текста задаёт условное имя оболочки, следующий аргумент становится `$1`. `<` передаёт содержимое кандидата программе `cat`. `umask 022` даёт создаваемому обычному файлу права `644`; `set -C` запрещает перезапись существующего обычного файла через `>`.

**Ожидается:** `root 644 /etc/cron.d/astra-schednet-1000`. Если имя уже занято или права другие, остановитесь. В имени нет точки, только разрешённые буквы, цифры и дефисы. Перезапуск Cron не нужен: он обнаруживает изменение автоматически.

Подождите одну-две минуты:

```bash
tail -n 6 -- "$LAB_BASE/report/cron-reports.log"
grep -c '^report_time=' "$LAB_BASE/report/cron-reports.log"
```

**Ожидается:** пары строк с временем отчёта и результатом сети; число отчётов не меньше одного. `grep -c` считает совпавшие строки, `^` привязывает поиск к началу строки. Через минуту число должно увеличиться.

Если записей нет, проверьте `cron.service`, установленный файл, права сценария и journal:

```bash
systemctl is-active cron.service
sudo journalctl --identifier=CRON --since='5 minutes ago' --no-pager --lines=20
```

`--identifier=CRON` фильтрует по метке процесса; она зависит от настройки системы, поэтому пустая выборка сама по себе не доказывает отсутствие запуска. **Ожидается:** `active` и доступные сообщения Cron. При запрете через PAM или политики Astra изучите причину, не отключайте ограничения ради задания.

## 16. Сравните интервалы и календарь

Наш systemd-таймер отсчитывает интервалы относительно активации и завершения службы. Cron использует календарные минуты. Интервал в 20 секунд удобен для обучения, а не является рекомендацией для рабочей проверки сети.

Посмотрите интерпретацию календарного выражения systemd:

```bash
systemd-analyze calendar 'Mon..Fri 09:30'
date --iso-8601=seconds
```

`calendar` разбирает выражение и показывает ближайшее срабатывание, ничего не устанавливая. `Mon..Fri` — диапазон будних дней. **Ожидается:** нормализованное выражение, ближайшее время и текущие часы с часовым поясом.

Для сравнения можно сохранить образец другого таймера:

```bash
cat > "$LAB_BASE/model/calendar-example.timer" <<EOF
[Unit]
Description=Astra calendar example

[Timer]
OnCalendar=Mon..Fri 09:30
Persistent=yes
Unit=$LAB_SERVICE
EOF
cat "$LAB_BASE/model/calendar-example.timer"
```

**Ожидается:** показанный текст. `OnCalendar` задаёт календарное расписание, `Persistent=yes` позволяет при активации наверстать пропущенное календарное срабатывание при наличии сохранённого состояния. Это не означает повтор каждого пропущенного запуска и не относится к нашему интервальному таймеру.

Файл — только образец, он не устанавливается в systemd. Действующий таймер остаётся прежним; серверные часы и часовой пояс не меняются.

## 17. Сохраните результаты и сравните основную сеть

```bash
ip -4 route show table main > "$LAB_BASE/report/host-routes-v4-after.txt"
ip -6 route show table main > "$LAB_BASE/report/host-routes-v6-after.txt"
diff -u "$LAB_BASE/report/host-routes-v4-before.txt" "$LAB_BASE/report/host-routes-v4-after.txt"
diff -u "$LAB_BASE/report/host-routes-v6-before.txt" "$LAB_BASE/report/host-routes-v6-after.txt"
```

`diff -u` показывает различия в объединённом формате. **Ожидается:** отсутствие вывода, код `0`, если таблицы не изменились. Код `1` означает найденные различия, а не ошибку программы. Независимые изменения DHCP, VPN или администратора возможны: при различиях выясните причину, а не восстанавливайте таблицу вручную по учебному файлу.

Снова посмотрите маршрут клиенту SSH тем блоком `route get`, который использовали в разделе 4. Это чтение состояния, а не попытка изменить подключение.

```bash
cp -- "$LAB_RUN/monitor.log" "$LAB_BASE/report/monitor-snapshot.log"
sudo journalctl --unit="$LAB_SERVICE" --no-pager --output=short-iso > "$LAB_BASE/report/service-journal.txt"
systemctl list-timers --all --no-pager "$LAB_TIMER" > "$LAB_BASE/report/timer-status.txt"
sha256sum "$LAB_BASE/report/client-addresses.txt" "$LAB_BASE/report/server-addresses.txt" \
    "$LAB_BASE/report/client-routes.txt" "$LAB_BASE/report/monitor-snapshot.log" \
    "$LAB_BASE/report/service-journal.txt" > "$LAB_BASE/report/SHA256SUMS"
sha256sum --check "$LAB_BASE/report/SHA256SUMS"
```

`cp` делает снимок текущего учебного журнала, чтобы последующие записи таймера не меняли проверяемый файл. `sha256sum` вычисляет суммы содержимого; `--check` сверяет их с сохранённым списком. **Ожидается:** пять строк `OK`. Эти суммы проверяют совпадение с сохранённым содержимым, а не защищают от изменения обоих файлов администратором.

## 18. Какие скриншоты сохранить

| Скриншот | Раздел | Что должно быть видно |
| --- | --- | --- |
| Адреса и связь двух сред | 8 | Адреса `.1/30`, `.2/30` и успешный ping |
| Дополнительный маршрут | 9 | `route get 203.0.113.10` через `.2` и ответы ping |
| Определение и выполнение службы | 12 | Собственный `FragmentPath`, `Result=success`, код `0` |
| Таймер | 13 | `list-timers` с собственной службой и несколько записей |
| Отказ и восстановление | 14 | `result=failed`, затем новая запись `result=ok` |
| Cron | 15 | Собственный файл расписания и несколько отчётов с разным временем |
| Проверка файлов | 17 | Пять контрольных сумм с `OK` |

Снимки должны содержать команды и их результаты. Не подменяйте реальный вывод примерами из текста. В отчёте отметьте, что сеть моделировалась двумя namespaces на одной машине, конфигурации постоянной сети были только образцами, а основной интерфейс SSH не перенастраивался.

Сохраните нужные результаты до очистки: удаление стенда удалит и его файлы отчёта. Системный journal при очистке не стирается.

## 19. Если SSH оборвался

Повторно подключитесь к той же машине под тем же пользователем. Повторите только блок переменных из раздела 5 и определение `lab_check_namespaces` из раздела 6. Каталоги, namespaces, unit и Cron повторно не создавайте.

Проверьте состояние:

```bash
sudo ip netns list
systemctl list-timers --all --no-pager "$LAB_TIMER"
systemctl show "$LAB_SERVICE" --property=Result --property=ExecMainStatus
tail -n 5 -- "$LAB_RUN/monitor.log"
```

**Ожидается:** сохранившийся стенд и последние результаты. Cron и таймер обычно продолжают работать после закрытия SSH. Если разрыв произошёл во время отключения `lab1`, после проверки принадлежности верните его в `up` командой раздела 14.

После перезагрузки `/run` очищается, namespaces и временные unit исчезают. Файл Cron в `/etc/cron.d` при этом сохраняется и может продолжать запускать пользовательский сценарий; тот запишет `network_report=unavailable`. В таком случае сначала удалите **свой** файл Cron по разделу 20.1. Оставшиеся материалы `/var/tmp` могут сохраняться, но подчиняются политике очистки сервера; не создавайте новый стенд поверх них автоматически.

Если часть объектов не была создана из-за ошибки, удаляйте только подтверждённые собственные объекты. Не применяйте массовое удаление всех namespaces и остановку всех таймеров.

## 20. Завершите работу в правильном порядке

### 20.1. Удалите только своё расписание Cron

```bash
if [ "$LAB_CRON" = "/etc/cron.d/astra-schednet-$(id -u)" ] &&
    sudo cmp -s -- "$LAB_BASE/cron.conf" "$LAB_CRON"; then
    sudo rm -- "$LAB_CRON" && printf '%s\n' 'Учебное задание Cron удалено.'
else
    printf '%s\n' 'STOP: путь или содержимое Cron не совпадает; проверьте файл.'
fi
```

`cmp -s` молча сравнивает содержимое кандидата и установленного файла. `rm` удаляет один явно заданный файл. **Ожидается:** подтверждение удаления. При несовпадении не удаляйте чужие изменения.

Подождите одну-две минуты, чтобы Cron заметил удаление, а уже начатый короткий отчёт завершился. Убедитесь, что число строк `report_time=` больше не растёт. Саму службу Cron не останавливайте.

### 20.2. Остановите только свой таймер и его службу

```bash
if [ "$(systemctl show --property=FragmentPath --value "$LAB_TIMER")" = "/run/systemd/system/$LAB_TIMER" ] &&
    [ "$(systemctl show --property=FragmentPath --value "$LAB_SERVICE")" = "/run/systemd/system/$LAB_SERVICE" ]; then
    sudo systemctl stop "$LAB_TIMER" "$LAB_SERVICE"
else
    printf '%s\n' 'STOP: загружены неожиданные unit-файлы.'
fi
systemctl is-active "$LAB_TIMER" "$LAB_SERVICE"
```

Проверка `FragmentPath` подтверждает выбранные определения. `stop` прекращает только эти два unit. **Ожидается:** два `inactive`; ненулевой код `is-active` здесь нормален. Если остановка завершилась ошибкой или один unit активен, сеть пока не удаляйте.

### 20.3. Удалите учебные пространства имён

```bash
if lab_check_namespaces; then
    LAB_PIDS_A="$(sudo ip netns pids "$LAB_NS_A")"
    LAB_PIDS_B="$(sudo ip netns pids "$LAB_NS_B")"
    if [[ -z "$LAB_PIDS_A" && -z "$LAB_PIDS_B" ]]; then
        sudo ip netns delete "$LAB_NS_A" &&
            sudo ip netns delete "$LAB_NS_B"
    else
        printf '%s\n' 'STOP: внутри учебной сети ещё есть процессы; проверьте их.'
    fi
fi
```

`ip netns pids` перечисляет процессы пространства; `-z` проверяет пустой результат. Удаление выполняется только после остановки задач, проверки идентичности и отсутствия процессов. `netns delete` удаляет выбранное имя; veth учебной пары исчезают вместе с освобождением сред.

**Ожидается:** отсутствие ошибок. При обнаружении процессов не завершайте их массово: выясните, не осталась ли ваша команда или чужой сеанс в этой среде.

```bash
sudo ip netns list
ip -brief address show
```

**Ожидается:** наших двух имён нет; реальные интерфейсы сервера на месте. Чужие namespaces могут оставаться и не относятся к упражнению.

### 20.4. Удалите только созданные административные файлы

```bash
if [ "$LAB_RUN" = "/run/astra-schednet-$(id -u)" ] &&
    [ "$LAB_SERVICE" = "astra-schednet-$(id -u).service" ] &&
    [ "$LAB_TIMER" = "astra-schednet-$(id -u).timer" ]; then
    sudo rm -- "/run/systemd/system/$LAB_TIMER" "/run/systemd/system/$LAB_SERVICE" &&
        sudo systemctl daemon-reload &&
        sudo rm -- "$LAB_RUN/check-network.sh" "$LAB_RUN/ns-a.inode" "$LAB_RUN/ns-b.inode" "$LAB_RUN/monitor.log" &&
        sudo rmdir -- "$LAB_RUN"
else
    printf '%s\n' 'STOP: неожиданные пути или имена.'
fi
```

Удаляются только перечисленные файлы. `rmdir` удаляет каталог исключительно если он пуст; неизвестное содержимое не удаляется рекурсивно с правами root. **Ожидается:** отсутствие ошибок. Если файл уже отсутствует после частичной очистки, сначала проверьте состояние и корректируйте только список собственных оставшихся файлов.

После намеренного сбоя в памяти systemd может ещё оставаться неудачное состояние нашего уже удалённого unit. Его можно сбросить адресно:

```bash
sudo systemctl reset-failed "$LAB_SERVICE"
```

`reset-failed` очищает статус ошибки только указанной службы, не запускает её и не очищает journal. **Ожидается:** отсутствие вывода; сообщение об уже отсутствующем unit не требует восстановления службы.

### 20.5. Удалите личный каталог

```bash
if [ "$LAB_BASE" = "/var/tmp/astra-schednet-$(id -u)" ] &&
    [ ! -e "$LAB_CRON" ] && [ ! -L "$LAB_CRON" ] && [ ! -d "$LAB_RUN" ]; then
    cd "$HOME" && rm -rI -- "$LAB_BASE"
else
    printf '%s\n' 'STOP: сначала завершите удаление задания и административных файлов.'
fi
```

`!` отрицает проверку; `cd "$HOME"` выводит оболочку из удаляемого дерева. `rm -r` удаляет дерево рекурсивно, заглавная `-I` запрашивает подтверждение. **Ожидается:** вопрос о вашем `/var/tmp/astra-schednet-UID`; проверьте путь и подтвердите. `sudo` для этого шага не нужен.

## 21. Типичные вопросы и ошибки

| Ситуация | Что означает и что делать |
| --- | --- |
| `Operation not permitted` при создании namespaces | Нет необходимых возможностей или действует политика защиты; не отключайте защиту и не переходите к изменению основной сети |
| `RTNETLINK answers: File exists` | Объект уже создан; прочитайте его состояние, не повторяйте весь сценарий поверх стенда |
| Ping не отвечает | Проверьте `up` обоих концов, адреса и префикс, маршруты именно внутри выбранной среды |
| `Network is unreachable` | В выбранной среде нет подходящего маршрута; наличие маршрута в основной ОС не помогает другой среде |
| Служба `inactive`, но результат `success` | Нормально для завершившегося `oneshot` |
| Служба `failed`, код `1` | Проверка не получила ответ; это ожидаемо во время учебного отключения |
| Код `2` или сообщение про inode | Нарушена подготовка или изменились namespaces; не продолжайте проверки по прежним именам |
| Таймер активен, но новой записи пока нет | Посмотрите ближайшее время и журнал; интервал отсчитывается от завершения службы |
| Cron не создаёт файл | Проверьте активность службы, имя файла без точки, поле пользователя, права, полный путь и политики запуска |
| У Cron нет переменных SSH | Это нормально: его среда отдельна; сценарий сам получает UID и задаёт PATH |
| Отчёт говорит `unavailable` | Исходный учебный журнал отсутствует, например после перезагрузки |

**С какого пункта выполнять команды?** С раздела 3. Разделы 1–2 сначала прочитайте. Начинать с середины нельзя: далее используются уже созданные переменные и объекты.

**Можно ли просто копировать команды?** Да, по одному полному блоку в Bash удалённой Astra, с проверкой каждого результата. Установку отсутствующих пакетов и восстановление выполняйте только при соответствующей ситуации. При ошибке сначала разберите её.

**Почему нет настройки настоящего `ens3`?** Через него может идти SSH. Для освоения адресов, маршрутов и расписаний достаточно виртуальной сети. Изменение реального адреса и шлюза требует отдельного плана доступа и восстановления.

**Нужно ли менять DNS?** Нет: проверки используют числовые IP, а рабочий DNS читается для знакомства. Образец сетевой конфигурации не применяется к основной системе.

**Можно ли оставить всё работать?** Это учебные задания с частыми проверками, не готовый мониторинг производства. Завершайте их разделом 20. Таймер временный, но файл Cron переживает перезагрузку до удаления.
