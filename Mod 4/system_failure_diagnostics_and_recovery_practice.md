# Модуль 4. Диагностика системных сбоев и восстановление компонентов Astra Linux

Вся работа выполняется **на одной удалённой Astra Linux Special Edition 1.7 по SSH**, в Bash обычного пользователя с доступом к `sudo`. Второй сервер, графическая среда и команды на вашем компьютере не требуются.

Сначала разберём порядок диагностики: состояние системы, ресурсы, журналы, службы и пакеты. Затем создадим собственный маленький пакет с текстовым файлом и учебную службу. Последовательно воспроизведём пять неисправностей, найдём их причины и восстановим работу.

| Неисправность | Что исследуем | Как восстанавливаем |
| --- | --- | --- |
| Неверная настройка | Сообщение приложения, код завершения, сравнение с резервной копией | Возвращаем собственную исправную конфигурацию |
| Файл недоступен службе | Владельца, права, пользователя службы | Возвращаем известные правильные права одного учебного файла |
| Содержимое файла повреждено | Принадлежность пакету, проверку содержимого и контрольную сумму | Переустанавливаем только собственный пакет из проверенного `.deb` |
| Файл удалён | Наличие файла и его запись в пакетной базе | Восстанавливаем тем же собственным пакетом |
| Неверный путь запуска | Определение unit, drop-in и ошибку `203/EXEC` | Удаляем только свою ошибочную настройку запуска |

Настоящие пакеты SSH, systemd и компонентов защиты не повреждаются и не переустанавливаются. Учебная служба работает от вашего обычного пользователя, не слушает портов и не меняет сеть. Файл unit хранится в `/run/systemd/system`, без автозапуска; пакет содержит только один текстовый файл в своём подкаталоге `/usr/share`.

Установка и удаление учебного пакета действительно меняют пакетную базу. Его имя содержит ваш UID; перед установкой проверяется отсутствие такого пакета и каталога. Системные журналы не очищаются, ошибки других служб не сбрасываются. Учебные события остаются в journal по обычным правилам хранения.

Здесь моделируются отказы компонентов при работающей ОС. Если сервер вообще не загружается или SSH уже недоступен, выполнить эти команды через прежний сеанс невозможно: сначала потребуется доступная консоль виртуальной машины или другой предусмотренный способ доступа администратора. Перезагрузка удалённого сервера в маршрут практики не входит.

Примеры вывода условные: пользователь `student`, UID `1000`, имя узла `astra-lab`. Команды сами определяют UID. Даты, версии и номера процессов на вашей машине отличаются.

## Часть 1. Подготовка и порядок диагностики

### 1. Как выполнять практику

Начинайте командные блоки с раздела 3. Сначала прочитайте объяснение шага, затем выполните один полный блок и сравните результат. При `STOP` или неожиданной ошибке следующий шаг не выполняйте.

Многострочные блоки с `EOF` вставляются целиком, включая завершающую строку. Если из-за неполного ввода Bash показывает `>`, Ctrl+C отменяет незавершённую команду. Функции тоже вставляются целиком: определение сохраняет команды, а не выполняет весь опыт сразу.

Не включайте общий `set -e` в SSH-оболочке. В этой практике есть специально вызванные неудачи; они обрабатываются условиями. Команды с ожидаемой ошибкой отдельно обозначены и не означают, что нужно закрыть терминал.

После каждого неисправного состояния обязательно выполните восстановление и получите исправный результат. Не переходите к следующему опыту с неустранённой причиной предыдущего. Скриншоты сохраняйте до очистки.

### 2. Диагностика: от симптома к проверяемой причине

Полезный порядок работы:

1. Установить, что именно не работает: вся машина, одна служба, доступ к файлу или отдельная операция.
2. Записать время наблюдения и состояние до изменения настроек.
3. Прочитать журнал выбранного компонента и код завершения.
4. Проверить ресурсы, пути, владельца и права, конфигурацию и принадлежность файлов пакету.
5. Выполнить одно обоснованное исправление и повторить тот же тест.

Симптом и причина — разные вещи. `failed` означает неудачу службы, но не объясняет её. Недоступность файла может быть следствием удаления, неправильного пути, обычных прав или политики защиты. Успешный запуск от root не доказывает доступность того же файла обычному пользователю службы.

| Проверка | На какой вопрос отвечает | Чего не доказывает |
| --- | --- | --- |
| `systemctl status/show` | В каком состоянии служба, чем закончился запуск | Почему приложение решило завершиться с этим кодом |
| `journalctl` | Какие события и ошибки были записаны | Что отсутствующая в выборке ошибка никогда не возникала |
| `df`, `free`, `ps` | Есть ли признаки нехватки ресурсов или нагрузки | Что причина обязательно в одном увиденном показателе |
| `stat`, `namei`, `test -r` | Какие права у пути и может ли выбранный пользователь читать файл | Что все политики безопасности разрешат любое дальнейшее действие |
| `dpkg --audit` | Есть ли незавершённые состояния пакетов | Что все установленные файлы исправны |
| `dpkg --verify` | Есть ли проверяемые расхождения содержимого с пакетной базой | Полную проверку прав, настроек и защищённости ОС |
| Контрольная сумма | Совпадает ли файл с сохранённым значением | Независимую подлинность, если можно подменить и файл, и сумму |

### 3. Проверьте ОС, оболочку и инструменты

```bash
whoami
hostname
cat /etc/astra_version
printf '%s\n' "$BASH_VERSION"
sudo -v
```

`whoami` показывает пользователя, `hostname` — машину, `cat` читает файл версии. `printf '%s\n'` выводит строку и перевод строки; `$BASH_VERSION` содержит версию Bash. `sudo -v` проверяет административные полномочия и при необходимости запрашивает пароль без отображения символов.

**Ожидается:** обычная учётная запись, Astra 1.7 и непустая версия Bash. После успешного `sudo -v` сообщений обычно нет.

```bash
export PATH="/usr/sbin:/usr/bin:/sbin:/bin:$PATH"
command -v systemctl systemd-analyze journalctl dpkg dpkg-query dpkg-deb apt-get apt-cache
command -v df free uptime ps stat namei sed awk grep diff cmp md5sum sha256sum install find
```

`export PATH=...` добавляет стандартные каталоги в начало пути поиска, сохраняя прежний путь после них. `command -v` показывает найденные программы. **Ожидается:** пути ко всем инструментам.

В Astra используются пакеты `.deb`. `dpkg` работает с установленными пакетами, `dpkg-deb` — с архивами, APT получает пакеты из настроенных репозиториев. `apt-cache policy` только показывает доступные версии; `apt-get update` обновляет индексы; `install` устанавливает выбранные пакеты. Общий `upgrade` не является способом диагностики конкретного сбоя.

Сборка нашего пакета не требует компилятора, `dpkg-dev`, Интернета и нового репозитория: достаточно установленного `dpkg-deb`. `free`, `uptime`, `ps` входят в `procps`, `namei` — в `util-linux`; остальные основные файловые команды — в `coreutils`.

Если отсутствует, например, `namei`, сначала посмотрите план установки его пакета:

```bash
apt-cache policy util-linux
sudo apt-get --simulate install --no-install-recommends --no-upgrade util-linux
```

`policy` показывает установленную и доступную версии. `--simulate` не применяет изменения; `--no-install-recommends` исключает необязательные рекомендации; `--no-upgrade` запрещает обновлять уже установленный явно запрошенный пакет, но не все зависимости.

**Ожидается:** понятный план из разрешённого репозитория вашего выпуска Astra. Если действительно нужна установка и план не требует нежелательных изменений:

```bash
sudo apt-get install --no-install-recommends --no-upgrade --no-remove util-linux
```

`--no-remove` запрещает удаление пакетов. **Ожидается:** успешная установка. Если инструменты уже есть, оба блока установки пропустите. Не подключайте репозитории другого выпуска, Debian или Ubuntu и не переустанавливайте базовые пакеты «на всякий случай».

### 4. Соберите исходное состояние без исправлений

```bash
date --iso-8601=seconds
uptime
systemctl is-system-running
systemctl --failed --no-pager
sudo dpkg --audit
sudo apt-get check
```

`date --iso-8601=seconds` показывает время с секундами и часовым поясом. `uptime` — время работы и среднюю нагрузку. `is-system-running` читает общее состояние systemd, `--failed` выбирает неудачные unit, `--no-pager` отключает постраничный просмотр. Ненулевой код при `degraded` — результат диагностики, а не команда выключения.

`dpkg --audit` ищет незавершённые состояния пакетов. `apt-get check` проверяет согласованность зависимостей без установки и удаления программ.

**Ожидается:** фактическое состояние сервера. `running` и пустой список failed означают отсутствие обнаруженных systemd неудач в этой проверке. Если уже есть чужие ошибки, запишите их; не исправляйте их массово в рамках упражнения. Если пакетная база сообщает незавершённые операции или нарушенные зависимости, сначала разберите это состояние, учебный пакет пока не устанавливайте.

Проверьте ресурсы:

```bash
df -h / /var /tmp
df -i / /var /tmp
free -h
ps -eo pid,comm,%cpu,%mem --sort=-%cpu | head -n 8
```

`df -h` показывает свободные блоки в удобных единицах, `-i` — inode. Пути могут относиться к одной файловой системе: отдельного раздела `/var` может не быть. `free -h` показывает память; `available` полезнее для оценки возможности новых выделений, чем только `free`.

`ps -e` выбирает все процессы, `-o` задаёт столбцы PID, имени, CPU и памяти, `--sort=-%cpu` сортирует по убыванию CPU. `| head -n 8` ограничивает вывод. **Ожидается:** реальные показатели; эти команды ничего не освобождают и не завершают.

В Linux высокая нагрузка не доказывает только нехватку CPU, а большой файловый кеш не равен утечке памяти. Для вывода нужны повторные наблюдения и события журнала. Диск в упражнении не заполняется, память искусственно не расходуется.

Прочитайте ограниченную выборку журнала:

```bash
sudo journalctl --boot=0 --priority=warning --lines=20 --no-pager
sudo journalctl --dmesg --boot=0 --lines=20 --no-pager
```

`--boot=0` выбирает текущую загрузку, `--priority=warning` — уровни warning и более важные, `--lines=20` — ограниченное число записей. `--dmesg` выбирает сообщения ядра. **Ожидается:** доступные записи или сообщение об их отсутствии. По двадцати строкам нельзя утверждать, что других ошибок не было.

Не выгружайте чужие журналы целиком в отчёт. Далее будем сохранять только сообщения собственной службы.

## Часть 2. Учебные неисправности и восстановление

### 5. Подготовьте имена и отдельные каталоги

```bash
LAB_UID="$(id -u)"
LAB_GID="$(id -g)"
LAB_USER="$(id -un)"
LAB_BASE="/var/tmp/astra-recovery-$LAB_UID"
LAB_RUN="/run/astra-recovery-$LAB_UID"
LAB_UNIT="astra-recovery-$LAB_UID.service"
LAB_DROPIN="/run/systemd/system/$LAB_UNIT.d"
LAB_PKG="astra-recovery-data-$LAB_UID"
LAB_DATA_DIR="/usr/share/astra-recovery-$LAB_UID"
LAB_DATA="$LAB_DATA_DIR/health.txt"
LAB_BUILD="$LAB_BASE/build"
LAB_DEB="$LAB_BASE/${LAB_PKG}_1.0_all.deb"
LAB_SINCE="$(date --iso-8601=seconds)"
```

`id -u` получает UID, `id -g` — основной GID, `id -un` — имя. `$(...)` подставляет результат. Переменные задают только собственные пути и имена. **Ожидается:** отсутствие вывода.

Проверьте отсутствие конфликтов:

```bash
LAB_READY=1
if [ "$LAB_UID" -eq 0 ] || [[ ! "$LAB_USER" =~ ^[a-zA-Z_][a-zA-Z0-9_-]*\$?$ ]]; then
    LAB_READY=0
    printf '%s\n' 'STOP: нужен обычный пользователь с простым локальным именем.'
fi
for LAB_PATH in "$LAB_BASE" "$LAB_RUN" "$LAB_DATA_DIR" "$LAB_DROPIN" "/run/systemd/system/$LAB_UNIT"; do
    if sudo test -e "$LAB_PATH" || sudo test -L "$LAB_PATH"; then
        LAB_READY=0
        printf 'STOP: путь уже существует: %s\n' "$LAB_PATH"
    fi
done
if dpkg-query --show "$LAB_PKG" > /dev/null 2>&1; then
    LAB_READY=0
    printf '%s\n' 'STOP: такое имя пакета уже присутствует в базе.'
fi
LAB_LOAD="$(systemctl show --property=LoadState --value "$LAB_UNIT" 2>/dev/null || true)"
if [ "$LAB_LOAD" != not-found ]; then
    LAB_READY=0
    printf '%s\n' 'STOP: имя службы занято или состояние не определено.'
fi
printf 'Готовность: %s\n' "$LAB_READY"
```

`-eq` сравнивает числа. Шаблон имени допускает простое локальное имя; сложные доменные варианты требуют отдельной адаптации. `test -e` находит объект, `test -L` — ссылку. `for` перебирает пути. `dpkg-query --show` обнаруживает пакет даже в некоторых остаточных состояниях; вывод скрыт через `> /dev/null 2>&1`.

`systemctl show --property=LoadState --value` получает только состояние загрузки unit; ожидается `not-found`. `|| true` позволяет обработать отсутствие unit как результат проверки. **Ожидается:** `Готовность: 1` и ни одного `STOP`. Иначе не продолжайте.

```bash
if [ "$LAB_READY" -eq 1 ]; then
    mkdir -m 700 -- "$LAB_BASE" &&
        mkdir -m 700 -- "$LAB_BASE/report" &&
        sudo mkdir -m 755 -- "$LAB_RUN"
else
    printf '%s\n' 'STOP: готовность не подтверждена.'
fi
systemctl --failed --no-pager > "$LAB_BASE/report/failed-before.txt"
```

`mkdir -m 700` создаёт личные каталоги. Каталог `/run` создаёт root с правами `755`: обычный пользователь сможет читать учебные настройки, но не менять их. `&&` выполняет зависимый шаг только при успехе предыдущего. `>` сохраняет исходный список failed.

**Ожидается:** отсутствие ошибок. При ошибке создания остановитесь. Пустой список failed содержит служебную строку systemctl, а не обязательно файл нулевой длины.

### 6. Соберите собственный пакет данных

```bash
mkdir -p -- "$LAB_BUILD/DEBIAN" "$LAB_BUILD$LAB_DATA_DIR"
printf 'healthy\n' > "$LAB_BUILD$LAB_DATA"
cat > "$LAB_BUILD/DEBIAN/control" <<EOF
Package: $LAB_PKG
Version: 1.0
Section: misc
Priority: optional
Architecture: all
Maintainer: Astra Training <training@example.invalid>
Description: Text data for an isolated recovery exercise
EOF
( cd "$LAB_BUILD" && md5sum "${LAB_DATA#/}" > DEBIAN/md5sums )
find "$LAB_BUILD" -type d -exec chmod 755 {} +
find "$LAB_BUILD" -type f -exec chmod 644 {} +
dpkg-deb --root-owner-group --build "$LAB_BUILD" "$LAB_DEB"
```

`mkdir -p` создаёт дерево с родителями. При склеивании `"$LAB_BUILD$LAB_DATA"` абсолютный путь файла становится частью дерева сборки, а не записью в настоящий `/usr/share`.

`cat ... <<EOF` записывает описание до отдельной строки `EOF`; без кавычек у ограничителя Bash подставляет имя пакета. `Architecture: all` подходит данным без машинного кода. Пакет не содержит зависимостей, служебных install/remove-сценариев и системных конфигураций.

`( cd ... )` меняет каталог только в подоболочке. `${LAB_DATA#/}` удаляет первый `/`, чтобы в `md5sums` был относительный путь. `md5sum` создаёт ожидаемую сумму для `dpkg --verify`; MD5 здесь служит сравнением содержимого с пакетной базой, а не доказательством происхождения пакета.

`find -type d/-type f` выбирает каталоги/обычные файлы; `-exec ... {} +` передаёт найденные пути команде `chmod`. `755` позволяет читать каталоги, `644` — файлы. `dpkg-deb --build` собирает `.deb`, `--root-owner-group` записывает в архив владельца root:root без сборки от root.

**Ожидается:** сообщение о создании пакета `astra-recovery-data-1000` версии `1.0`.

Проверьте архив перед установкой:

```bash
dpkg-deb --field "$LAB_DEB" Package Version Architecture
dpkg-deb --contents "$LAB_DEB"
dpkg-deb --control "$LAB_DEB" "$LAB_BASE/control-inspect"
find "$LAB_BASE/control-inspect" -maxdepth 1 -type f -printf '%f\n'
sha256sum "$LAB_DEB" > "$LAB_BASE/report/package.sha256"
sha256sum --check "$LAB_BASE/report/package.sha256"
```

`--field` читает поля, `--contents` показывает дерево, `--control` извлекает метаданные для осмотра. `find -maxdepth 1` ограничивает глубину; `-printf '%f\n'` выводит имена. `sha256sum --check` сверяет сумму.

**Ожидается:** свой пакет, версия `1.0`, `all`; только собственный текстовый файл под `/usr/share/astra-recovery-UID` и содержащие его каталоги. В метаданных — `control` и `md5sums`, без `postinst`, `prerm` и подобных сценариев. Сумма заканчивается `OK`.

### 7. Установите только свой пакет

```bash
if [ "$(dpkg-deb --field "$LAB_DEB" Package)" = "$LAB_PKG" ] &&
    [ "$(dpkg-deb --field "$LAB_DEB" Version)" = 1.0 ] &&
    sha256sum --check "$LAB_BASE/report/package.sha256"; then
    sudo dpkg --install "$LAB_DEB"
else
    printf '%s\n' 'STOP: имя, версия или сумма пакета не совпадают.'
fi
```

`dpkg --install` устанавливает именно указанный архив, не выполняя общий поиск обновлений. У нашего пакета нет дополнительных зависимостей. Устанавливать случайные чужие `.deb` по этой схеме нельзя: они могут содержать административные сценарии.

**Ожидается:** выбор нового учебного пакета, распаковка и настройка версии `1.0` без ошибок. Если пакетный менеджер занят, дождитесь текущей операции; не удаляйте файлы блокировок.

```bash
dpkg-query --show --showformat='${Package} ${Version} ${Status}\n' "$LAB_PKG"
dpkg-query --search "$LAB_DATA"
stat -c '%U %G %a %n' -- "$LAB_DATA"
cat "$LAB_DATA"
sha256sum "$LAB_DATA" > "$LAB_BASE/report/data-baseline.sha256"
sudo dpkg --verify "$LAB_PKG"
```

`--showformat` задаёт поля пакетной базы; одинарные кавычки сохраняют `${Package}` и другие подстановки для dpkg-query. `--search` находит владельца пути. `stat -c` показывает владельца `%U`, группу `%G`, права `%a`, имя `%n`.

**Ожидается:** `install ok installed`, собственное имя пакета перед путём, `root root 644`, содержимое `healthy`. У `dpkg --verify` в исходно исправном состоянии вывода нет. Это отдельная проверка от состояния «пакет установлен».

### 8. Создайте учебную проверку и её настройки

```bash
printf 'expected=healthy\n' > "$LAB_BASE/settings.conf"
cat > "$LAB_BASE/check-component.sh" <<'EOF'
#!/bin/sh
set -u
PATH=/usr/bin:/bin
export PATH
uid_target="$1"
case "$uid_target" in ''|*[!0-9]*) exit 2 ;; esac
settings="/run/astra-recovery-$uid_target/settings.conf"
data="/usr/share/astra-recovery-$uid_target/health.txt"
if [ ! -f "$settings" ] || [ ! -r "$settings" ]; then
    printf '%s\n' 'event=settings_unreadable' >&2
    exit 10
fi
expected="$(sed -n 's/^expected=//p' "$settings")" || exit 10
if [ "$expected" != healthy ]; then
    printf '%s\n' 'event=invalid_settings expected_value_must_be_healthy' >&2
    exit 11
fi
if [ ! -f "$data" ]; then
    printf '%s\n' 'event=data_missing' >&2
    exit 12
fi
if [ ! -r "$data" ]; then
    printf '%s\n' 'event=data_unreadable' >&2
    exit 13
fi
actual="$(cat "$data")" || exit 13
if [ "$actual" != "$expected" ]; then
    printf '%s\n' 'event=data_mismatch' >&2
    exit 14
fi
printf 'event=ready uid=%s data=%s\n' "$(id -u)" "$data"
exit 0
EOF
/bin/sh -n "$LAB_BASE/check-component.sh"
sudo install -o root -g root -m 644 -- "$LAB_BASE/check-component.sh" "$LAB_RUN/check-component.sh"
sudo install -o root -g root -m 644 -- "$LAB_BASE/settings.conf" "$LAB_RUN/settings.conf"
sudo cp -p -- "$LAB_RUN/settings.conf" "$LAB_RUN/settings.conf.good"
```

`<<'EOF'` сохраняет сценарий буквально: `$1` и остальные переменные подставятся при его запуске. `/bin/sh -n` проверяет синтаксис без выполнения. `install -o/-g/-m` задаёт владельца, группу и права. `cp -p` создаёт собственную исправную копию с сохранением обычных прав, владельца и времени.

**Ожидается:** отсутствие сообщений. В `/run` установлены root-файлы `644`; служба сможет их читать, но обычный пользователь не сможет переписать их напрямую.

Логика проверки:

- `#!/bin/sh` выбирает интерпретатор; `set -u` обнаруживает незаданные переменные только этого сценария. `PATH` задаёт поиск программ, `export` передаёт его дочерним командам.
- `$1` — UID стенда; `case` разрешает только цифры. Пути вычисляются внутри сценария, а не читаются из произвольного файла команд.
- `-f` проверяет обычный файл, `-r` — возможность чтения. `!` отрицает условие, `||` означает «или».
- `sed -n 's/^expected=//p'` извлекает значение настройки, не исполняя файл как Bash-код. `^` обозначает начало строки, `s` — замену, `p` — печать совпадения.
- `!=` сравнивает строки на неравенство, `>&2` направляет сообщение в поток ошибок, `exit` завершает сценарий с указанным кодом.
- Коды `10`–`14` придуманы для этого упражнения и объяснены самим сценарием. Они не являются универсальными кодами всех приложений Astra.

Если хотите открыть файл в редакторе, используйте `nano -w "$LAB_BASE/check-component.sh"`: `-w` отключает жёсткое разбиение длинных строк. Сохранение — Ctrl+O, затем Enter; выход — Ctrl+X. После изменения сначала повторите проверку синтаксиса и установку исправленного файла, а не редактируйте рабочие компоненты ОС.

### 10. Подготовьте проверки принадлежности и удобный просмотр

Функция ниже защищает от действий с ошибочно подставленной чужой службой или файлом:

```bash
lab_check_scope() {
    local owner fragment
    if [[ "$LAB_BASE" != "/var/tmp/astra-recovery-$(id -u)" ||
          "$LAB_UNIT" != "astra-recovery-$(id -u).service" ||
          "$LAB_RUN" != "/run/astra-recovery-$(id -u)" ||
          "$LAB_DROPIN" != "/run/systemd/system/$LAB_UNIT.d" ||
          "$LAB_PKG" != "astra-recovery-data-$(id -u)" ||
          "$LAB_DATA_DIR" != "/usr/share/astra-recovery-$(id -u)" ||
          "$LAB_DATA" != "$LAB_DATA_DIR/health.txt" ||
          "$LAB_DEB" != "$LAB_BASE/${LAB_PKG}_1.0_all.deb" ]]; then
        printf '%s\n' 'STOP: неожиданные имена объектов.'
        return 1
    fi
    fragment="$(systemctl show --property=FragmentPath --value "$LAB_UNIT")" || return 1
    owner="$(dpkg-query --search "$LAB_DATA")" || return 1
    if [[ "$fragment" = "/run/systemd/system/$LAB_UNIT" && "$owner" = "$LAB_PKG: $LAB_DATA" ]]; then
        return 0
    fi
    printf '%s\n' 'STOP: служба или пакет не совпадают с учебным стендом.'
    return 1
}
lab_check_scope
```

`local` ограничивает переменные функцией. `--value` выводит только значение без имени свойства. Сравнение `=` требует точного совпадения, `!=` обнаруживает другое значение. `return 1` завершает функцию с ошибкой, но не закрывает SSH.

**Ожидается:** отсутствие сообщений. Принадлежность пути берётся из пакетной базы: она сохраняется даже после удаления самого файла, пока пакет установлен.

Определите просмотр и ожидаемый неудачный запуск:

```bash
lab_status() {
    systemctl show "$LAB_UNIT" --property=ActiveState --property=SubState --property=Result --property=ExecMainStatus
    sudo journalctl --unit="$LAB_UNIT" --lines=10 --no-pager --output=short-iso
}
lab_expect_failure() {
    lab_check_scope || return 1
    if sudo systemctl restart "$LAB_UNIT"; then
        printf '%s\n' 'STOP: служба неожиданно запустилась; проверьте условия опыта.'
        return 1
    fi
    printf '%s\n' 'Запуск вернул ошибку; проверяем её причину.'
    lab_status
}
```

**Ожидается:** отсутствие вывода — функции только определены. `restart` заставляет нашу `oneshot`-проверку выполниться заново, даже если она уже `active/exited`. Повторный `start` исправной active-службы мог бы ничего не сделать.

Ненулевой код `systemctl` сам по себе не доказывает именно задуманную причину: её нужно подтвердить событием и `ExecMainStatus`. Сообщения сценария в stderr не обязательно получают важность `err` в journal, поэтому основной фильтр здесь — `--unit`, без ограничения важности.

### 12. Опыт 2: служба не может прочитать файл

```bash
lab_check_scope &&
    sudo chmod 600 -- "$LAB_DATA" &&
    lab_expect_failure
```

`chmod 600` оставляет чтение и запись только владельцу root. Наша служба работает обычным пользователем, поэтому чтение запрещено. **Ожидается:** `ExecMainStatus=13`, `event=data_unreadable`.

Проверьте владельца, весь путь и фактического пользователя:

```bash
stat -c '%U %G %a %n' -- "$LAB_DATA"
namei -l "$LAB_DATA"
systemctl show "$LAB_UNIT" --property=User --property=Group
if sudo -u "$LAB_USER" test -r "$LAB_DATA"; then
    printf '%s\n' 'Чтение разрешено: проверьте, почему условие опыта отличается.'
else
    printf '%s\n' 'Пользователь службы не может читать файл.'
fi
sudo dpkg --verify "$LAB_PKG"
```

`namei -l` разбирает путь и показывает права его компонентов: для доступа к файлу нужна также возможность прохода по каталогам. `sudo -u` выполняет только проверку `test -r` от выбранного пользователя. **Ожидается:** root:root, `600`, обычный пользователь службы, отказ чтения.

У `dpkg --verify` в этом опыте может не быть вывода: содержимое не менялось. В рассматриваемой версии dpkg это прежде всего проверка сумм, а не полноценная сверка режима `600` против исходного `644`. Пустой вывод не отменяет уже обнаруженную проблему прав.

Верните **известные правильные права одного файла**, не применяя рекурсивный chmod:

```bash
lab_check_scope &&
    sudo chmod 644 -- "$LAB_DATA" &&
    sudo systemctl restart "$LAB_UNIT" &&
    lab_status
```

**Ожидается:** код `0`, `event=ready`. `644` известно из созданного нами пакета. Для рабочих компонентов нельзя подбирать права наугад или использовать `777`; ограничения мандатного контроля Astra не сводятся к обычным битам доступа.

```bash
systemctl --failed --no-pager
```

**Ожидается:** root:root и `644`, отсутствие новых проблем пакетной базы, нашей службы нет среди failed. Другие ошибки, существовавшие до работы или возникшие независимо, нельзя автоматически приписывать упражнению.

### 17. Как применять этот порядок к настоящим компонентам Astra

Чтение сведений о реальной системе можно продолжить без восстановления её пакетов:

```bash
dpkg-query --show --showformat='${Package} ${Version} ${Status}\n' bash systemd coreutils
apt-cache policy bash systemd coreutils
systemctl status ssh.service --no-pager --lines=8
systemctl status systemd-journald.service --no-pager --lines=8
```

**Ожидается:** фактически установленные версии, доступные кандидаты и состояние выбранных служб. `status` может вернуть ненулевой код при неактивном или отсутствующем unit; это диагностика. Имя службы SSH зависит от установки, поэтому сначала учитывайте сообщение о наличии unit.

Для реального компонента порядок решения таков:

1. Найти точный путь, владельца пакета и версию, а не угадывать пакет по похожему имени.
2. Отделить изменённые настройки от повреждённых штатных файлов и проверить права от пользователя службы.
3. Сохранить текущую конфигурацию и выяснить наличие исправной копии, совместимого пакета своего выпуска и доступного способа восстановления.
4. Оценить влияние на соединение, зависимости и компоненты защиты; только затем выбирать конкретное изменение.

Переустановка рабочего пакета может запускать его обработчики и затронуть службы. Она не должна выполняться массово, а сохранение conffiles означает, что неправильная настройка может остаться. Нельзя удалять lock-файлы dpkg, самовольно править пакетную базу или отключать защиту ради устранения сообщения.

Если обычные права выглядят правильными, но доступ запрещён, это повод исследовать журналы и политики Astra, а не расширять права всему дереву. Обновление или восстановление компонентов защиты выполняется по процедурам конкретного выпуска ОС и предприятия.

### 18. Сохраните результаты и скриншоты

```bash
sudo journalctl --unit="$LAB_UNIT" --since="$LAB_SINCE" --no-pager --output=short-iso > "$LAB_BASE/report/service-history.txt"
systemctl show "$LAB_UNIT" --property=FragmentPath --property=User --property=Result --property=ExecMainStatus > "$LAB_BASE/report/final-state.txt"
dpkg-query --show --showformat='${Package} ${Version} ${Status}\n' "$LAB_PKG" > "$LAB_BASE/report/package-state.txt"
sha256sum "$LAB_BASE/report/service-history.txt" "$LAB_BASE/report/final-state.txt" \
    "$LAB_BASE/report/package-state.txt" "$LAB_BASE/report/verify-damaged.txt" \
    > "$LAB_BASE/report/report.sha256"
sha256sum --check "$LAB_BASE/report/report.sha256"
```

`>` сохраняет собственные результаты; `sha256sum --check` сверяет четыре файла отчёта. **Ожидается:** четыре `OK`. История содержит и намеренные ошибки, и исправные запуски. Это нормально: устранение причины не удаляет прошлые записи.

| Скриншот | Раздел | Что показать |
| --- | --- | --- |
| Исходное состояние | 7–9 | Свой пакет, права `644`, успешный запуск, `event=ready` |
| Неверная настройка | 11 | Код `11`, сообщение и отличие конфигурации |
| Исправление настройки | 11 | Новый код `0` после возврата исправного файла |
| Отказ по правам | 12 | Владелец root, `600`, пользователь службы и код `13` |
| Повреждение пакета | 13 | `install ok installed`, расхождение проверки и последующая сумма `OK` после установки |
| Пропавший файл | 14 | `data_missing`, известный владелец пакета и успешное восстановление |
| Ошибка запуска | 15 | Drop-in, `missing-program`, код `203/EXEC` |
| Итог | 16–18 | Исправные настройки, права, сумма и успешная служба |

Показывайте команды и настоящий вывод. До восстановления каждого случая снимите его ошибочное состояние, затем снимите исправное. Для отчёта не нужно публиковать чужие журналы, ключи, реальные конфигурации безопасности или полные дампы процессов.

### 19. Если SSH оборвался

Подключитесь к той же машине под тем же обычным пользователем. Повторите **только блок переменных раздела 5** и определения функций раздела 10. Не повторяйте создание каталогов, сборку и установку поверх существующего стенда.

```bash
systemctl status "$LAB_UNIT" --no-pager --lines=10
sudo journalctl --unit="$LAB_UNIT" --lines=15 --no-pager
dpkg-query --show "$LAB_PKG"
```

**Ожидается:** сохранившийся текущий опыт. Код и событие подскажут, какой шаг восстановления нужен. Для чтения старых событий не используйте новое время `LAB_SINCE` как нижнюю границу: оно было заново получено при подключении.

Если сервер перезагрузился, `/run` и временный unit исчезают, но установленный пакет остаётся. Не ищите его удалением всех неизвестных пакетов. Проверьте точное имя, источник собственного `.deb`, файлы и пакетную базу; затем решайте, восстановить временную службу или удалить только свой учебный пакет. Восстанавливать всё дерево `/run` из старой копии не требуется.

Если подготовка остановилась на середине, часть объектов может отсутствовать. Удаляйте только те собственные объекты, которые уже подтверждены, а не выполняйте всю очистку без проверки.

### 20. Завершите работу и удалите учебные объекты

Сначала сохраните отчёт: после удаления личного каталога его файлы исчезнут. Перед очисткой служба должна быть восстановлена, а ошибочный drop-in из раздела 15 — удалён.

#### 20.1. Остановите только свою службу и удалите только свой пакет

```bash
lab_check_scope &&
    sudo systemctl stop "$LAB_UNIT" &&
    sudo dpkg --remove "$LAB_PKG"
```

`stop` останавливает выбранный unit; `dpkg --remove` удаляет только именованный учебный пакет без принудительных флагов. **Ожидается:** удаление `astra-recovery-data-UID` и его текстового файла. Не используйте общее удаление пакетов по маске и `autoremove` вместо этого шага.

#### 20.2. Удалите временное определение и собственные файлы root

```bash
if [ "$LAB_UNIT" = "astra-recovery-$(id -u).service" ] &&
    [ "$LAB_RUN" = "/run/astra-recovery-$(id -u)" ] &&
    sudo cmp -s -- "$LAB_BASE/$LAB_UNIT" "/run/systemd/system/$LAB_UNIT"; then
    sudo rm -- "/run/systemd/system/$LAB_UNIT" &&
        sudo systemctl daemon-reload &&
        sudo rm -- "$LAB_RUN/check-component.sh" "$LAB_RUN/settings.conf" "$LAB_RUN/settings.conf.good" &&
        sudo rmdir -- "$LAB_RUN"
else
    printf '%s\n' 'STOP: проверьте имена и содержимое unit.'
fi
```

`cmp -s` молча сравнивает установленное определение с нашим исходным файлом. Удаляются только перечисленные пути; `rmdir` откажется удалять непустой каталог. **Ожидается:** отсутствие ошибок. Не добавляйте рекурсивное удаление с правами root, если обнаружилось неизвестное содержимое.

После успешного восстановления и остановки отдельный `reset-failed` обычно не нужен. Если systemd ещё помнит именно нашу прошлую неудачу, его можно выполнить только для `$LAB_UNIT`; сброс ошибки всех служб не относится к очистке этого стенда.

#### 20.3. Проверьте состояние и удалите личный каталог

```bash
sudo dpkg --audit
systemctl --failed --no-pager
if [ -e "$LAB_DATA" ]; then
    printf '%s\n' 'STOP: учебный файл ещё существует; проверьте удаление пакета.'
else
    printf '%s\n' 'Учебный файл пакета удалён.'
fi
```

**Ожидается:** отсутствие новых ошибок пакетной базы, отсутствие нашей failed-службы и подтверждение удаления данных. Чужие службы и их журналы не изменяются.

```bash
if [ "$LAB_BASE" = "/var/tmp/astra-recovery-$(id -u)" ] &&
    [ ! -e "/run/systemd/system/$LAB_UNIT" ] && [ ! -d "$LAB_RUN" ] && [ ! -e "$LAB_DATA" ]; then
    cd "$HOME" && rm -rI -- "$LAB_BASE"
else
    printf '%s\n' 'STOP: сначала завершите удаление учебных объектов.'
fi
```

`!` отрицает проверку; `cd "$HOME"` выводит оболочку из удаляемого дерева. `rm -r` удаляет дерево рекурсивно, заглавная `-I` запрашивает подтверждение. **Ожидается:** вопрос об удалении только вашего `/var/tmp/astra-recovery-UID`; проверьте путь и подтвердите. Здесь `sudo` не нужен.

### 21. Частые вопросы

**Можно ли просто копировать блоки?** Да, последовательно в Bash удалённой Astra, проверяя результаты. При первом прохождении начинайте с раздела 3, а не с искусственных неисправностей. Ошибки ожидаются только там, где они специально описаны.

**Служба failed — сервер сломан?** Нет. Это состояние конкретного unit. Во время учебных отказов общее состояние systemd может стать `degraded`; после восстановления собственного unit проверьте, какие ошибки остались и были ли они раньше.

**Почему проверяем и пакет, и службу?** Пакет может оставаться установленным при повреждённом файле. И наоборот, файлы могут быть целыми, а служба не работает из-за прав, настроек или пути запуска.

**Почему не запускаем всё от root?** Это скрыло бы часть ошибок доступа. Учебная служба намеренно работает обычным пользователем, а административные операции выполняются отдельно и только над её объектами.

**Почему не исправляем SSH или компонент защиты на практике?** Их повреждение может лишить удалённого доступа и нарушить работу сервера. Здесь отрабатывается переносимый порядок диагностики на собственном компоненте; рабочее восстановление требует сведений о конкретной причине и выпуске ОС.

**Нужно ли удалять журнал ошибок?** Нет. Записи подтверждают, что происходило и каким было исправление. `reset-failed` меняет состояние systemd, но не заменяет восстановление и не стирает историю.
