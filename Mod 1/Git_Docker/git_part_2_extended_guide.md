# Git и GitHub: расширенная инструкция

Этот файл — простая расширенная инструкция по работе с Git и GitHub. Она подходит для человека, который только начинает работать с кодом, файлами проекта и репозиториями.

В первой части обычно достаточно научиться устанавливать Git, создавать аккаунт GitHub, клонировать репозиторий, делать `git status`, `git add`, `git commit`, `git push` и `git pull`. В этой части добавляется полный базовый сценарий: как создать локальный Git-репозиторий через `git init`, как связать его с GitHub, как работать с ветками через `git branch`, как переключаться между ветками и как объединять изменения через `git merge`.

---

## 1. Что такое Git

**Git** — это распределённая система контроля версий.

Система контроля версий нужна для того, чтобы сохранять историю изменений в проекте. Проектом может быть программа, сайт, учебный репозиторий, набор скриптов, документация, Markdown-файлы или любой набор файлов.

Когда человек работает без Git, он часто сохраняет файлы так:

```text
project_final.docx
project_final_2.docx
project_final_new.docx
project_final_new_really_final.docx
```

Такой способ быстро становится неудобным. Непонятно, какая версия актуальная. Трудно понять, что именно изменилось. Сложно вернуться к предыдущему состоянию. Ещё сложнее работать вместе с другими людьми.

Git решает эту проблему иначе. Он сохраняет не случайные копии файлов, а историю изменений. Каждое важное состояние проекта можно сохранить как **commit**. Коммит можно понимать как контрольную точку. В коммите Git запоминает, какие файлы изменились и какое сообщение оставил пользователь.

Например:

```text
commit 1: добавлен README
commit 2: добавлен файл main.py
commit 3: исправлена ошибка в расчёте
commit 4: обновлена инструкция по запуску
```

Главная особенность Git — он **распределённый**. Это означает, что полная история проекта хранится не только на одном центральном сервере. Каждый разработчик, который клонировал репозиторий, получает локальную копию проекта вместе с историей коммитов.

Поэтому с Git можно работать локально на компьютере: создавать коммиты, смотреть историю, создавать ветки, сравнивать изменения. Интернет нужен не для каждой команды, а только тогда, когда нужно обменяться изменениями с удалённым репозиторием, например на GitHub.

## 2. Что такое GitHub и чем он отличается от Git

**Git** — это инструмент контроля версий. Он установлен на компьютере и работает через командную строку или графический интерфейс.

**GitHub** — это облачная платформа для хранения Git-репозиториев и совместной работы с кодом. GitHub использует Git, но не является самим Git.

Проще говоря:

```text
Git    = инструмент, который следит за версиями файлов.
GitHub = облачное место, где можно хранить Git-репозитории.
```

Локальный репозиторий находится на компьютере. Удалённый репозиторий находится на GitHub. Обычно они связаны между собой.

Типовая логика такая:

```text
Компьютер пользователя           GitHub
локальный репозиторий   <---->   удалённый репозиторий
```

Когда вы делаете `git commit`, изменение сохраняется локально. Оно ещё не отправлено на GitHub.

Когда вы делаете `git push`, локальные коммиты отправляются в удалённый репозиторий GitHub.

Когда вы делаете `git pull`, изменения из GitHub загружаются на компьютер.

## 3. Основные термины простыми словами

### Repository / репозиторий

**Репозиторий** — это папка проекта, за которой следит Git. Внутри репозитория находятся файлы проекта и скрытая папка `.git`, где Git хранит служебную информацию и историю.

### Local repository / локальный репозиторий

**Локальный репозиторий** — репозиторий на вашем компьютере.

### Remote repository / удалённый репозиторий

**Удалённый репозиторий** — репозиторий на GitHub или другой платформе.

### Working directory / рабочая папка

**Рабочая папка** — обычная папка с файлами, которые вы редактируете.

### Staging area / индекс

**Staging area** — промежуточная область перед коммитом. Команда `git add` кладёт изменения в эту область.

### Commit / коммит

**Коммит** — сохранённая контрольная точка проекта.

### Branch / ветка

**Ветка** — отдельная линия работы. В ветке можно делать изменения, не ломая основную ветку.

### Merge / слияние

**Merge** — объединение изменений из одной ветки в другую.

### Origin

`origin` — стандартное имя удалённого репозитория. Обычно так называют GitHub-репозиторий, с которым связан локальный проект.

### Main

`main` — основная ветка проекта. Сейчас на GitHub основная ветка чаще всего называется `main`.

## 6. Personal Access Token: токен вместо пароля

При работе с GitHub через HTTPS обычный пароль аккаунта не используется как пароль для Git-операций. Для командной строки применяется **personal access token**.

Токен можно понимать как специальный пароль для доступа к GitHub из Git. Его нужно хранить аккуратно. Нельзя отправлять токен в чат, публиковать в репозитории, вставлять в README или показывать на скриншотах.

Официальная страница GitHub по токенам:

```text
https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens
```

Упрощённый путь в интерфейсе GitHub:

```text
GitHub → Settings → Developer settings → Personal access tokens
```

Лучше использовать **fine-grained token**, если он подходит для вашей задачи. Для учебного репозитория обычно достаточно дать токену доступ только к конкретному репозиторию.

Минимальная логика такая:

1. Зайти в настройки GitHub.
2. Открыть **Developer settings**.
3. Открыть **Personal access tokens**.
4. Создать новый токен.
5. Выбрать срок действия.
6. Выбрать нужный репозиторий.
7. Выдать минимально необходимые права.
8. Скопировать токен сразу после создания.

Важно: GitHub покажет токен только один раз. Если вы его потеряли, проще удалить старый токен и создать новый.

Когда Git попросит пароль при `git push`, вставьте токен вместо пароля.

Пример:

```text
Username: YourUsername
Password: сюда вставляется token, а не пароль от GitHub
```

Токен не должен отображаться в командной строке. Это нормально: при вставке пароль может не показываться.

## 7. Настройка Git config

Перед первым коммитом нужно настроить имя и email. Эти данные будут записываться в коммиты.

Глобальная настройка для всех проектов на компьютере:

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "your.email@example.com"
```

Пример:

```bash
git config --global user.name "Ivan Ivanov"
git config --global user.email "ivan@example.com"
```

Проверить настройки можно так:

```bash
git config --global --list
```

Если нужно настроить имя и email только для одного конкретного проекта, нужно перейти в папку проекта и использовать `--local`:

```bash
git config --local user.name "Ваше Имя"
git config --local user.email "your.email@example.com"
```

Разница простая:

```text
--global = настройка для всех проектов пользователя.
--local  = настройка только для текущего репозитория.
```

Обычно новичку достаточно `--global`.

```bash
mkdir my-project

```

Команда `mkdir my-project` создаёт папку.

Команда `cd my-project` переходит внутрь этой папки.

На этом этапе это ещё не Git-репозиторий. Это просто папка.

## 9. `git init`: превращаем папку в Git-репозиторий

Чтобы Git начал отслеживать проект, нужно выполнить команду:

```bash
git init
```

После этой команды Git создаёт внутри проекта скрытую папку `.git`.

Именно в ней Git хранит историю, настройки репозитория, информацию о ветках и служебные данные.

Проверить, что репозиторий создан, можно командой:

```bash
git status
```

Если всё правильно, Git покажет состояние репозитория.

Примерный ответ может быть таким:

```text
On branch master
No commits yet
nothing to commit
```

Или таким:

```text
On branch main
No commits yet
nothing to commit
```

Название начальной ветки зависит от настроек Git.

## 10. Переименование основной ветки в `main`

Если после `git init` Git создал ветку `master`, можно переименовать её в `main`.

```bash
git branch -m master main
```

Если вы уже находитесь в ветке `master`, можно использовать короткий вариант:

```bash
git branch -M main
```

Команда `git branch -M main` означает: переименовать текущую ветку в `main` принудительно.

Проверить текущую ветку:

```bash
git branch
```

Звёздочка показывает ветку, в которой вы сейчас находитесь.

Пример:

```text
* main
```

## 12. `git status`: проверяем состояние репозитория

Команда `git status` показывает, что происходит в репозитории.

```bash
git status
```

Она помогает понять:

- какие файлы изменены;
- какие файлы новые;
- какие файлы уже подготовлены к коммиту;
- в какой ветке вы находитесь;
- есть ли изменения, которые нужно отправить на GitHub.

После создания `README.md` Git может показать:

```text
Untracked files:
  README.md
```

`Untracked files` означает, что Git видит новый файл, но пока не отслеживает его историю.

Это нормально. Новый файл сначала нужно добавить через `git add`.

---

## 13. `git add`: добавляем изменения в индекс

Команда `git add` подготавливает изменения к коммиту.

Добавить один файл:

```bash
git add README.md
```

Добавить несколько конкретных файлов:

```bash
git add filename1.txt filename2.md
```

Добавить все изменения в текущей папке:

```bash
git add .
```

`git add .` удобно использовать, когда нужно добавить все новые и изменённые файлы. Но новичку полезно сначала чаще делать `git status`, чтобы случайно не добавить лишний файл.

Проверим состояние:

```bash
git status
```

Теперь Git должен показать, что файл подготовлен к коммиту.

Пример:

```text
Changes to be committed:
  new file: README.md
```

## 14. `git commit`: сохраняем контрольную точку

Команда `git commit` создаёт сохранённое состояние проекта.

```bash
git commit -m "Добавлен README"
```

Флаг `-m` означает message, то есть сообщение коммита.

Сообщение должно кратко объяснять, что изменилось.

Хорошие примеры сообщений:

```bash
git commit -m "Добавлен README"
git commit -m "Исправлена ошибка в расчёте"
git commit -m "Обновлена инструкция по запуску"
```

Плохие примеры:

```bash
git commit -m "1"
git commit -m "fix"
git commit -m "changes"
```

Такие сообщения почти ничего не объясняют.

После коммита Git сохранит изменение в локальной истории. Но оно ещё не отправлено на GitHub.

---

## 15. `git log --oneline`: смотрим историю коммитов

Чтобы посмотреть историю, используйте:

```bash
git log --oneline
```

Пример:

```text
a1b2c3d Добавлен README
```

В начале строки находится короткий идентификатор коммита. После него — сообщение коммита.

Если коммитов несколько, история будет выглядеть так:

```text
f4e5d6c Обновлена инструкция
b2a1c9e Добавлен main.py
a1b2c3d Добавлен README
```

Самые новые коммиты обычно находятся сверху.

## 16. Создание репозитория на GitHub

Теперь нужно создать удалённый репозиторий на GitHub.

Откройте GitHub:

```text
https://github.com/
```

Дальше:

1. Нажмите **New repository**.
2. Укажите имя репозитория, например `my-project`.
3. Выберите тип репозитория:
   - **Public** — репозиторий виден всем;
   - **Private** — репозиторий виден только вам и тем, кому вы дали доступ.
4. Если вы уже создали локальный проект, лучше не добавлять README через GitHub.
5. Нажмите **Create repository**.

После создания GitHub покажет адрес репозитория.

Пример HTTPS-адреса:

```text
https://github.com/YourUsername/my-project.git
```

Скопируйте этот адрес.

## 17. Связь локального репозитория с GitHub

Локальный репозиторий уже есть на компьютере. Удалённый репозиторий уже создан на GitHub. Теперь их нужно связать.

Для этого используется команда `git remote add`.

```bash
git remote add origin https://github.com/YourUsername/my-project.git
```

Замените `YourUsername` и `my-project` на свои значения.

Пример:

```bash
git remote add origin https://github.com/ivanivanov/my-project.git
```

Здесь:

- `remote` означает удалённый репозиторий;
- `add` означает добавить;
- `origin` — имя удалённого репозитория;
- URL — адрес репозитория на GitHub.

Проверить связь можно так:

```bash
git remote -v
```

Пример результата:

```text
origin  https://github.com/ivanivanov/my-project.git (fetch)
origin  https://github.com/ivanivanov/my-project.git (push)
```

`fetch` означает получение данных с GitHub.

`push` означает отправку данных на GitHub.

## 18. `git push -u origin main`: первая отправка на GitHub

После первого коммита и привязки удалённого репозитория можно отправить проект на GitHub.

```bash
git push -u origin main
```

Здесь:

- `push` — отправить локальные коммиты в удалённый репозиторий;
- `origin` — имя удалённого репозитория;
- `main` — ветка, которую отправляем;
- `-u` — запомнить связь между локальной веткой `main` и веткой `main` на GitHub.

После этого в следующий раз можно будет писать короче:

```bash
git push
```

Если Git попросит логин и пароль, введите:

```text
Username: ваш GitHub username
Password: ваш personal access token
```

Пароль от GitHub-аккаунта здесь не используется. Нужен токен.

## 19. Полный сценарий: создать локальный проект и отправить на GitHub

Ниже полный сценарий от пустой папки до отправки на GitHub.

```bash
mkdir my-project
cd my-project

git init
git branch -M main

echo "# My Project" > README.md

git status
git add README.md
git commit -m "Добавлен README"

git remote add origin https://github.com/YourUsername/my-project.git
git remote -v

git push -u origin main
```

После этого проект должен появиться на GitHub.

Если вы обновите страницу репозитория в браузере, там будет файл `README.md`.

## 20. Обычный рабочий цикл после настройки

После первой настройки каждый рабочий день обычно выглядит так.

Сначала получить свежие изменения с GitHub:

```bash
git pull origin main
```

Потом изменить файлы.

Потом проверить состояние:

```bash
git status
```

Потом добавить изменения:

```bash
git add .
```

Или добавить конкретные файлы:

```bash
git add filename1.txt filename2.md
```

Потом создать коммит:

```bash
git commit -m "Описание изменений"
```

Потом отправить изменения на GitHub:

```bash
git push origin main
```

Короткая схема:

```text
pull → изменить файлы → status → add → commit → push
```

## 21. `git pull`: получение изменений из GitHub

Команда `git pull` получает изменения из удалённого репозитория и применяет их к вашей локальной ветке.

```bash
git pull origin main
```

Это особенно важно, если с репозиторием работает несколько человек.

Пример ситуации:

1. Вы начали работу утром.
2. Другой человек уже отправил изменения на GitHub.
3. У вас на компьютере старое состояние проекта.
4. Нужно сначала выполнить `git pull origin main`.
5. После этого можно спокойно продолжать работу.

Хорошая привычка:

```bash
git pull origin main
```

перед началом работы и перед отправкой своих изменений.

## 22. `git clone`: скачать уже существующий репозиторий

Если репозиторий уже есть на GitHub, его не нужно создавать через `git init`. Его можно скачать через `git clone`.

```bash
git clone https://github.com/YourUsername/my-project.git
```

После выполнения команды появится папка `my-project`.

Перейдите в неё:

```bash
cd my-project
```

Проверьте состояние:

```bash
git status
```

В этом случае Git уже знает, с каким удалённым репозиторием связан проект. Обычно `origin` уже настроен автоматически.

Проверить можно так:

```bash
git remote -v
```

## 23. Когда использовать `git init`, а когда `git clone`

Используйте `git init`, если проект уже есть на вашем компьютере или вы создаёте новый проект с нуля.

Пример:

```text
У вас есть папка my-project на компьютере.
Вы хотите начать отслеживать её через Git.
Тогда используйте git init.
```

Используйте `git clone`, если репозиторий уже создан на GitHub и вы хотите скачать его на компьютер.

Пример:

```text
На GitHub уже есть репозиторий.
Вы хотите получить его локальную копию.
Тогда используйте git clone.
```

Главное правило:

```text
git init  = создать Git-репозиторий из локальной папки.
git clone = скачать уже существующий Git-репозиторий.
```

---

## 24. Что такое ветка в Git

Ветка — это отдельная линия работы внутри репозитория.

Представьте, что основная ветка `main` содержит стабильную версию проекта. Если нужно попробовать новую функцию, исправить ошибку или изменить документацию, можно создать отдельную ветку.

В этой ветке можно работать спокойно, не изменяя основную ветку `main`.

Пример:

```text
main              стабильная версия проекта
feature-readme    ветка для изменения README
fix-error         ветка для исправления ошибки
```

Ветки полезны, потому что позволяют разделять работу.

Пример логики:

1. Основная версия проекта лежит в `main`.
2. Для новой задачи создаётся ветка `feature-readme`.
3. В этой ветке редактируются файлы.
4. Изменения коммитятся.
5. После проверки ветка объединяется с `main` через `git merge`.

---

## 25. `git branch`: просмотр веток

Посмотреть список веток можно командой:

```bash
git branch
```

Пример:

```text
* main
  feature-readme
```

Звёздочка показывает текущую ветку.

В этом примере пользователь находится в ветке `main`.

Если звёздочка стоит рядом с `feature-readme`, значит пользователь сейчас работает в этой ветке.

```text
  main
* feature-readme
```

Перед выполнением важных команд всегда полезно проверять текущую ветку:

```bash
git branch
```

Это помогает не сделать изменения не в той ветке.

---

## 26. Создание новой ветки

Создать новую ветку можно так:

```bash
git branch feature-readme
```

Эта команда создаёт ветку, но не переключает вас в неё.

Чтобы переключиться:

```bash
git checkout feature-readme
```

Есть короткий способ: создать ветку и сразу перейти в неё.

```bash
git checkout -b feature-readme
```

Команда означает:

```text
создать новую ветку feature-readme и сразу начать работать в ней.
```

Проверим:

```bash
git branch
```

Пример:

```text
  main
* feature-readme
```

Теперь все новые коммиты будут создаваться в ветке `feature-readme`.

---

## 27. Работа в отдельной ветке

Допустим, мы находимся в ветке `feature-readme`.

Проверим:

```bash
git branch
```

Изменим файл `README.md`.

Потом проверим состояние:

```bash
git status
```

Добавим файл:

```bash
git add README.md
```

Создадим коммит:

```bash
git commit -m "Обновлено описание проекта"
```

Теперь изменение сохранено в ветке `feature-readme`.

Основная ветка `main` пока не изменилась.

Это и есть смысл ветки: можно подготовить изменение отдельно, а потом объединить его с основной веткой.

---

## 28. Переключение между ветками

Переключиться на ветку `main`:

```bash
git checkout main
```

Переключиться обратно на ветку `feature-readme`:

```bash
git checkout feature-readme
```

Перед переключением желательно проверить статус:

```bash
git status
```

Если есть незакоммиченные изменения, Git может не дать переключиться или перенести изменения в другую ветку. Для новичка безопаснее сначала завершить работу:

```bash
git add .
git commit -m "Описание изменений"
```

И только потом переключаться.

---

## 29. `git merge`: объединение веток

`git merge` объединяет изменения из одной ветки в другую.

Важно понимать направление слияния.

Если нужно перенести изменения из `feature-readme` в `main`, нужно сначала перейти в `main`.

```bash
git checkout main
```

Затем выполнить merge:

```bash
git merge feature-readme
```

Логика такая:

```text
Я нахожусь в main.
Я забираю изменения из feature-readme в main.
```

После успешного merge изменения из ветки `feature-readme` появятся в `main`.

Потом можно отправить обновлённую `main` на GitHub:

```bash
git push origin main
```

## 30. Полный сценарий работы с веткой и merge

Допустим, нужно изменить README, но не сразу в основной ветке.

```bash
# 1. Убедиться, что мы в main
git checkout main

# 2. Получить свежие изменения с GitHub
git pull origin main

# 3. Создать новую ветку и перейти в неё
git checkout -b feature-readme

# 4. Изменить README.md вручную в редакторе

# 5. Проверить изменения
git status

# 6. Добавить изменения
git add README.md

# 7. Создать коммит
git commit -m "Обновлено описание проекта"

# 8. Вернуться в main
git checkout main

# 9. Объединить изменения из feature-readme в main
git merge feature-readme

# 10. Отправить main на GitHub
git push origin main
```

После этого изменения попадут в основную ветку и будут видны на GitHub.

## 31. Что делать после merge

После успешного merge можно продолжать работу в `main` или создать новую ветку для следующей задачи.

Проверить состояние:

```bash
git status
```

Посмотреть историю:

```bash
git log --oneline
```

Если ветка `feature-readme` больше не нужна, её можно удалить локально:

```bash
git branch -d feature-readme
```

Это удаляет только локальную ветку.

Для новичка удаление ветки не обязательно. Можно оставить её, пока вы не уверены.

## 32. Конфликты при merge

Иногда Git не может автоматически объединить изменения.

Это происходит, если в двух ветках изменён один и тот же участок файла.

Например:

- в ветке `main` изменили строку в `README.md`;
- в ветке `feature-readme` изменили ту же строку;
- Git не понимает, какую версию оставить.

Тогда возникает конфликт.

Git может показать сообщение примерно такого вида:

```text
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

Откройте конфликтующий файл. Внутри будут специальные метки:

```text
<<<<<<< HEAD
Текст из текущей ветки
=======
Текст из ветки, которую мы вливаем
>>>>>>> feature-readme
```

Нужно вручную выбрать правильный вариант и удалить служебные метки.

После исправления:

```bash
git add README.md
git commit -m "Исправлен конфликт merge"
```

Потом можно отправить результат:

```bash
git push origin main
```

Главное правило: конфликт — это не поломка Git. Это ситуация, где Git просит человека выбрать правильный вариант.

## 33. Как не запутаться в ветках

Перед началом работы проверяйте ветку:

```bash
git branch
```

Перед началом работы получайте свежие изменения:

```bash
git pull origin main
```

Для каждой отдельной задачи создавайте отдельную ветку:

```bash
git checkout -b feature-task-name
```

Делайте небольшие коммиты с понятными сообщениями:

```bash
git commit -m "Добавлена инструкция по установке"
```

После завершения задачи объединяйте ветку в `main`:

```bash
git checkout main
git merge feature-task-name
git push origin main
```

Если вы не уверены, где находитесь, выполните:

```bash
git status
git branch
git remote -v
```

Эти три команды часто помогают понять состояние проекта.

## 34. Частые ошибки новичков

### Ошибка 1. Сделать `commit`, но забыть `push`

Коммит сохраняется локально. GitHub не увидит его, пока не выполнен `push`.

Проверяйте:

```bash
git status
```

Если Git пишет, что ветка опережает удалённую, нужно выполнить:

```bash
git push origin main
```

### Ошибка 2. Сделать изменения не в той ветке

Перед работой проверяйте:

```bash
git branch
```

### Ошибка 3. Забыть `git pull`

Если несколько человек работают с одним репозиторием, перед началом работы полезно выполнить:

```bash
git pull origin main
```

### Ошибка 4. Пытаться ввести пароль GitHub вместо токена

Для HTTPS-доступа GitHub использует токен вместо пароля.

Если Git просит пароль, вставляйте personal access token.

### Ошибка 5. Добавить лишние файлы через `git add .`

`git add .` добавляет все изменения. Перед этим лучше выполнить:

```bash
git status
```

Если среди файлов есть лишние, не добавляйте всё сразу. Добавьте только нужные файлы:

```bash
git add README.md main.py
```

## 37. Итоговая логика

Git нужен для сохранения истории изменений. GitHub нужен для хранения репозитория в облаке и совместной работы.

Локальный репозиторий создаётся через:

```bash
git init
```

Связь с GitHub создаётся через:

```bash
git remote add origin https://github.com/YourUsername/projectName.git
```

Обычный цикл работы строится так:

```text
pull → изменить файлы → status → add → commit → push
```

Ветки нужны, чтобы работать над задачами отдельно от основной ветки.

Слияние нужно, чтобы перенести готовые изменения из рабочей ветки в основную.

Главная привычка новичка — чаще выполнять:

```bash
git status
```

Эта команда безопасна. Она ничего не ломает, а только показывает состояние проекта.

Если вы не понимаете, что происходит, начните с трёх команд:

```bash
git status
git branch
git remote -v
```

Они покажут:

- какие файлы изменены;
- в какой ветке вы находитесь;
- с каким GitHub-репозиторием связан проект.
