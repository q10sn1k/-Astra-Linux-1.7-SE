# Практика: загрузка, systemd, журналы, модули ядра и пакеты в Astra Linux SE 1.7

В этой работе вы исследуете уже загруженную Astra Linux, создадите собственную службу, найдёте причину её учебной неисправности, настроите таймер и точку монтирования, затем соберёте и обновите небольшой пакет с текстовыми данными.

**Все команды ниже выполняются в терминале удалённой Astra Linux SE 1.7 после входа по SSH.** На вашем компьютере может быть Windows, Arch Linux, Debian или Ubuntu: после входа команды обрабатывает удалённая система. Подключение описано в [инструкции SSH](ssh_connection_guide.md).

Работайте из обычной пользовательской оболочки Bash с выданным правом `sudo`. Не переходите в постоянную оболочку root. Если права администратора не предоставлены, доступны разделы чтения; создание системных юнитов, монтирование и установка пакета потребуют администратора. При запрете со стороны механизмов защиты Astra Linux остановите соответствующее упражнение и передайте сообщение администратору: менять режим защиты, метки и правила доступа для выполнения практики не нужно.

Команды выполняйте последовательно. Копируйте содержимое блока с командами, а не пример результата. Многострочный блок, начинающийся с `tee` и содержащий `EOF`, вставляйте полностью: завершающий `EOF` должен стоять в начале отдельной строки. Обозначение приглашения терминала в команды не включено.

Имена пользователей, номера UID, PID, версии, даты и сообщения в примерах условные. Ваша машина может показывать другие значения. Это примеры ожидаемого поведения, а не результаты проверки конкретной учебной ВМ. Если указано «Вывода нет», успешная команда просто возвращает приглашение терминала.

### Как устроена работа

1. Убедиться, что команды выполняются на нужной Astra Linux.
2. Найти следы стадий загрузки и изучить системные юниты.
3. Создать свою службу и исследовать её жизненный цикл.
4. Прочитать журнал, воспроизвести и исправить учебную ошибку.
5. Запустить периодическое задание через таймер.
6. Создать mount-юнит с ограниченной временной файловой системой.
7. Исследовать модули ядра без изменения работающих драйверов.
8. Изучить APT и dpkg; установить, обновить и удалить собственный пакет.
9. Удалить созданные объекты и проверить результат.

### Границы упражнений на удалённой машине

Служба SSH, сеть, межсетевой экран, загрузчик, параметры ядра, системные репозитории и `/etc/fstab` остаются рабочей инфраструктурой. В этой практике их только просматривают. Не останавливайте SSH и сетевые службы, не меняйте целевой режим загрузки, не перезагружайте и не выключайте ВМ.

Системные учебные юниты размещаются в `/run/systemd/system`: это временные определения до перезагрузки. Их включение в зависимости также будет временным. Учебная файловая система занимает отдельный каталог в `/mnt` и ограничена по объёму; существующие диски не форматируются. Настоящая установка затрагивает только созданный здесь пакет с одним текстовым файлом и без установочных сценариев. Обновление остальных пакетов рассматривается через симуляцию.

Для каждого пользователя имена объектов содержат его числовой UID. Не выполняйте практику одновременно в нескольких сеансах одной учётной записи: они получат одинаковые имена. Второй SSH-сеанс можно держать открытым для наблюдения и восстановления доступа, но команды изменения выполняйте только в основном сеансе.

## 1. Проверяем удалённую систему и права

### Кто выполняет команды

```bash
whoami
hostname
id
```

Пример результата:

```text
student
astra-lab
uid=1000(student) gid=1000(student) группы=1000(student),27(sudo)
```

`whoami` выводит имя текущей учётной записи; `hostname` — имя удалённого компьютера; `id` — числовые идентификаторы пользователя и его групп. Флагов в этих трёх командах нет. `uid` — идентификатор пользователя, `gid` — основной группы. Членство в группе само по себе ещё не гарантирует разрешение любой команды через `sudo`.

Проверьте имя компьютера. Если вместо учебной Astra Linux видите свой личный компьютер, сначала подключитесь по SSH. Если `uid=0`, вы работаете как root: вернитесь в обычную учётную запись перед созданием учебных объектов.

### Название ОС и версия ядра

```bash
cat /etc/os-release
cat /etc/astra_version
uname -r
```

Пример результата:

```text
PRETTY_NAME="Astra Linux"
NAME="Astra Linux"
ID=astra
VERSION_ID="1.7"
1.7.5
5.15.0-70-generic
```

`cat` читает указанный файл и печатает его содержимое; дополнительных флагов нет. `/etc/os-release` описывает дистрибутив, `/etc/astra_version` — версию Astra Linux. Состав файлов зависит от обновления; отсутствие второго файла не повод создавать его вручную. `uname` сообщает сведения о системе, `-r` выбирает выпуск работающего ядра. Версия ядра и версия дистрибутива — разные сведения; у разных обновлений 1.7 ядра могут различаться.

### Версия systemd и командная оболочка

```bash
systemctl --version
ps -p $$ -o comm=
```

Пример результата:

```text
systemd 241
+PAM +AUDIT +SELINUX +IMA +APPARMOR +SMACK +SYSVINIT +UTMP +LIBCRYPTSETUP +GCRYPT
bash
```

`systemctl` управляет systemd; `--version` выводит версию и возможности сборки, не меняя службы. Число в примере не является требованием к вашей ВМ.

`ps` показывает процессы; `-p` выбирает PID, `$$` подставляет PID текущей оболочки; `-o` задаёт столбцы; `comm=` означает краткое имя исполняемого файла без заголовка столбца. Ожидается `bash`. Если выданная удалённая оболочка другая, попросите администратора предоставить Bash для этой работы. Локальная fish или PowerShell после входа не определяет удалённую оболочку.

### Проверка права sudo

```bash
sudo -v
```

Пример результата:

```text
[sudo] пароль для student:
После правильного ввода пароля появляется приглашение терминала.
```

`sudo` выполняет разрешённые административные операции; `-v` проверяет и обновляет срок действия подтверждённых полномочий, не запускает административную оболочку. Пароль вводится без отображения символов; если авторизация ещё действует, запроса может не быть. Сообщение о запрете означает, что продолжать разделы изменения нельзя без предоставленных прав. Не перебирайте способы обхода ограничения.

### Подтверждаем наличие systemd как PID 1

```bash
ps -p 1 -o pid,comm,args
```

Пример результата:

```text
PID COMMAND         COMMAND
    1 systemd         /sbin/init
```

`ps` — просмотр процессов; `-p 1` — только процесс с PID 1; `-o pid,comm,args` — идентификатор, короткое имя и полная командная строка. В обычной загруженной Astra Linux здесь ожидается systemd. Если это контейнер без systemd или появляется ошибка подключения к системной шине, упражнения с системными юнитами не подходят к выданной среде: нужна полноценная учебная ВМ. Устанавливать альтернативную систему инициализации не нужно.

### Проверяем свободное место и память

```bash
df -h / /run /mnt
free -h
```

Пример результата:

```text
Файл.система    Размер Использовано Дост Использовано% Cмонтировано в
/dev/vda2         30G          8,0G   21G           28% /
tmpfs            392M          1,2M 391M            1% /run
/dev/vda2         30G          8,0G   21G           28% /
              total        used        free      shared  buff/cache   available
Mem:           3,8G        900M        1,5G         20M        1,4G        2,6G
Swap:          1,0G          0B        1,0G
```

`df` показывает использование файловых систем; `-h` — удобные единицы измерения; `/`, `/run`, `/mnt` — пути, для которых ищется содержащая файловая система. Каталог `/mnt` до учебного монтирования обычно находится на том же разделе, что и `/`.

`free` показывает память и swap; `-h` делает размеры читаемыми. Поле `available` оценивает память, доступную приложениям. Если корневая файловая система или `/run` почти заполнены, либо памяти осталось очень мало, сначала согласуйте состояние ВМ с администратором. Учебный tmpfs будет иметь верхний предел 8 MiB, а не занимать всю память.

## 2. Изучаем стадии уже завершённой загрузки

Компьютер проходит несколько этапов до появления SSH. Часть из них можно исследовать по следам работающей системы, но нельзя повторить внутри текущего сеанса.

| Стадия | Что происходит | Что можно проверить по SSH |
| --- | --- | --- |
| BIOS или UEFI | Прошивка выбирает загрузочное устройство. | Косвенные признаки режима прошивки. |
| Загрузчик, обычно GRUB | Выбирает ядро, initramfs и параметры запуска. | Переданные ядру параметры; меню загрузчика по SSH не открывается. |
| Ядро и initramfs | Инициализируются устройства и ранняя среда; подготавливается доступ к корневой ФС. | Сообщения ядра, сведения о корневой ФС и загруженных модулях. |
| systemd | Как PID 1 запускает зависимости, монтирования и службы. | Целевые состояния, зависимости, журнал и оценки длительности. |
| Работающая система | SSH принимает соединения пользователя. | Состояние SSH и журнал текущей загрузки. |

Initramfs — временная ранняя файловая среда для запуска ОС. Корневая файловая система — дерево каталогов, начинающееся с `/`. Target, или целевой юнит, — группа зависимостей systemd, описывающая определённое состояние системы.

### Определяем признаки UEFI

```bash
if [ -d /sys/firmware/efi ]; then
    printf 'Обнаружен интерфейс EFI\n'
else
    printf 'Интерфейс EFI не виден\n'
fi
```

Пример результата:

```text
Обнаружен интерфейс EFI
```

`if … then … else … fi` — условие Bash. `[` — команда проверки; `-d` проверяет существование каталога; `/sys/firmware/efi` — интерфейс ядра для EFI. `printf` выводит указанный текст; `\n` означает перевод строки. Флагов у `printf` нет. Отсутствие каталога на обычной ВМ часто соответствует загрузке в режиме BIOS, но ограничения виртуализации и видимости `/sys` тоже возможны. Эта проверка не меняет настройки прошивки.

### Читаем параметры работающего ядра

```bash
cat /proc/cmdline
```

Пример результата:

```text
BOOT_IMAGE=/boot/vmlinuz-5.15.0-70-generic root=UUID=11111111-2222-3333-4444-555555555555 ro quiet
```

`cat` без флагов читает `/proc/cmdline`. Это виртуальный файл с параметрами, переданными ядру при загрузке. `BOOT_IMAGE=` — указание образа загрузчиком, `root=` — источник корневой ФС, `UUID=` — идентификатор файловой системы, `ro` — начальный режим только для чтения, `quiet` — уменьшение количества сообщений. Это элементы вывода, их не надо вводить как команды. Не редактируйте GRUB и не пересоздавайте initramfs.

### Узнаём, откуда смонтирован корень

```bash
findmnt --target / --output TARGET,SOURCE,FSTYPE,OPTIONS
```

Пример результата:

```text
TARGET SOURCE    FSTYPE OPTIONS
/      /dev/vda2 ext4   rw,relatime,errors=remount-ro
```

`findmnt` показывает монтирования; `--target /` ищет файловую систему, содержащую путь `/`; `--output` задаёт столбцы. `TARGET` — куда смонтировано, `SOURCE` — источник, `FSTYPE` — тип ФС, `OPTIONS` — параметры. `rw` означает чтение и запись; `relatime` — режим обновления времени доступа; `errors=remount-ro` — реакция ext4 на ошибки. Название устройства может быть другим, в том числе логическим томом.

### Целевое состояние по умолчанию и активные targets

```bash
systemctl get-default
systemctl list-units --type=target --state=active --no-pager
```

Пример результата:

```text
graphical.target
UNIT                  LOAD   ACTIVE SUB    DESCRIPTION
basic.target          loaded active active Basic System
multi-user.target     loaded active active Multi-User System
graphical.target      loaded active active Graphical Interface
network.target        loaded active active Network
```

`get-default` читает target по умолчанию для загрузки. `list-units` показывает загруженные в менеджер юниты; `--type=target` оставляет целевые, `--state=active` — активные, `--no-pager` — печатает прямо в терминал без программы постраничного просмотра.

`multi-user.target` — многопользовательская система; `graphical.target` обычно добавляет графический вход. Графическая Astra Linux может принимать SSH, это не противоречие. Активность `network.target` сама по себе не доказывает доступность интернета. Из этого раздела не следует менять target: смена состояния системы может оборвать доступ.

### Смотрим зависимости многопользовательского состояния

```bash
systemctl list-dependencies multi-user.target --no-pager
```

Пример результата:

```text
multi-user.target
● ├─ssh.service
● ├─systemd-logind.service
● ├─basic.target
● └─remote-fs.target
```

`list-dependencies` выводит дерево зависимостей указанного юнита; `multi-user.target` — объект просмотра; `--no-pager` отключает постраничный просмотр. Состав дерева зависит от установки. Зависимость отвечает на вопрос, какие юниты связаны с достижением состояния, а не показывает точный последовательный сценарий: systemd запускает многие задачи параллельно.

### Оценка длительности загрузки

```bash
systemd-analyze time
systemd-analyze blame --no-pager
systemd-analyze critical-chain multi-user.target --no-pager
```

Пример результата:

```text
Startup finished in 2.100s (kernel) + 8.400s (userspace) = 10.500s
5.200s example.service
1.300s systemd-udev-settle.service
 180ms ssh.service
multi-user.target @8.400s
└─example.service @3.100s +5.200s
  └─basic.target @3.000s
```

`systemd-analyze` исследует работу systemd. `time` показывает доступные измерения этапов; `blame` сортирует юниты по измеренной длительности активации; `critical-chain multi-user.target` показывает цепочку, важную для достижения выбранного target. `--no-pager` отключает просмотрщик.

В дереве `@` — момент активации относительно начала соответствующей шкалы, `+` — длительность активации. Время параллельных служб нельзя складывать для получения общего времени. Долгое ожидание зависимости не равнозначно медленной работе самой службы. Учебное имя `example.service` иллюстрирует формат; искать его на своей ВМ не нужно. Прошивка, загрузчик и initramfs могут не иметь отдельных измерений; сообщение о недоступности метрик допустимо для некоторых сред.

### Сообщения ядра текущей загрузки

```bash
sudo journalctl -k -b -n 25 --no-pager
```

Пример результата:

```text
-- Logs begin at Thu 2026-10-22 09:00:00 MSK, end at Thu 2026-10-22 09:05:00 MSK. --
Oct 22 09:00:01 astra-lab kernel: Linux version 5.15.0-70-generic ...
Oct 22 09:00:02 astra-lab kernel: EXT4-fs (vda2): mounted filesystem with ordered data mode
```

`sudo` даёт разрешённый доступ к системному журналу. `journalctl` читает журнал; `-k` выбирает сообщения ядра; `-b` ограничивает текущей загрузкой; `-n 25` — не более 25 последних записей; `--no-pager` — вывод в терминал. Последние записи не обязаны содержать самые первые события: пример сокращён и показывает тип сообщений. Пустой результат означает отсутствие доступных записей по выбранному фильтру, а не доказательство отсутствия ошибок.

Проверьте понимание: какой процесс имеет PID 1? На каком этапе появился доступ по SSH? Какие признаки говорят о режиме UEFI? Чем дерево зависимостей отличается от временной шкалы? Запишите ответы своими словами; перезагрузка для проверки не требуется.

## 3. Читаем состояние существующих служб

Юнит — объект, которым управляет systemd. Суффикс имени определяет его вид: `.service` — служба, `.socket` — сокет активации, `.target` — группа зависимостей, `.timer` — расписание, `.mount` — монтирование, `.device` — устройство. На работающей машине безопаснее сначала читать состояние, затем изменять только созданные вами объекты.

### Загруженные службы и файлы служб

```bash
systemctl list-units --type=service --state=running --no-pager
systemctl list-unit-files --type=service --no-pager
```

Пример результата:

```text
UNIT                       LOAD   ACTIVE SUB     DESCRIPTION
ssh.service                loaded active running OpenBSD Secure Shell server
systemd-journald.service    loaded active running Journal Service

UNIT FILE                       STATE
ssh.service                     enabled
systemd-journald.service         static
```

`list-units` показывает юниты, известные менеджеру сейчас; `--type=service` выбирает службы; `--state=running` оставляет выполняющиеся; `--no-pager` отключает просмотрщик. `list-unit-files` показывает файлы определений и состояние их включения, включая неактивные службы; тот же `--type=service` ограничивает вид.

`loaded` — определение прочитано, `active` — юнит активен, `running` — процесс службы работает. `enabled` — созданы связи включения; `disabled` — таких связей нет; `static` — нет обычного механизма включения через раздел `[Install]`. Static-служба может запускаться как зависимость. `active` и `enabled` отвечают на разные вопросы.

### Читаем состояние SSH без изменения

```bash
systemctl status ssh.service --no-pager --full
systemctl is-active ssh.service
```

Пример результата:

```text
● ssh.service - OpenBSD Secure Shell server
   Loaded: loaded (/lib/systemd/system/ssh.service; enabled; vendor preset: enabled)
   Active: active (running) since Thu 2026-10-22 09:00:04 MSK
 Main PID: 640 (sshd)
active
```

`status` выводит состояние и недавние сообщения службы; `ssh.service` — имя SSH-сервера на типичной Astra Linux; `--no-pager` отключает просмотрщик, `--full` запрещает сокращение длинных строк. `is-active` печатает состояние активности. Если имя отсутствует, найдите фактическое имя в списке служб, не создавайте замену.

`Main PID` — основной процесс службы. У `status` и `is-active` ненулевой код завершения возможен для неработающей службы: это результат диагностики. SSH здесь только читаем. Остановка или перезапуск SSH не входят в упражнение.

### Смотрим определение SSH

```bash
systemctl cat ssh.service --no-pager
```

Пример результата:

```text
# /lib/systemd/system/ssh.service
[Unit]
Description=OpenBSD Secure Shell server
After=network.target auditd.service

[Service]
ExecStart=/usr/sbin/sshd -D $SSHD_OPTS

[Install]
WantedBy=multi-user.target
```

`cat` как подкоманда `systemctl` выводит файлы определения юнита и его дополнений; это другая команда, чем самостоятельная `cat`. `ssh.service` — объект чтения; `--no-pager` — без просмотрщика. Строка с `#` в примере — автоматически выведенный путь, её вводить не нужно.

`[Unit]` содержит общие свойства; `Description=` — описание; `After=` — порядок относительно других юнитов; `[Service]` описывает запуск; `ExecStart=` — исполняемая команда; `[Install]` — правила включения; `WantedBy=` — target, который будет хотеть этот юнит при включении. В показанном выводе `sshd -D` оставляет сервер на переднем плане для контроля systemd, `$SSHD_OPTS` — переменная окружения службы. Это разбор чужого определения, запускать его вручную не нужно. `After=` задаёт порядок, но сам по себе не запускает указанный соседний юнит.

### Исходные неисправные юниты

```bash
systemctl --failed --no-pager
```

Пример результата:

```text
UNIT LOAD ACTIVE SUB DESCRIPTION
0 loaded units listed.
```

`--failed` выбирает юниты в состоянии отказа; `--no-pager` выводит результат без просмотрщика. Если список непустой, запишите исходные имена: позднее важно отличать существовавшие неисправности от учебной ошибки. Не сбрасывайте состояние и не перезапускайте все неисправные службы разом.

## 4. Готовим имена и отдельные учебные каталоги

### Сохраняем параметры работы в переменных Bash

```bash
LAB_UID=$(id -u)
LAB_GID=$(id -g)
LAB_USER=$(id -un)
LAB_GROUP=$(id -gn)
LAB_TAG="astra-practice-${LAB_UID}"
LAB_DIR="/run/astra_practice_${LAB_UID}"
LAB_MOUNT_DIR="/mnt/astra_practice_${LAB_UID}"
LAB_SERVICE="${LAB_TAG}.service"
LAB_FAIL="${LAB_TAG}-failure.service"
LAB_TICK_SERVICE="${LAB_TAG}-tick.service"
LAB_TIMER="${LAB_TAG}-tick.timer"
LAB_MOUNT_UNIT=$(systemd-escape --path --suffix=mount "$LAB_MOUNT_DIR")
LAB_PACKAGE="astra-practice-data-${LAB_UID}"
LAB_WORK="$HOME/astra_practice_${LAB_UID}"
printf 'Пользователь: %s\nКаталог: %s\nСлужба: %s\nMount-юнит: %s\nПакет: %s\n' "$LAB_USER" "$LAB_DIR" "$LAB_SERVICE" "$LAB_MOUNT_UNIT" "$LAB_PACKAGE"
```

Пример результата:

```text
Пользователь: student
Каталог: /run/astra_practice_1000
Служба: astra-practice-1000.service
Mount-юнит: mnt-astra_practice_1000.mount
Пакет: astra-practice-data-1000
```

`ИМЯ=значение` сохраняет переменную Bash; пробелы вокруг `=` не ставятся. `$(...)` выполняет вложенную команду и подставляет её вывод. `id -u` — числовой UID, `id -g` — числовой GID, `id -un` — имя пользователя (`-u` выбирает пользователя, `-n` — имя), `id -gn` — имя основной группы (`-g` и `-n`). Значения берутся из удалённой машины.

`$ИМЯ` и `${ИМЯ}` подставляют переменную; фигурные скобки отделяют имя от соседнего текста. Двойные кавычки сохраняют путь единым аргументом. `$HOME` читается как домашний каталог пользователя и не переопределяется.

`systemd-escape` преобразует путь в имя юнита; `--path` задаёт обработку именно пути; `--suffix=mount` добавляет суффикс `.mount`. Имя mount-юнита обязано соответствовать точке монтирования. `printf` выводит строку, `%s` подставляет очередное текстовое значение, `\n` переводит строку.

Эти переменные существуют только в текущей оболочке. После повторного подключения выполните этот блок заново под той же учётной записью, затем изучите состояние созданных объектов. Каталоги повторно создавать и файлы бездумно перезаписывать не нужно. Пока ВМ не перезагружена, объекты в `/run` сохраняются независимо от SSH-сеанса.

### Проверяем, не заняты ли имена и пути

```bash
ls -ld "$LAB_DIR" "$LAB_MOUNT_DIR" "$LAB_WORK" "/usr/share/$LAB_PACKAGE" "/run/systemd/system/$LAB_FAIL.d" "/run/systemd/system/$LAB_TICK_SERVICE.d"
systemctl cat "$LAB_SERVICE" "$LAB_FAIL" "$LAB_TICK_SERVICE" "$LAB_TIMER" "$LAB_MOUNT_UNIT" --no-pager
dpkg-query -W "$LAB_PACKAGE"
```

Пример результата:

```text
ls: невозможно получить доступ к '/run/astra_practice_1000': Нет такого файла или каталога
ls: невозможно получить доступ к '/mnt/astra_practice_1000': Нет такого файла или каталога
ls: невозможно получить доступ к '/home/student/astra_practice_1000': Нет такого файла или каталога
Для /usr/share/astra-practice-data-1000 и обоих каталогов дополнений также ожидается сообщение об отсутствии.
No files found for astra-practice-1000.service.
No files found for astra-practice-1000-failure.service.
No files found for astra-practice-1000-tick.service.
No files found for astra-practice-1000-tick.timer.
No files found for mnt-astra_practice_1000.mount.
dpkg-query: не найден ни один пакет, соответствующий шаблону astra-practice-data-1000
```

`ls` перечисляет файлы; `-l` выводит подробные сведения, `-d` показывает сами каталоги, а не содержимое. Аргументы задают проверяемые пути, включая устанавливаемый каталог и каталоги дополнений. Для всех ожидается отсутствие. `systemctl cat` с несколькими именами ищет все определения, включая постоянные и дополнения; `--no-pager` — без просмотрщика. `dpkg-query` читает базу установленных пакетов; `-W` запрашивает запись об указанном имени.

**Здесь отсутствие объектов — ожидаемый результат**, поэтому команды могут завершиться с ненулевым кодом. Если хотя бы один путь, юнит или пакет уже существует, не продолжайте создание: это может быть предыдущая практика или чужая работа под той же учётной записью. Сначала разберите его происхождение. Не удаляйте существующие объекты только ради совпадения с примером.

### Создаём каталоги без перезаписи существующих

```bash
sudo mkdir -m 0755 "$LAB_DIR" "$LAB_MOUNT_DIR"
mkdir -m 0700 "$LAB_WORK"
```

Пример результата:

```text
Вывода нет.
```

`mkdir` создаёт каталог; `-m 0755` задаёт владельцу чтение, запись и проход, остальным — чтение и проход. `sudo` создаёт служебные каталоги от имени root; они остаются под его управлением. Второй `mkdir` выполняется обычным пользователем, `-m 0700` даёт доступ только владельцу.

Флага `-p` здесь нет намеренно: уже существующий каталог вызовет ошибку вместо незаметного повторного использования. Если любая команда сообщает об ошибке, остановитесь и выясните причину. `/run/...` хранит временные сценарии, `/mnt/...` — будущая точка монтирования, домашний каталог — исходники учебного пакета.

## 5. Создаём собственную службу systemd

### Создаём сценарий с сообщениями в журнал

```bash
sudo tee "$LAB_DIR/worker.sh" > /dev/null <<'EOF'
#!/bin/sh
printf 'worker: started\n'
while :; do
    printf 'worker: heartbeat\n'
    sleep 15
done
EOF
```

Пример результата:

```text
Вывода нет.
```

`tee` читает стандартный ввод и записывает его в указанный файл; `sudo` разрешает запись в каталог root. `> /dev/null` скрывает копию текста, которую `tee` обычно выводит в терминал; запись в файл сохраняется. `<<'EOF'` передаёт следующие строки как вход до отдельной строки `EOF`; кавычки у ограничителя запрещают Bash подставлять переменные внутри текста. `EOF` — выбранное слово-граница, в файл оно не попадает.

`#!/bin/sh` указывает интерпретатор сценария; запуск ниже всё равно будет явно через `/bin/sh`. `printf` печатает сообщение, `\n` добавляет перевод строки. `while … do … done` — цикл; `:` — встроенная команда, успешно завершающаяся без действий, поэтому цикл повторяется. `sleep 15` ждёт 15 секунд, снижая частоту работы и объём журнала. У `tee`, `printf`, `sleep` дополнительных флагов здесь нет. Сценарий не обращается к сети и не меняет настройки ОС.

### Ограничиваем права сценария и проверяем синтаксис

```bash
sudo chmod 0644 "$LAB_DIR/worker.sh"
/bin/sh -n "$LAB_DIR/worker.sh"
```

Пример результата:

```text
Вывода нет.
```

`chmod` меняет права: `0644` даёт владельцу чтение и запись, остальным — чтение; право исполнения не требуется, потому что файл читает интерпретатор. `sudo` нужен, так как файл принадлежит root. `/bin/sh` запускает стандартную командную оболочку; `-n` только проверяет синтаксис без выполнения сценария. Путь — проверяемый файл. Если синтаксическая ошибка есть, её надо исправить до запуска службы.

### Записываем временное определение службы

```bash
sudo tee "/run/systemd/system/$LAB_SERVICE" > /dev/null <<EOF
[Unit]
Description=Astra practice heartbeat $LAB_UID

[Service]
Type=simple
User=$LAB_USER
Group=$LAB_GROUP
ExecStart=/bin/sh $LAB_DIR/worker.sh
Restart=no
NoNewPrivileges=yes
StandardOutput=journal
StandardError=journal
SyslogIdentifier=$LAB_TAG

[Install]
WantedBy=multi-user.target
EOF
```

Пример результата:

```text
Вывода нет.
```

`sudo tee` записывает определение; `> /dev/null` скрывает повтор текста; `<<EOF` передаёт многострочный ввод. Здесь `EOF` без кавычек: Bash подставляет текущие значения `$LAB_UID`, `$LAB_USER`, `$LAB_GROUP`, `$LAB_DIR`, `$LAB_TAG` при создании файла. В готовом юните будут конкретные значения, а не ссылки на вашу SSH-оболочку.

| Строка определения | Смысл |
| --- | --- |
| `[Unit]` | Общие свойства юнита. |
| `Description=` | Понятное описание в списках и журнале. |
| `[Service]` | Настройки запуска процесса. |
| `Type=simple` | systemd контролирует непосредственно запущенный процесс; приложение не уходит в фон само. |
| `User=` и `Group=` | Сценарий работает с правами выданного обычного пользователя. |
| `ExecStart=/bin/sh ...` | Интерпретатор читает учебный сценарий. |
| `Restart=no` | Не перезапускать автоматически после завершения. |
| `NoNewPrivileges=yes` | Запретить процессу и потомкам получение новых привилегий через выполнение программ. |
| `StandardOutput=journal` | Направить обычный вывод в журнал. |
| `StandardError=journal` | Направить сообщения об ошибках в журнал. |
| `SyslogIdentifier=` | Метка сообщений приложения. |
| `[Install]` | Правила создания связей при включении. |
| `WantedBy=multi-user.target` | При включении добавить службу в желания этого target. |

Системный менеджер читает файл от root, но процесс выполняется как обычный пользователь. Постоянный каталог `/etc/systemd/system` в этом упражнении не используется.

### Проверяем юнит до запуска

```bash
sudo systemd-analyze verify "/run/systemd/system/$LAB_SERVICE"
```

Пример результата:

```text
Вывода нет при отсутствии диагностических сообщений.
```

`systemd-analyze verify` проверяет определение и зависимости; аргумент — полный путь файла. `sudo` обеспечивает доступ к системным определениям. Команда не запускает вашу службу. Предупреждения о других системных файлах отделяйте от ошибок собственного юнита. Не игнорируйте сообщение о неизвестном ключе или неправильном `ExecStart`. Проверка синтаксиса не гарантирует разрешение запуска политиками защиты.

### Перечитываем определения и запускаем службу

```bash
sudo systemctl daemon-reload
sudo systemctl start "$LAB_SERVICE"
```

Пример результата:

```text
Вывода нет.
```

`daemon-reload` перечитывает файлы юнитов и перестраивает зависимости системного менеджера. Он не перезапускает SSH и другие работающие службы. `start` запускает только указанный учебный юнит. `sudo` требуется для изменения состояния системного менеджера. Кавычки сохраняют имя из переменной одним аргументом. Дополнительных флагов нет.

Если `start` сообщает об ошибке, переходите к чтению `status` и журнала этой службы, а не к перезапуску всей машины.

### Проверяем результат запуска

```bash
systemctl status "$LAB_SERVICE" --no-pager --full
systemctl show "$LAB_SERVICE" -p ActiveState -p SubState -p MainPID -p FragmentPath
```

Пример результата:

```text
● astra-practice-1000.service - Astra practice heartbeat 1000
   Loaded: loaded (/run/systemd/system/astra-practice-1000.service; disabled; vendor preset: enabled)
   Active: active (running)
 Main PID: 2100 (sh)
Oct 22 09:10:00 astra-lab astra-practice-1000[2100]: worker: started
Oct 22 09:10:00 astra-lab astra-practice-1000[2100]: worker: heartbeat
MainPID=2100
FragmentPath=/run/systemd/system/astra-practice-1000.service
ActiveState=active
SubState=running
```

`status` показывает состояние; `--no-pager` отключает просмотрщик; `--full` сохраняет длинные строки. `show` выдаёт свойства в виде `имя=значение`; каждый `-p` выбирает свойство. `ActiveState` — общее состояние, `SubState` — уточнение, `MainPID` — основной процесс, `FragmentPath` — файл определения. Порядок строк может отличаться.

Сейчас служба `active`, но `disabled`: её запустили вручную и ещё не включили в зависимости target. `vendor preset` — рекомендация поставщика, а не текущее состояние включения. Найдите собственный PID и убедитесь, что путь начинается с `/run/systemd/system/`.

## 6. Управляем жизненным циклом своей службы

Действия со службой отличаются от изменения правил её включения. `start` и `stop` меняют состояние сейчас; `enable` и `disable` меняют связи запуска. Перечитывание определений менеджером и перечитывание настроек приложением тоже разные операции.

| Действие | Что означает |
| --- | --- |
| `start` | Запустить юнит. |
| `stop` | Остановить юнит. |
| `restart` | Остановить и запустить; может запустить и ранее остановленную службу. |
| `reload` | Попросить приложение перечитать свои настройки, если оно это поддерживает. |
| `daemon-reload` | Перечитать файлы юнитов systemd; процессы приложения не перезапускаются. |
| `enable` | Создать связи включения согласно `[Install]`. |
| `disable` | Удалить связи включения; работающий процесс без отдельного указания не останавливается. |

Таблица объясняет термины. Практические команды ниже обращаются только к вашей службе. У нашего сценария нет собственного механизма перечитывания настроек, поэтому действие `reload` для него не отрабатывается.

### Останавливаем службу и наблюдаем состояние

```bash
sudo systemctl stop "$LAB_SERVICE"
systemctl is-active "$LAB_SERVICE"
systemctl show "$LAB_SERVICE" -p ActiveState -p SubState -p MainPID
```

Пример результата:

```text
inactive
MainPID=0
ActiveState=inactive
SubState=dead
```

`stop` завершает работу выбранной службы через systemd. `is-active` выводит состояние и при `inactive` возвращает ненулевой код — здесь это ожидаемо. `show` читает свойства; `-p` выбирает поля `ActiveState`, `SubState`, `MainPID`. Нулевой `MainPID` означает отсутствие основного процесса. `sudo` нужен только для остановки; команды чтения выполняются обычным пользователем. Пустой вывод самой команды `stop` означает нормальное выполнение.

### Повторно запускаем и перезапускаем

```bash
sudo systemctl start "$LAB_SERVICE"
systemctl show "$LAB_SERVICE" -p MainPID
sudo systemctl restart "$LAB_SERVICE"
systemctl show "$LAB_SERVICE" -p MainPID
```

Пример результата:

```text
MainPID=2200
MainPID=2210
```

`start` запускает службу; `restart` выполняет остановку и новый запуск. `show -p MainPID` читает основной PID до и после. Значение обычно меняется: создан новый процесс. `sudo` разрешает операции изменения. Дополнительных флагов нет, кроме `-p` выбора свойства. Сами `start` и `restart` при успехе ничего не печатают. Это упражнение выполняется только для учебного юнита; на SSH-сервер его не переносим.

### Временно включаем службу в зависимости target

```bash
sudo systemctl enable --runtime "$LAB_SERVICE"
systemctl is-enabled "$LAB_SERVICE"
systemctl is-active "$LAB_SERVICE"
```

Пример результата:

```text
Created symlink /run/systemd/system/multi-user.target.wants/astra-practice-1000.service → /run/systemd/system/astra-practice-1000.service.
enabled-runtime
active
```

`enable` создаёт связи по `[Install]`; `--runtime` размещает их в `/run`, только до перезагрузки. `is-enabled` читает состояние включения, `is-active` — состояние работы. `sudo` даёт право создать системную ссылку. Постоянная загрузочная конфигурация не меняется.

Служба уже работала до `enable`; эта команда не является её повторным запуском. Символическая ссылка — запись, ссылающаяся на файл определения. Мы изучаем механизм включения без перезагрузки. Не проверяйте его перезапуском ВМ.

### Отключаем временное включение, оставляя процесс работающим

```bash
sudo systemctl disable --runtime "$LAB_SERVICE"
systemctl is-enabled "$LAB_SERVICE"
systemctl is-active "$LAB_SERVICE"
```

Пример результата:

```text
Removed /run/systemd/system/multi-user.target.wants/astra-practice-1000.service.
disabled
active
```

`disable --runtime` убирает временные связи включения данного юнита. `is-enabled` теперь показывает `disabled` и возвращает ненулевой код; `is-active` всё ещё показывает `active`. `sudo` требуется для удаления ссылки; дополнительных флагов нет. Процесс продолжает работу, потому что остановку не запрашивали. Убедитесь по двум результатам, что состояние включения и состояние выполнения независимы.

## 7. Читаем и фильтруем журнал через journalctl

systemd-journald собирает структурированные сообщения: время, источник, принадлежность службе и другие поля. `journalctl` читает эти записи. В работе мы не удаляем журналы, не меняем срок хранения и не перезапускаем journald. Для чтения системных записей используем `sudo`, чтобы результат не зависел от членства в группе доступа к журналу.

### Смотрим последние сообщения своей службы

```bash
sudo journalctl -u "$LAB_SERVICE" -b -n 20 --no-pager
```

Пример результата:

```text
Oct 22 09:12:00 astra-lab systemd[1]: Started Astra practice heartbeat 1000.
Oct 22 09:12:00 astra-lab astra-practice-1000[2210]: worker: started
Oct 22 09:12:00 astra-lab astra-practice-1000[2210]: worker: heartbeat
Oct 22 09:12:15 astra-lab astra-practice-1000[2210]: worker: heartbeat
```

`journalctl` читает журнал; `-u` выбирает записи, относящиеся к конкретному юниту; значение берётся из `$LAB_SERVICE`; `-b` — текущая загрузка; `-n 20` — не более 20 последних сообщений; `--no-pager` — без просмотрщика. `sudo` разрешает чтение всего системного журнала.

Здесь видны и сообщения менеджера о службе, и строки самого сценария. Сравните PID и время запуска с предыдущим разделом. Если записей пока мало, дождитесь следующего heartbeat, не увеличивая частоту цикла.

### Ограничиваем интервал времени и меняем формат

```bash
sudo journalctl -u "$LAB_SERVICE" --since "5 minutes ago" --until now -o short-iso --no-pager
```

Пример результата:

```text
2026-10-22T09:12:00+0300 astra-lab astra-practice-1000[2210]: worker: started
2026-10-22T09:12:15+0300 astra-lab astra-practice-1000[2210]: worker: heartbeat
```

`-u` выбирает юнит; `--since "5 minutes ago"` задаёт нижнюю границу относительно текущего времени удалённой системы; `--until now` — верхнюю границу; кавычки объединяют слова аргумента. `-o short-iso` выбирает компактный формат с датой и часовым поясом; `--no-pager` отключает просмотрщик. Фильтры времени и службы применяются совместно. Часовой пояс может отличаться от примера; не меняйте время ВМ ради совпадения.

### Отдельно смотрим предупреждения и ошибки загрузки

```bash
sudo journalctl -b -p warning -n 30 --no-pager
```

Пример результата:

```text
-- No entries --
```

`-b` — текущая загрузка; `-p warning` выбирает уровень warning и более серьёзные уровни, включая err, crit, alert и emerg; `-n 30` ограничивает число последних записей; `--no-pager` отключает просмотрщик. `sudo` обеспечивает доступ. Приоритет — серьёзность сообщения, а не важность службы. Отсутствие записей по этому фильтру не доказывает полную исправность системы. Если записи есть, прочитайте источник и контекст, не исправляйте чужие службы в рамках практики.

### Посмотрим доступные загрузки

```bash
sudo journalctl --list-boots --no-pager
```

Пример результата:

```text
0 0123456789abcdef0123456789abcdef Thu 2026-10-22 09:00:00 MSK—Thu 2026-10-22 09:15:00 MSK
```

`--list-boots` выводит доступные в журнале загрузки; `--no-pager` отключает просмотрщик. `0` — текущая загрузка, отрицательные смещения — предыдущие. Длинная строка — идентификатор загрузки. Если хранение журнала временное или архивы очищались, доступна только текущая загрузка. Создавать постоянное хранилище журнала для этой практики не нужно.

### Читаем предыдущую загрузку, если она есть в списке

```bash
sudo journalctl -b -1 -n 15 --no-pager
```

Пример результата:

```text
Specifying boot ID or boot offset has no effect, no persistent journal was found.
```

`-b -1` выбирает предыдущую загрузку; `-n 15` — последние 15 записей; `--no-pager` — без просмотрщика. В примере предыдущий журнал недоступен: это допустимо. Если он есть, вместо сообщения увидите записи. Не перезагружайте ВМ, чтобы получить второй элемент списка. Доступность истории зависит от настроек и сохранённых файлов, а не от числа запусков ОС вообще.

### Наблюдаем новые сообщения без завершения SSH

```bash
sudo journalctl -u "$LAB_SERVICE" -f -n 3
```

Пример результата:

```text
Oct 22 09:15:00 astra-lab astra-practice-1000[2210]: worker: heartbeat
Oct 22 09:15:15 astra-lab astra-practice-1000[2210]: worker: heartbeat
Далее появляются новые строки; после Ctrl+C возвращается приглашение Bash.
```

`-u` выбирает службу; `-f` включает непрерывное слежение за новыми сообщениями; `-n 3` сначала показывает не более трёх последних записей. Прерывайте просмотр сочетанием **Ctrl+C** после появления новых heartbeat. Оно завершает локально запущенный внутри удалённой оболочки `journalctl`, а ваша SSH-сессия и служба продолжают работать. Ctrl+Z не нужен: он приостановил бы просмотрщик. Не вводите следующий блок, пока не вернулось приглашение Bash.

### Читаем только текст сообщений приложения

```bash
sudo journalctl -b -t "$LAB_TAG" -n 5 -o cat --no-pager
```

Пример результата:

```text
worker: started
worker: heartbeat
worker: heartbeat
worker: heartbeat
worker: heartbeat
```

`-b` — текущая загрузка; `-t` выбирает `SyslogIdentifier`, заданный в юните; `-n 5` — последние пять записей; `-o cat` оставляет только текст сообщения; `--no-pager` — без просмотрщика. `cat` здесь название формата, а не отдельная команда чтения файла. В отличие от фильтра `-u`, метка приложения обычно не включает сообщения самого systemd о запуске и остановке службы.

### Сохраняем журнал только своей службы

```bash
sudo journalctl -u "$LAB_SERVICE" -b -n 50 --no-pager > "$LAB_WORK/heartbeat-journal.txt"
ls -l "$LAB_WORK/heartbeat-journal.txt"
```

Пример результата:

```text
-rw-r--r-- 1 student student 3510 окт 22 09:16 /home/student/astra_practice_1000/heartbeat-journal.txt
```

`journalctl`: `-u` — выбранный юнит, `-b` — текущая загрузка, `-n 50` — последние 50 записей, `--no-pager` — без просмотрщика. `>` перенаправляет вывод в файл и заменяет прежнее содержимое, если файл уже существует. Перенаправление выполняет ваша обычная Bash, поэтому файл принадлежит пользователю, хотя чтение журнала делал `sudo`. `ls -l` показывает права, владельца, размер, дату и путь. Сам экспорт при успехе ничего не печатает.

Сохраняйте для передачи только относящиеся к задаче записи: общий системный журнал может содержать сведения об инфраструктуре. В учебном экспорте выбран только ваш heartbeat-юнит.

## 8. Воспроизводим и исправляем отказ учебной службы

Создадим второй юнит, который намеренно завершается с кодом ошибки. Он не связан с SSH или первой службой. Так можно отработать диагностику, не ломая рабочую конфигурацию.

### Создаём службу с предсказуемым отказом

```bash
sudo tee "/run/systemd/system/$LAB_FAIL" > /dev/null <<EOF
[Unit]
Description=Astra practice failure $LAB_UID

[Service]
Type=oneshot
User=$LAB_USER
Group=$LAB_GROUP
ExecStart=/bin/false
NoNewPrivileges=yes
EOF
sudo systemd-analyze verify "/run/systemd/system/$LAB_FAIL"
sudo systemctl daemon-reload
```

Пример результата:

```text
Вывода нет при отсутствии ошибок проверки.
```

`sudo tee` записывает файл, `> /dev/null` подавляет повтор текста, `<<EOF` передаёт строки с подстановкой переменных. `systemd-analyze verify` проверяет именно новый файл; `systemctl daemon-reload` перечитывает определения.

`[Unit]` и `Description=` задают описание; `[Service]` — параметры запуска; `Type=oneshot` означает одноразовую задачу, результат которой systemd ожидает перед завершением активации. `User=` и `Group=` задают обычного пользователя; `ExecStart=/bin/false` запускает программу, которая ничего не делает и возвращает код 1; `NoNewPrivileges=yes` ограничивает получение привилегий. `[Install]` отсутствует: включение этой службы не требуется. Это корректный синтаксис и намеренно неуспешное выполнение.

### Запускаем отказ и собираем три вида свидетельств

```bash
sudo systemctl start "$LAB_FAIL"
systemctl status "$LAB_FAIL" --no-pager --full
systemctl show "$LAB_FAIL" -p Result -p ExecMainCode -p ExecMainStatus
sudo journalctl -u "$LAB_FAIL" -b -n 15 --no-pager
```

Пример результата:

```text
Job for astra-practice-1000-failure.service failed because the control process exited with error code.
● astra-practice-1000-failure.service - Astra practice failure 1000
   Active: failed (Result: exit-code)
  Process: 2400 ExecStart=/bin/false (code=exited, status=1/FAILURE)
Result=exit-code
ExecMainCode=1
ExecMainStatus=1
Oct 22 09:17:00 astra-lab systemd[1]: astra-practice-1000-failure.service: Main process exited, code=exited, status=1/FAILURE
Oct 22 09:17:00 astra-lab systemd[1]: Failed to start Astra practice failure 1000.
```

`start` пытается выполнить задачу и здесь ожидаемо завершается ошибкой. `status` показывает состояние и последние сообщения, `--no-pager` отключает просмотрщик, `--full` сохраняет полные строки. `show` читает поля; каждый `-p` выбирает одно: `Result` — итог службы, `ExecMainCode` — вид завершения главного процесса, `ExecMainStatus` — его статус. В примере процесс завершился обычным выходом с кодом 1, а не был убит сигналом.

`journalctl -u` выбирает этот юнит, `-b` — текущую загрузку, `-n 15` ограничивает записи, `--no-pager` печатает их сразу. `sudo` нужен для запуска и полного чтения системного журнала. Ненулевые коды `start` и `status` на этом шаге — ожидаемая часть упражнения. Не применяйте исправление к другим службам со статусом failed.

### Исправляем запуск через отдельное дополнение drop-in

```bash
sudo mkdir -m 0755 "/run/systemd/system/$LAB_FAIL.d"
sudo tee "/run/systemd/system/$LAB_FAIL.d/override.conf" > /dev/null <<'EOF'
[Service]
ExecStart=
ExecStart=/bin/true
EOF
sudo systemd-analyze verify "/run/systemd/system/$LAB_FAIL"
sudo systemctl daemon-reload
systemctl cat "$LAB_FAIL" --no-pager
```

Пример результата:

```text
# /run/systemd/system/astra-practice-1000-failure.service
[Unit]
Description=Astra practice failure 1000
[Service]
Type=oneshot
User=student
Group=student
ExecStart=/bin/false
NoNewPrivileges=yes

# /run/systemd/system/astra-practice-1000-failure.service.d/override.conf
[Service]
ExecStart=
ExecStart=/bin/true
```

`mkdir -m 0755` создаёт каталог дополнения с правами владельца на запись и чтением/проходом для остальных; `sudo` делает его системным. Имя `$LAB_FAIL.d` в Bash означает значение переменной `$LAB_FAIL` и суффикс `.d`. `tee`, перенаправление и quoted-heredoc работают как раньше; кавычки у `EOF` запрещают подстановки внутри файла. `verify` проверяет определение вместе с дополнениями; `daemon-reload` перечитывает; `systemctl cat --no-pager` показывает основной файл и drop-in.

Drop-in — дополнительный файл свойств поверх исходного определения. `[Service]` выбирает раздел службы; пустой `ExecStart=` сначала сбрасывает прежний список команд запуска; следующий `ExecStart=/bin/true` задаёт успешную команду. `/bin/true` ничего не печатает и возвращает 0. Сброс необходим, чтобы именно заменить прежнюю команду, а не добавить вторую. Создание дополнения не переписывает базовый файл.

### Проверяем успешное одноразовое выполнение

```bash
sudo systemctl start "$LAB_FAIL"
systemctl show "$LAB_FAIL" -p ActiveState -p Result -p ExecMainStatus
sudo journalctl -u "$LAB_FAIL" -b -n 8 --no-pager
```

Пример результата:

```text
Result=success
ExecMainStatus=0
ActiveState=inactive
Oct 22 09:18:00 astra-lab systemd[1]: Starting Astra practice failure 1000...
Oct 22 09:18:00 astra-lab systemd[1]: Started Astra practice failure 1000.
```

`start` запускает исправленную задачу; успешного вывода самой команды нет. `show -p` читает выбранные свойства: успешный результат и код 0 при `inactive` допустимы. Для `Type=oneshot` без `RemainAfterExit=yes` процесс заканчивается, и служба не остаётся активной. Это отличается от отказа `failed`. `journalctl`: `-u` — этот юнит, `-b` — текущая загрузка, `-n 8` — последние восемь записей, `--no-pager` — без просмотрщика. Ранние записи об ошибке остаются в журнале и не означают повторного отказа; сравнивайте время.

### Сбрасываем только учебный след отказа

```bash
sudo systemctl reset-failed "$LAB_FAIL"
systemctl --failed --no-pager
```

Пример результата:

```text
UNIT LOAD ACTIVE SUB DESCRIPTION
0 loaded units listed.
```

`reset-failed` сбрасывает состояние failed и счётчики ограничения запусков только названного юнита; он не исправляет настройки и не запускает процесс. После успешного запуска сбрасывать failed обычно уже нечего, но команда показывает адресную работу со счётчиками. `--failed` читает общий список отказов, `--no-pager` отключает просмотрщик. Сравните с исходным списком из раздела 3: чужие неисправности могли сохраниться, их сбрасывать не нужно.

Объясните своими словами: почему файл с `/bin/false` прошёл проверку синтаксиса, но не запустился успешно? Почему после исправления oneshot оказался `inactive`, хотя `Result=success`? Почему перечитывание определения без нового запуска ещё не проверяет исправление?

## 9. Создаём периодическое задание через timer-юнит

Таймер запускает отдельный юнит, обычно одноимённую службу. Создадим короткую задачу, которая печатает одно сообщение и завершается. Такой подход удобен для периодических проверок. Наш пример не делает сетевых запросов и не записывает системные файлы.

### Определяем одноразовую задачу для таймера

```bash
sudo tee "/run/systemd/system/$LAB_TICK_SERVICE" > /dev/null <<EOF
[Unit]
Description=Astra practice timer message $LAB_UID

[Service]
Type=oneshot
User=$LAB_USER
Group=$LAB_GROUP
ExecStart=/bin/echo timer: task completed
NoNewPrivileges=yes
StandardOutput=journal
StandardError=journal
EOF
```

Пример результата:

```text
Вывода нет.
```

`sudo tee` записывает файл в системный временный каталог; `> /dev/null` скрывает копию; `<<EOF` разрешает подстановку переменных. `[Unit]` и `Description=` описывают задачу; `[Service]` задаёт исполнение; `Type=oneshot` — короткий процесс; `User=` и `Group=` — обычные права; `ExecStart=/bin/echo timer: task completed` печатает текст и завершается кодом 0. У `echo` флагов нет; слова после пути — аргументы программы. `NoNewPrivileges=yes` запрещает получение новых привилегий; два `Standard...=journal` отправляют вывод и ошибки в журнал.

`RemainAfterExit` не включаем: служба должна снова становиться неактивной после каждого успешного выполнения, чтобы таймер мог запустить её повторно.

### Определяем расписание

```bash
sudo tee "/run/systemd/system/$LAB_TIMER" > /dev/null <<EOF
[Unit]
Description=Astra practice timer $LAB_UID

[Timer]
OnActiveSec=10s
OnUnitActiveSec=30s
AccuracySec=1s
Unit=$LAB_TICK_SERVICE
EOF
sudo systemd-analyze verify "/run/systemd/system/$LAB_TICK_SERVICE" "/run/systemd/system/$LAB_TIMER"
sudo systemctl daemon-reload
```

Пример результата:

```text
Вывода нет при успешной проверке.
```

`tee`, `sudo`, `> /dev/null` и `<<EOF` создают файл с подстановкой текущих имён. `systemd-analyze verify` проверяет оба файла, переданные отдельными аргументами; `daemon-reload` перечитывает определения.

`[Timer]` — раздел таймера; `OnActiveSec=10s` задаёт первый запуск относительно активации самого таймера; `OnUnitActiveSec=30s` — последующие запуски относительно последней активации целевой службы; `AccuracySec=1s` задаёт окно объединения срабатываний systemd, а не гарантию точности до секунды; `Unit=` явно указывает целевую службу. `s` — секунды. `[Unit]` и `Description=` — общие свойства. `[Install]` отсутствует, включение на загрузку не требуется. Это относительное расписание, не календарное время.

### Запускаем таймер и находим ближайшее срабатывание

```bash
sudo systemctl start "$LAB_TIMER"
systemctl list-timers --all "$LAB_TIMER" --no-pager
```

Пример результата:

```text
NEXT                        LEFT     LAST PASSED UNIT                           ACTIVATES
Thu 2026-10-22 09:20:10 MSK   8s left  n/a  n/a    astra-practice-1000-tick.timer astra-practice-1000-tick.service
1 timers listed.
```

`start` активирует только таймер; при успехе не печатает ничего. `list-timers` показывает расписание; `--all` включает также неактивные загруженные таймеры; аргумент `$LAB_TIMER` ограничивает вывод вашим именем; `--no-pager` отключает просмотрщик. `NEXT` — ближайшее срабатывание, `LEFT` — сколько осталось, `LAST` — последнее, `PASSED` — сколько прошло, `ACTIVATES` — запускаемый юнит. До первого выполнения `n/a` нормально.

### Находим результаты периодического задания

```bash
sudo journalctl -u "$LAB_TICK_SERVICE" -b -n 12 --no-pager
systemctl is-active "$LAB_TIMER"
systemctl show "$LAB_TICK_SERVICE" -p ActiveState -p Result
```

Пример результата:

```text
Oct 22 09:20:10 astra-lab echo[2500]: timer: task completed
Oct 22 09:20:40 astra-lab echo[2510]: timer: task completed
active
Result=success
ActiveState=inactive
```

Выполните после появления двух срабатываний в расписании. `journalctl`: `-u` — служба задания, `-b` — текущая загрузка, `-n 12` — последние записи, `--no-pager` — без просмотрщика. `is-active` читает активность таймера, `show -p` — результат и состояние короткой службы.

Активный таймер и неактивная успешно завершившаяся oneshot-служба — нормальная пара. Если записей ещё нет, проверьте `NEXT`, имя `Unit=` и состояние именно своего таймера. Не сокращайте интервал до долей секунды.

### Останавливаем дальнейшие срабатывания

```bash
sudo systemctl stop "$LAB_TIMER"
systemctl is-active "$LAB_TIMER"
```

Пример результата:

```text
inactive
```

`stop` отключает выполнение таймера сейчас; `is-active` проверяет состояние и при `inactive` возвращает ненулевой код. Остановка таймера не является универсальной остановкой уже выполняющегося задания: у нас задача короткая и к этому моменту обычно завершена. Другие таймеры системы не затрагиваются.

## 10. Создаём mount-юнит для отдельной временной файловой системы

Монтирование присоединяет файловую систему к каталогу. Сам каталог существует и до монтирования, но после операции его видимое содержимое берётся из подключённой ФС. Поэтому монтировать поверх непустого рабочего каталога опасно: прежние файлы окажутся временно скрыты.

Используем только созданный пустой каталог `$LAB_MOUNT_DIR`. Источник — tmpfs, файловая система в памяти с возможным использованием swap. Ей не нужен раздел диска, форматирование или петлевое устройство. Данные tmpfs теряются после размонтирования. Лимит не резервирует весь объём заранее, но ограничивает возможное потребление. Корень, домашние каталоги и системные монтирования не изменяются.

### Убеждаемся, что каталог пуст и пока не является точкой монтирования

```bash
ls -la "$LAB_MOUNT_DIR"
mountpoint "$LAB_MOUNT_DIR"
```

Пример результата:

```text
итого 8
drwxr-xr-x 2 root root 4096 окт 22 09:10 .
drwxr-xr-x 3 root root 4096 окт 22 09:10 ..
/mnt/astra_practice_1000 is not a mountpoint
```

`ls -la` объединяет `-l` (подробные сведения) и `-a` (включая имена, начинающиеся с точки). Только `.` и `..` означают пустой каталог: это ссылки на него самого и родителя. `mountpoint` без флагов проверяет точную точку монтирования; отрицательный результат и ненулевой код сейчас ожидаемы. Если видны другие файлы или каталог уже смонтирован, не продолжайте, пока не выясните причину.

### Записываем определение mount-юнита

```bash
sudo tee "/run/systemd/system/$LAB_MOUNT_UNIT" > /dev/null <<EOF
[Unit]
Description=Astra practice tmpfs $LAB_UID

[Mount]
What=tmpfs
Where=$LAB_MOUNT_DIR
Type=tmpfs
Options=size=8M,nr_inodes=128,mode=0700,uid=$LAB_UID,gid=$LAB_GID,nosuid,nodev,noexec
TimeoutSec=10s
EOF
sudo systemd-analyze verify "/run/systemd/system/$LAB_MOUNT_UNIT"
sudo systemctl daemon-reload
```

Пример результата:

```text
Вывода нет при успешной проверке.
```

`sudo tee` создаёт файл; `> /dev/null` скрывает повтор содержимого; `<<EOF` разрешает подстановку пути, UID и GID. `verify` проверяет определение; `daemon-reload` перечитывает файлы юнитов.

| Параметр | Значение и назначение |
| --- | --- |
| `[Unit]`, `Description=` | Общее описание монтирования. |
| `[Mount]` | Раздел параметров точки монтирования. |
| `What=tmpfs` | Условное имя источника виртуальной ФС, а не дисковое устройство. |
| `Where=` | Полный путь отдельной точки монтирования. |
| `Type=tmpfs` | Тип файловой системы. |
| `size=8M` | Верхний предел данных — 8 MiB; не означает немедленное выделение памяти. |
| `nr_inodes=128` | Предел числа inode, то есть объектов ФС. |
| `mode=0700` | Доступ к корню ФС только у владельца. |
| `uid=` и `gid=` | Владелец корня смонтированной ФС — текущий учебный пользователь и его группа. |
| `nosuid` | Не учитывать повышение привилегий через setuid/setgid и файловые capabilities на этой ФС. |
| `nodev` | Не интерпретировать специальные файлы как устройства. |
| `noexec` | Не разрешать непосредственное выполнение файлов с этого монтирования; это не запрет чтения сценария интерпретатором. |
| `TimeoutSec=10s` | Ограничить ожидание операции монтирования. |

В этой точке не запускаем программы: она нужна для небольших текстовых файлов. Имя `$LAB_MOUNT_UNIT` уже вычислено через `systemd-escape` и соответствует `Where=`. `[Install]` отсутствует, автоматическая загрузка этого монтирования не настраивается.

### Монтируем и проверяем точный результат

```bash
sudo systemctl start "$LAB_MOUNT_UNIT"
systemctl status "$LAB_MOUNT_UNIT" --no-pager --full
findmnt --mountpoint "$LAB_MOUNT_DIR" --output TARGET,SOURCE,FSTYPE,OPTIONS
df -h "$LAB_MOUNT_DIR"
```

Пример результата:

```text
● mnt-astra_practice_1000.mount - Astra practice tmpfs 1000
   Loaded: loaded (/run/systemd/system/mnt-astra_practice_1000.mount; static; vendor preset: enabled)
   Active: active (mounted)
    Where: /mnt/astra_practice_1000
     What: tmpfs
TARGET                    SOURCE FSTYPE OPTIONS
/mnt/astra_practice_1000   tmpfs  tmpfs  rw,nosuid,nodev,noexec,relatime,size=8192k,nr_inodes=128,mode=700,uid=1000,gid=1000
Файл.система Размер Использовано Дост Использовано% Cмонтировано в
tmpfs          8,0M             0 8,0M            0% /mnt/astra_practice_1000
```

`systemctl start` запускает только ваш mount-юнит; `sudo` нужен для монтирования. `status` читает состояние, `--no-pager` отключает просмотрщик, `--full` запрещает сокращение строк. `findmnt --mountpoint` ищет именно отдельное монтирование в указанной точке, а не содержащую путь родительскую ФС; `--output` задаёт столбцы. `df -h` показывает объём ФС в читаемых единицах.

Ожидаются `active (mounted)`, `tmpfs`, отдельный путь и небольшой лимит. Порядок и представление опций ядром могут отличаться. Если вместо tmpfs виден системный диск, не записывайте данные до выяснения результата. При запрете монтирования механизмами защиты не меняйте политику: переходите к чтению журнала своего юнита.

### Записываем и читаем небольшой файл без sudo

```bash
printf 'Hello from the isolated tmpfs\n' > "$LAB_MOUNT_DIR/note.txt"
cat "$LAB_MOUNT_DIR/note.txt"
ls -l "$LAB_MOUNT_DIR/note.txt"
```

Пример результата:

```text
Hello from the isolated tmpfs
-rw-r--r-- 1 student student 30 окт 22 09:25 /mnt/astra_practice_1000/note.txt
```

`printf` печатает строку, `\n` завершает её переводом строки; `>` направляет вывод в файл вместо терминала. `cat` без флагов читает файл; `ls -l` показывает сведения о нём. Пишем обычным пользователем, потому что `uid=` и `gid=` в параметрах монтирования назначили ему корень tmpfs. Права файла зависят также от `umask`; при другом значении они могут быть строже. На системном диске файл не создаётся: текущая точка ведёт в tmpfs.

### Связываем учебную задачу с нужным монтированием

```bash
sudo mkdir -m 0755 "/run/systemd/system/$LAB_TICK_SERVICE.d"
sudo tee "/run/systemd/system/$LAB_TICK_SERVICE.d/mount.conf" > /dev/null <<EOF
[Unit]
RequiresMountsFor=$LAB_MOUNT_DIR

[Service]
ExecStart=
ExecStart=/bin/sh -c 'echo mount dependency works > $LAB_MOUNT_DIR/from-service.txt'
EOF
sudo systemd-analyze verify "/run/systemd/system/$LAB_TICK_SERVICE"
sudo systemctl daemon-reload
```

Пример результата:

```text
Вывода нет при успешной проверке.
```

Таймер из предыдущего раздела должен быть уже остановлен. `mkdir -m 0755` создаёт каталог дополнения; `sudo tee` пишет файл; `> /dev/null` скрывает копию; `<<EOF` подставляет путь. `verify` проверяет службу, `daemon-reload` перечитывает определения.

`RequiresMountsFor=` в `[Unit]` добавляет зависимости требования и порядка для монтирований, необходимых указанному пути. Это сильнее одного `After=`: systemd не только упорядочит запуск, но и запросит нужное монтирование. В `[Service]` пустой `ExecStart=` сбрасывает прежнюю команду, следующий задаёт новую.

`/bin/sh -c` исполняет строку, переданную следующим аргументом; `-c` означает «выполнить текст команды». Одинарные кавычки внутри строки юнита группируют этот аргумент для systemd. Внутри оболочки `echo` без флагов печатает текст, а `>` записывает его в `from-service.txt`. Внешний heredoc подставляет путь ещё при создании файла. Пользователь и ограничения службы наследуются из основного определения.

### Проверяем размонтирование и потерю временного содержимого

```bash
cd "$HOME"
sudo systemctl stop "$LAB_MOUNT_UNIT"
mountpoint "$LAB_MOUNT_DIR"
ls -la "$LAB_MOUNT_DIR"
```

Пример результата:

```text
/mnt/astra_practice_1000 is not a mountpoint
итого 8
drwxr-xr-x 2 root root 4096 окт 22 09:10 .
drwxr-xr-x 3 root root 4096 окт 22 09:10 ..
```

`cd` меняет текущий каталог Bash; `$HOME` — ваш домашний каталог; флагов нет. Это исключает удержание tmpfs текущей оболочкой. `systemctl stop` размонтирует только учебную точку; `sudo` даёт право операции. `mountpoint` подтверждает отсутствие монтирования и ожидаемо возвращает ненулевой код. `ls -la` показывает все записи каталога подробно.

Прежний `note.txt` исчез вместе с tmpfs. Сам нижележащий пустой каталог снова виден на системной ФС. Это не удаление каталога. Если размонтирование не удалось и сообщается `busy`, выйдите из этого каталога во всех своих терминалах и закройте свои открытые в нём файлы. Не используйте принудительное или ленивое размонтирование и не завершайте чужие процессы.

### Запускаем задачу и наблюдаем автоматическое монтирование зависимости

```bash
sudo systemctl start "$LAB_TICK_SERVICE"
findmnt --mountpoint "$LAB_MOUNT_DIR" --output TARGET,SOURCE,FSTYPE
cat "$LAB_MOUNT_DIR/from-service.txt"
sudo journalctl -u "$LAB_MOUNT_UNIT" -b -n 10 --no-pager
```

Пример результата:

```text
TARGET                    SOURCE FSTYPE
/mnt/astra_practice_1000   tmpfs  tmpfs
mount dependency works
Oct 22 09:27:00 astra-lab systemd[1]: Mounting Astra practice tmpfs 1000...
Oct 22 09:27:00 astra-lab systemd[1]: Mounted Astra practice tmpfs 1000.
```

`start` запускает oneshot-службу, а systemd сначала поднимает требуемое монтирование. `findmnt --mountpoint` подтверждает точную точку, `--output` выбирает столбцы; `cat` читает результат работы службы. `journalctl -u` выбирает mount-юнит, `-b` — текущую загрузку, `-n 10` — последние десять записей, `--no-pager` отключает просмотрщик. Сам `start` вывода не имеет.

Новый tmpfs не содержит старого `note.txt`, но содержит новый `from-service.txt`. После завершения oneshot монтирование остаётся активным: зависимости запуска не означают автоматическое размонтирование при выходе короткой задачи. Мы удалим его явно при очистке. Не запускайте теперь таймер повторно без необходимости: его задача уже изменена дополнением.

Проверьте понимание: зачем имя mount-юнита вычислять из пути? Чем `--target` отличается от `--mountpoint` у `findmnt`? Почему данные tmpfs исчезают после остановки? Почему для службы с файлом в tmpfs одного `After=` недостаточно?

## 11. Исследуем модули ядра без выгрузки драйверов

Модуль ядра — дополнительный код, подключаемый к ядру, например драйвер устройства или поддержка файловой системы. Часть функций может быть встроена непосредственно в ядро: их отсутствие в списке модулей не означает отсутствие поддержки.

На удалённой ВМ особенно опасно выгружать драйверы сетевых карт, виртуальных устройств, дисков и корневой ФС: SSH может исчезнуть вместе с доступом к данным. Здесь используем чтение сведений и сухой прогон `modprobe`. Параметры модулей, списки запрета и initramfs не меняем.

### Смотрим загруженные модули

```bash
lsmod | head -n 15
```

Пример результата:

```text
Module                  Size  Used by
crc32c_generic         16384  0
virtio_net            53248  0
virtio_blk            20480  2
ext4                 974848  1
mbcache               16384  1 ext4
```

`lsmod` без флагов выводит модули работающего ядра. `|` передаёт вывод следующей программе. `head -n 15` оставляет первые 15 строк; `-n` задаёт количество. `Module` — имя, `Size` — размер модуля в памяти, `Used by` — счётчик использования и имена зависимых модулей, если они есть.

Счётчик 0 не является разрешением на выгрузку: важность драйвера и ограничения ядра так не определяются. Строк в примере меньше лимита, реальные имена и размеры отличаются.

### Находим каталог модулей для текущего ядра

```bash
ls -ld "/lib/modules/$(uname -r)"
```

Пример результата:

```text
drwxr-xr-x 5 root root 4096 окт 22 08:00 /lib/modules/5.15.0-70-generic
```

`uname -r` возвращает версию работающего ядра; `$(...)` подставляет её в путь. `ls -l` показывает подробные сведения, `-d` — сам каталог. Двойные кавычки сохраняют путь единым аргументом. Если каталога нет, не создавайте его вручную и не подставляйте версию другого ядра: для дальнейшей диагностики нужна согласованность установленного набора модулей и работающего ядра.

### Читаем сведения об одном модуле

```bash
modinfo -F filename crc32c_generic
modinfo -F description crc32c_generic
modinfo -F depends crc32c_generic
```

Пример результата:

```text
/lib/modules/5.15.0-70-generic/kernel/crypto/crc32c_generic.ko
CRC32c (Castagnoli) calculations
После имени зависимостей может быть пустая строка.
```

`modinfo` читает метаданные модуля; `-F` выбирает поле: `filename` — путь, `description` — описание, `depends` — зависимости. `crc32c_generic` — распространённая программная реализация контрольной суммы CRC32c, выбранная только как пример чтения метаданных, без загрузки. Контрольная сумма помогает обнаруживать изменения данных; это не шифрование.

Если модуль отсутствует, получите сообщение об ошибке: это допустимое различие комплектации ядра. Для чтения можно выбрать другое точное имя из собственного `lsmod`, но не запускайте для него команды изменения. Пустое поле `depends` означает отсутствие перечисленных модульных зависимостей, а не отсутствие любых связей с ядром. Суффикс файла может включать сжатие.

### Делаем сухой прогон разрешения модуля

```bash
sudo modprobe --dry-run --verbose --show-depends crc32c_generic
```

Пример результата:

```text
insmod /lib/modules/5.15.0-70-generic/kernel/crypto/crc32c_generic.ko
```

`modprobe` подбирает модуль и зависимости для текущего ядра. `--dry-run` запрещает реальные операции загрузки, выгрузки и выполнение установочных команд; `--verbose` запрашивает подробности; `--show-depends` выводит найденные зависимости и команды их подключения, не выполняя их. `sudo` обеспечивает чтение системной конфигурации по правилам машины.

Строка `insmod ...` здесь **план, а не отдельная команда для копирования**. Если конфигурация содержит собственные `install`-правила, они также могут быть показаны как текст. На иной сборке результат отличается, модуль может быть встроен или отсутствовать. Не убирайте `--dry-run` и не превращайте диагностический пример в загрузку. В этом разделе не меняется ни один модуль.

### Читаем ошибки ядра отдельно от прикладных журналов

```bash
sudo journalctl -k -b -p warning -n 20 --no-pager
```

Пример результата:

```text
-- No entries --
```

`journalctl` читает журнал; `-k` выбирает ядро; `-b` — текущую загрузку; `-p warning` — предупреждения и более серьёзные приоритеты; `-n 20` ограничивает последние записи; `--no-pager` отключает просмотрщик. `sudo` даёт доступ. Если сообщения есть, сопоставьте время и имя устройства, но не меняйте драйвер удалённой ВМ на основании одного сообщения. Отсутствие записей по фильтру не является полной проверкой драйверов.

## 12. Изучаем APT, dpkg и настроенные репозитории

В Astra Linux используются пакеты `.deb`. `dpkg` ведёт базу установленных пакетов и устанавливает содержимое конкретного пакета; APT дополнительно работает с источниками, индексами, версиями и зависимостями. Репозиторий — источник пакетов и описаний, а индекс — локальная информация о доступных пакетах.

Настройки репозиториев зависят от установленного обновления Astra Linux, доступных носителей и правил инфраструктуры. Не копируйте источники Debian, Ubuntu, Astra Linux 1.8 или другого выпуска в эту ВМ. Мы только читаем существующую конфигурацию, а установку отрабатываем на собственном локальном пакете.

### Находим файлы настроенных источников

```bash
ls -l /etc/apt/sources.list
find /etc/apt/sources.list.d -maxdepth 1 -type f -print
```

Пример результата:

```text
-rw-r--r-- 1 root root 310 окт 22 08:00 /etc/apt/sources.list
/etc/apt/sources.list.d/local-training.list
```

`ls -l` читает сведения об основном файле источников. `find` ищет в указанном каталоге; `-maxdepth 1` ограничивает глубину непосредственными элементами, `-type f` выбирает обычные файлы, `-print` выводит пути. Если дополнительных файлов нет, вторая команда ничего не выведет. Отсутствие одного из путей допустимо при другой организации конфигурации.

Дополнительные источники APT обычно лежат в `.list` и, если поддерживается установленной версией APT, `.sources`. Имена файлов сами по себе ещё не показывают, какие источники активны.

### Читаем источники без редактирования

```bash
grep -R -n -E --include="*.list" --include="*.sources" "^[[:space:]]*[^#[:space:]]" /etc/apt/sources.list /etc/apt/sources.list.d
```

Пример результата:

```text
/etc/apt/sources.list:1:deb https://repo.example.invalid/astra/approved/ 1.7_x86-64 main contrib non-free
/etc/apt/sources.list.d/local-training.list:1:deb https://mirror.example.invalid/astra/approved/ 1.7_x86-64 main
```

`grep` ищет строки; `-R` проходит по каталогам рекурсивно, `-n` добавляет номер строки, `-E` включает расширенное регулярное выражение; `--include="*.list"` и `--include="*.sources"` ограничивают имена файлов, кавычки сохраняют шаблоны для `grep`. Выражение `^[[:space:]]*[^#[:space:]]` выбирает строки, где первый непробельный символ не `#`: `^` — начало, `[[:space:]]*` — ноль или больше пробельных символов, `[^...]` — символ вне перечисленного набора. Аргументы в конце — источники поиска. Команда не меняет настройки. При отсутствии совпадений код 1 ожидаем.

Адреса `.invalid` в примере намеренно нерабочие; их нельзя записывать в конфигурацию. Реальный вывод останется внутри вашей SSH-сессии. В строке `.list` `deb` означает бинарные пакеты; следующий элемент — адрес; затем выпуск/набор; `main`, `contrib`, `non-free` — компоненты. Строки `deb-src` описывают исходные пакеты. В `.sources` формат иной: используются поля наподобие `Types:`, `URIs:`, `Suites:`, `Components:`. Закомментированные записи не используются; поле `Enabled: no` также может отключать источник в `.sources`.

### Смотрим установленную и доступную версии базового пакета

```bash
apt-cache policy bash
dpkg-query -W -f='${binary:Package}\t${Version}\t${Status}\n' bash
```

Пример результата:

```text
bash:
  Установлен: 5.0-4
  Кандидат:   5.0-4
  Таблица версий:
 *** 5.0-4 100
        100 /var/lib/dpkg/status
bash    5.0-4    install ok installed
```

`apt-cache policy` читает сведения о версии и приоритетах из локальных индексов; `bash` — имя пакета. `Установлен` — текущая версия; `Кандидат` — версия, которую выбрал бы APT при текущей конфигурации; `***` отмечает установленную версию. Числа приоритетов влияют на выбор. Чтение не обращается за обновлением индексов автоматически.

`dpkg-query -W` запрашивает пакет из базы; `-f=` задаёт формат. `${binary:Package}`, `${Version}`, `${Status}` здесь поля `dpkg-query`, а не переменные Bash: одинарные кавычки предотвращают их подстановку оболочкой. `\t` — табуляция, `\n` — новая строка. `install ok installed` означает установленный и сконфигурированный пакет. Версии в примере условные.

### Ищем пакет и читаем его описание

```bash
apt-cache search --names-only "^bash$"
apt-cache show bash | head -n 20
```

Пример результата:

```text

Package: bash
Version: 5.0-4
Architecture: amd64
Essential: yes
Description: GNU Bourne Again SHell
```

`apt-cache search` ищет по локальным описаниям; `--names-only` ограничивает поиск именами; регулярное выражение `^bash$` требует точного имени: `^` — начало, `$` — конец. Кавычки сохраняют выражение. `apt-cache show` выводит карточку пакета. `|` передаёт её в `head`, `-n 20` оставляет первые двадцать строк. `Essential: yes` — признак базового пакета; удалять его для упражнения нельзя. Поиск и чтение не устанавливают ПО.

### Связываем файл с пакетом и смотрим список его файлов

```bash
dpkg-query -S /bin/bash
dpkg-query -L bash | head -n 15
```

Пример результата:

```text

/.
/bin
/bin/bash
/etc
/etc/bash.bashrc
/usr
/usr/share
/usr/share/doc
/usr/share/doc/bash
```

`dpkg-query -S` ищет владельца пути среди записанных в базе пакетов; `/bin/bash` — проверяемый файл. `-L` перечисляет зарегистрированные файлы пакета `bash`; `| head -n 15` ограничивает вывод пятнадцатью строками. Поиск отражает базу пакетов, а не гарантирует неизменность файла на диске. На системе с другой организацией `/bin` и `/usr/bin` путь может отличаться; это не основание удалять или перемещать оболочку.

### Проверяем согласованность базы пакетов

```bash
sudo dpkg --audit
```

Пример результата:

```text
Вывода нет, если незавершённых состояний пакетов не найдено.
```

`dpkg --audit` проверяет базу на частично установленные пакеты и ряд несогласованностей; `sudo` обеспечивает доступ. Это диагностика, а не проверка всего содержимого каждого файла и не автоматическое исправление. Если перечислены проблемные системные пакеты, отложите установку учебного пакета и передайте вывод администратору. Не запускайте массовое исправление зависимостей наугад.

### При необходимости обновляем только индексы разрешённых источников

```bash
sudo apt-get update
```

Пример результата:

```text
Сущ:1 https://repo.example.invalid/astra/approved 1.7_x86-64 InRelease
Чтение списков пакетов… Готово
```

Этот шаг выполняйте, только если настроенные источники соответствуют вашей ВМ и доступны из неё. `apt-get update` скачивает индексы из уже настроенных репозиториев; `sudo` нужен для записи в системный кэш APT. Команда не устанавливает новые версии пакетов, но может выполнять настроенные администратором APT-hooks и делать сетевые обращения. URL в примере заменён на нерабочий адрес `.invalid`: ваша команда использует реальные существующие настройки, а не пример.

При недоступной сети этот шаг можно пропустить и продолжить локальное пакетное упражнение. Ошибка DNS, носитель `cdrom:`, запрос носителя, недоверенная подпись или недоступный сервер — повод остановить обновление индексов и разобраться с администратором. Ctrl+C прекращает текущую попытку; не добавляйте чужой репозиторий, не отключайте проверку подписей и не удаляйте файлы блокировок. При сообщении о занятой блокировке дождитесь завершения штатного менеджера пакетов.

### Смотрим обновления без их установки

```bash
apt list --upgradable
sudo apt-get --simulate upgrade
```

Пример результата:

```text
Listing... Done
bash/approved 5.0-5 amd64 [upgradable from: 5.0-4]
Чтение списков пакетов… Готово
Построение дерева зависимостей… Готово
Следующие пакеты будут обновлены:
  bash
Обновлено 1 пакетов, установлено 0 новых пакетов, для удаления отмечено 0 пакетов.
Inst bash [5.0-4] (5.0-5 approved [amd64])
Conf bash (5.0-5 approved [amd64])
```

`apt list` показывает списки пакетов; `--upgradable` выбирает доступные обновления по текущим индексам. `apt-get upgrade` строит обычный план обновления установленных пакетов; **`--simulate` переводит его в симуляцию без установки, удаления и настройки пакетов**. `sudo` обеспечивает чтение тех же настроек APT, что были бы доступны административной операции. `Inst` и `Conf` в выводе описывают план установки и настройки, а не выполненное действие.

Если индексы не обновлялись, результат может быть устаревшим. Не выполняйте этот блок без `--simulate`. На Astra Linux общесистемные обновления выбираются по документации конкретного очередного обновления и регламенту администратора; в рамках SSH-практики обновлять ядро, SSH, systemd и весь дистрибутив не требуется.

## 13. Собираем локальный пакет только с учебными данными

Для реальной установки создадим пакет, содержимое которого полностью видно: один текстовый файл в отдельном каталоге `/usr/share`. В нём не будет зависимостей, служб, конфигурационных файлов, файлов устройств, ссылок и сценариев `preinst`, `postinst`, `prerm`, `postrm`. Поэтому упражнение не требует скачивания стороннего ПО и не перезапускает SSH.

Даже установка собственного пакета изменяет системную базу dpkg. Выполняйте этот раздел только на выданной учебной ВМ и при исправной базе пакетов. Штатные системные триггеры dpkg могут выполняться по правилам ВМ; пакет создаётся вне обычных каталогов документов и man-страниц, чтобы не добавлять ненужные триггеры. При уже имеющихся незавершённых состояниях из предыдущего раздела установку отложите.

### Готовим дерево пакета в своём рабочем каталоге

```bash
mkdir -p "$LAB_WORK/pkg/DEBIAN" "$LAB_WORK/pkg/usr/share/$LAB_PACKAGE"
printf 'Practice data, version 1.0\n' > "$LAB_WORK/pkg/usr/share/$LAB_PACKAGE/note.txt"
```

Пример результата:

```text
Вывода нет.
```

`mkdir -p` создаёт недостающие промежуточные каталоги. Здесь это допустимо, потому что весь `$LAB_WORK` уже создан специально для практики и принадлежит вам. `DEBIAN` — служебный каталог описания пакета; `usr/share/...` — дерево будущих устанавливаемых данных. `printf` печатает содержимое, `\n` добавляет перевод строки, `>` записывает в `note.txt`. Системный `/usr/share` пока не меняется: это только исходное дерево внутри вашего домашнего каталога.

### Создаём описание пакета

```bash
tee "$LAB_WORK/pkg/DEBIAN/control" > /dev/null <<EOF
Package: $LAB_PACKAGE
Version: 1.0
Section: misc
Priority: optional
Architecture: all
Maintainer: Training Example <training@example.invalid>
Description: Data-only Astra Linux practice package
 Contains one text file for package management exercises.
EOF
```

Пример результата:

```text
Вывода нет.
```

`tee` без `sudo` пишет пользовательский файл; `> /dev/null` скрывает копию; `<<EOF` передаёт строки с подстановкой имени `$LAB_PACKAGE`. `control` — обязательное описание бинарного пакета.

| Поле | Значение |
| --- | --- |
| `Package` | Уникальное учебное имя с UID. |
| `Version` | Версия содержимого, здесь `1.0`. |
| `Section` | Категория, здесь прочие пакеты. |
| `Priority` | Приоритет, необязательный пакет. |
| `Architecture: all` | Нет машинного кода, содержимое не зависит от архитектуры процессора. |
| `Maintainer` | Контакт в метаданных; здесь вымышленное имя и зарезервированный домен `.invalid`. |
| `Description` | Краткое описание и продолжение с начальным пробелом. |

Не удаляйте начальный пробел перед `Contains`: он обозначает продолжение описания. Установочных сценариев здесь нет; не добавляйте их.

### Проверяем права и собираем архив

```bash
chmod 0755 "$LAB_WORK/pkg" "$LAB_WORK/pkg/DEBIAN" "$LAB_WORK/pkg/usr" "$LAB_WORK/pkg/usr/share" "$LAB_WORK/pkg/usr/share/$LAB_PACKAGE"
chmod 0644 "$LAB_WORK/pkg/DEBIAN/control" "$LAB_WORK/pkg/usr/share/$LAB_PACKAGE/note.txt"
dpkg-deb --build --root-owner-group "$LAB_WORK/pkg" "$LAB_WORK/${LAB_PACKAGE}_1.0_all.deb"
```

Пример результата:

```text
dpkg-deb: сборка пакета «astra-practice-data-1000» в «/home/student/astra_practice_1000/astra-practice-data-1000_1.0_all.deb».
```

`chmod 0755` назначает каталогам чтение и проход для всех, запись владельцу; `chmod 0644` делает файлы читаемыми без права исполнения. Это важно для создаваемого архива: права установленного содержимого берутся из исходного дерева. Все аргументы относятся к вашей новой рабочей папке.

`dpkg-deb` работает с `.deb`-архивами; `--build` собирает пакет из дерева; `--root-owner-group` записывает владельца и группу содержимого в архив как root без запуска сборки от root. Первый путь — исходное дерево, второй — новый архив. Сборка ничего не устанавливает. Часть имени `_all` соответствует архитектуре из control; версию dpkg берёт из поля `Version`, а не только из имени файла.

### Осматриваем метаданные и содержимое до установки

```bash
dpkg-deb --info "$LAB_WORK/${LAB_PACKAGE}_1.0_all.deb"
dpkg-deb --contents "$LAB_WORK/${LAB_PACKAGE}_1.0_all.deb"
```

Пример результата:

```text
новый пакет Debian, версия 2.0.

 Package: astra-practice-data-1000
 Version: 1.0
 Section: misc
 Priority: optional
 Architecture: all
 Maintainer: Training Example <training@example.invalid>

  Contains one text file for package management exercises.
drwxr-xr-x root/root         0 2026-10-22 09:35 ./
drwxr-xr-x root/root         0 2026-10-22 09:35 ./usr/
drwxr-xr-x root/root         0 2026-10-22 09:35 ./usr/share/
drwxr-xr-x root/root         0 2026-10-22 09:35 ./usr/share/astra-practice-data-1000/
-rw-r--r-- root/root        27 2026-10-22 09:35 ./usr/share/astra-practice-data-1000/note.txt
```

`dpkg-deb --info` выводит метаданные и список элементов управляющего архива; `--contents` перечисляет устанавливаемое дерево с правами и владельцами. Единственный аргумент каждой команды — ваш архив. Размеры и даты могут отличаться; пример вывода сокращён.

Проверьте имя пакета, версию `1.0`, архитектуру `all`, владельца `root/root` и единственный обычный файл `note.txt` в `/usr/share/$LAB_PACKAGE`. В управляющем архиве должен быть только `control`, без сценариев. Если неожиданно обнаружены `/etc`, службы, исполняемые файлы или чужие пути, пакет не устанавливайте: сначала исправьте исходное дерево.

### Смотрим план установки через APT

```bash
sudo apt-get --simulate install "$LAB_WORK/${LAB_PACKAGE}_1.0_all.deb"
```

Пример результата:

```text

Построение дерева зависимостей… Готово
```

`apt-get install` строит установку указанного локального `.deb`; полный путь отличает файл от имени пакета в репозитории; `--simulate` оставляет только план. `sudo` даёт административный контекст чтения. В нормальном плане изменяется только ваш пакет, нет обновлений и удалений других пакетов. Если APT предлагает исправить накопленные системные проблемы, остановитесь: наш пакет не должен требовать таких изменений. Сам план не устанавливает файл.

### Устанавливаем только проверенный локальный пакет


Пример результата:


`dpkg --install` устанавливает и настраивает пакет из указанного архива; `sudo` нужен для записи в `/usr/share` и базу dpkg. У нашего пакета нет зависимостей и установочных сценариев, поэтому достаточно dpkg и не нужен сетевой доступ. Для произвольного стороннего пакета dpkg сам недостающие зависимости из репозитория не скачает: этот приём нельзя бездумно переносить на неизвестное ПО.

Если пакетная база занята, дождитесь штатной операции, не удаляйте блокировки. При любой иной ошибке сохраните полный вывод и не запускайте массовое автоматическое исправление. Ожидается ровно установленный учебный пакет.

### Подтверждаем установленную версию, файлы и владельца

```bash
dpkg-query -W -f='${binary:Package}\t${Version}\t${Status}\n' "$LAB_PACKAGE"

dpkg-query -S "/usr/share/$LAB_PACKAGE/note.txt"

```

Пример результата:

```text

/.

/usr/share
```

`dpkg-query -W` читает запись о пакете; `-f=` выбирает поля имени, версии и состояния. Одинарные кавычки сохраняют `${...}` как поля формата dpkg; `\t` — табуляция, `\n` — перевод строки. `-L` перечисляет зарегистрированные пути, `-S` находит пакет-владельца указанного файла. `cat` без флагов читает установленное содержимое. ## 14. Обновляем свой пакет и исследуем удаление

Установленный пакет и исходный `.deb` — разные вещи. Изменение исходника в домашнем каталоге само по себе не обновляет установленный файл. Для обновления соберём новый архив с более высокой версией и установим его.

### Меняем версию и данные только в исходном дереве

```bash
sed -i 's/^Version: 1[.]0$/Version: 1.1/' "$LAB_WORK/pkg/DEBIAN/control"
printf 'Practice data, version 1.1\n' > "$LAB_WORK/pkg/usr/share/$LAB_PACKAGE/note.txt"
dpkg-deb --build --root-owner-group "$LAB_WORK/pkg" "$LAB_WORK/${LAB_PACKAGE}_1.1_all.deb"
dpkg-deb --field "$LAB_WORK/${LAB_PACKAGE}_1.1_all.deb" Package Version
```

Пример результата:

```text
dpkg-deb: сборка пакета «astra-practice-data-1000» в «/home/student/astra_practice_1000/astra-practice-data-1000_1.1_all.deb».
Package: astra-practice-data-1000
Version: 1.1
```

`sed` преобразует текст; `-i` записывает результат в тот же исходный файл. Выражение `s/старое/новое/` выполняет замену: `^Version: 1[.]0$` выбирает строго строку версии 1.0; `^` — начало, `$` — конец, `[.]` — буквальная точка. Меняется только ваш control, системные конфигурации не редактируются.

`printf` и `>` заменяют исходный текст; `\n` добавляет перевод строки. `dpkg-deb --build --root-owner-group` собирает новый архив с владельцем root в метаданных. `--field` читает только перечисленные поля `Package` и `Version`. Установленная версия пока остаётся 1.0: проверьте различие с предыдущим разделом.

### Планируем обновление единственного учебного пакета

```bash
sudo apt-get --simulate install "$LAB_WORK/${LAB_PACKAGE}_1.1_all.deb"
```

Пример результата:

```text
Следующие пакеты будут обновлены:
  astra-practice-data-1000
Обновлено 1 пакетов, установлено 0 новых пакетов, для удаления отмечено 0 пакетов.
Inst astra-practice-data-1000 [1.0] (1.1 local-deb [all])
Conf astra-practice-data-1000 (1.1 local-deb [all])
```

`apt-get install` при более новой версии того же пакета строит обновление; `--simulate` не даёт применить план. Полный путь указывает новый локальный архив; `sudo` обеспечивает административный контекст. В плане должна быть только замена вашего пакета с 1.0 на 1.1. `Inst` и `Conf` — запланированные действия. Любые другие системные изменения требуют остановиться и разобраться.

### Обновляем и проверяем содержимое

```bash
sudo dpkg --install "$LAB_WORK/${LAB_PACKAGE}_1.1_all.deb"
dpkg-query -W -f='${Version}\n' "$LAB_PACKAGE"
cat "/usr/share/$LAB_PACKAGE/note.txt"
```

Пример результата:

```text
Подготовка к распаковке …/astra-practice-data-1000_1.1_all.deb …
Распаковывается astra-practice-data-1000 (1.1) на замену (1.0) …
Настраивается пакет astra-practice-data-1000 (1.1) …
1.1
Practice data, version 1.1
```

`sudo dpkg --install` устанавливает новую версию того же имени поверх предыдущей. `dpkg-query -W` запрашивает пакет; `-f='${Version}\n'` выводит только поле версии с переводом строки, кавычки защищают шаблон от Bash. `cat` без флагов читает установленный файл. Теперь должны согласоваться метаданные `1.1` и строка содержимого `1.1`. Версия в имени архива сама по себе не достаточна — важны метаданные и реальный результат.

### Сравниваем remove и purge в симуляции

```bash
sudo apt-get --simulate remove "$LAB_PACKAGE"
sudo apt-get --simulate purge "$LAB_PACKAGE"
```

Пример результата:

```text
Следующие пакеты будут УДАЛЕНЫ:
  astra-practice-data-1000
Remv astra-practice-data-1000 [1.1]

Следующие пакеты будут УДАЛЕНЫ:
  astra-practice-data-1000*
Purg astra-practice-data-1000 [1.1]
```

`apt-get remove` планирует удаление пакета с сохранением его управляемых конфигурационных файлов; `purge` планирует удаление также таких конфигурационных файлов. `--simulate` в обеих командах запрещает применять план. Аргумент — только ваше имя пакета; `sudo` обеспечивает административный контекст. `Remv` и `Purg` показывают тип действия.

Наш пакет конфигурационных файлов не содержит, поэтому практическая разница в содержимом минимальна. `purge` не означает универсальное уничтожение пользовательских данных в домашних каталогах и резервных копиях. Массовое удаление неиспользуемых пакетов в этой работе не выполняется.

### Удаляем свой пакет без затрагивания других

```bash
sudo dpkg --purge "$LAB_PACKAGE"
dpkg-query -W "$LAB_PACKAGE"
ls -ld "/usr/share/$LAB_PACKAGE"
```

Пример результата:

```text
Удаляется astra-practice-data-1000 (1.1) …
dpkg-query: не найден ни один пакет, соответствующий шаблону astra-practice-data-1000
ls: невозможно получить доступ к '/usr/share/astra-practice-data-1000': Нет такого файла или каталога
```

`dpkg --purge` удаляет только указанный пакет и его зарегистрированные конфигурационные файлы; `sudo` разрешает изменение базы и системных путей. `dpkg-query -W` после удаления ожидаемо сообщает об отсутствии записи; `ls -ld` проверяет сам каталог с подробностями и ожидаемо сообщает об отсутствии. Эти две проверки имеют ненулевой код: здесь это признак ожидаемого отсутствия объекта.

Если каталог остался, не удаляйте его рекурсивно: проверьте, не созданы ли в нём дополнительные файлы, которые dpkg не зарегистрировал. Архивы и исходное дерево в `$LAB_WORK` пока сохраняются, удаление установленного пакета их не затрагивает.

### Проверяем журнал пакетной операции

```bash
grep -F "$LAB_PACKAGE" /var/log/dpkg.log | tail -n 12
```

Пример результата:

```text
2026-10-22 09:36:00 install astra-practice-data-1000:all <none> 1.0
2026-10-22 09:36:00 status installed astra-practice-data-1000:all 1.0
2026-10-22 09:38:00 upgrade astra-practice-data-1000:all 1.0 1.1
2026-10-22 09:38:00 status installed astra-practice-data-1000:all 1.1
2026-10-22 09:40:00 remove astra-practice-data-1000:all 1.1 <none>
2026-10-22 09:40:00 purge astra-practice-data-1000:all 1.1 <none>
```

`grep -F` ищет буквальный текст имени, без интерпретации как регулярного выражения, в `/var/log/dpkg.log`; `|` передаёт совпадения в `tail`; `-n 12` оставляет последние двенадцать строк. Пример сокращён: между ними возможны дополнительные изменения состояния. При запрете чтения администратор может разрешить просмотр через `sudo`; менять права журнала нельзя. При иной настройке журналирования файл может быть недоступен или уже ротирован.

Здесь видны реальные действия dpkg. Симуляции APT не должны добавлять записи об установке и удалении пакетов. Отличайте журнал пакетов от systemd journal: это разные источники событий.

## 15. Убираем учебные объекты и проверяем доступность системы

Выполняйте очистку под той же обычной учётной записью и в оболочке с переменными из раздела 4. Если подключались заново, сначала повторите только блок присваивания переменных. Не повторяйте создание файлов. Перед удалением убедитесь, что UID, имена и пути ваши.

Сначала останавливаются источники периодических запусков и службы, потом монтирование. Только после подтверждённого размонтирования удаляются определения и пустой каталог. Ниже нет рекурсивного удаления произвольного дерева и нет очистки общесистемного журнала.

### Ещё раз видим точные имена объектов

```bash
printf 'UID=%s\nСлужба=%s\nОшибка=%s\nТаймер=%s\nМонтирование=%s\nКаталог=%s\n' "$LAB_UID" "$LAB_SERVICE" "$LAB_FAIL" "$LAB_TIMER" "$LAB_MOUNT_UNIT" "$LAB_MOUNT_DIR"
```

Пример результата:

```text
UID=1000
Служба=astra-practice-1000.service
Ошибка=astra-practice-1000-failure.service
Таймер=astra-practice-1000-tick.timer
Монтирование=mnt-astra_practice_1000.mount
Каталог=/mnt/astra_practice_1000
```

`printf` выводит форматированную памятку; `%s` заменяется очередной переменной, `\n` переводит строку; флагов нет. Пустые значения, другой UID или чужие имена означают, что очистку продолжать нельзя до восстановления правильных переменных. Значения должны совпадать с вашей работой, а не обязательно с числом 1000 в примере.

### Останавливаем свои задания и монтирование

```bash
sudo systemctl stop "$LAB_TIMER" "$LAB_TICK_SERVICE" "$LAB_SERVICE" "$LAB_FAIL"
cd "$HOME"
sudo systemctl stop "$LAB_MOUNT_UNIT"
mountpoint "$LAB_MOUNT_DIR"
```

Пример результата:

```text
/mnt/astra_practice_1000 is not a mountpoint
```

`systemctl stop` принимает несколько отдельных имён; сначала останавливаются ваш таймер и три службы. `cd` без флагов с аргументом `$HOME` переводит оболочку домой. Затем `stop` останавливает только ваше монтирование. `sudo` даёт административные права операций. `mountpoint` подтверждает отсутствие точного монтирования; ненулевой код сейчас ожидаем.

Команды остановки при успехе ничего не выводят. Если `mountpoint` говорит `is a mountpoint` или `stop` сообщил об ошибке, **не переходите к удалению файлов и каталога**: разберитесь с собственными открытыми файлами и рабочими каталогами. Принудительное размонтирование не применяется.

### Убираем временное включение и сбрасываем только свои состояния отказа

```bash
sudo systemctl disable --runtime "$LAB_SERVICE"
sudo systemctl reset-failed "$LAB_SERVICE" "$LAB_FAIL" "$LAB_TICK_SERVICE" "$LAB_TIMER" "$LAB_MOUNT_UNIT"
```

Пример результата:

```text
Обычно вывода нет: временное включение службы уже было удалено ранее.
```

`disable --runtime` повторно проверяет и удаляет связи включения только вашей службы в `/run`; при уже отключённом юните это нормально. `reset-failed` адресно очищает возможные состояния failed и счётчики только перечисленных учебных объектов. `sudo` разрешает изменение состояния менеджера. Не используйте здесь `reset-failed` без списка имён: это скрыло бы исходные неисправности чужих служб.

### Удаляем только созданные файлы определений и сценарий

```bash
sudo rm -- "/run/systemd/system/$LAB_FAIL.d/override.conf" "/run/systemd/system/$LAB_TICK_SERVICE.d/mount.conf"
sudo rmdir -- "/run/systemd/system/$LAB_FAIL.d" "/run/systemd/system/$LAB_TICK_SERVICE.d"
sudo rm -- "/run/systemd/system/$LAB_SERVICE" "/run/systemd/system/$LAB_FAIL" "/run/systemd/system/$LAB_TICK_SERVICE" "/run/systemd/system/$LAB_TIMER" "/run/systemd/system/$LAB_MOUNT_UNIT" "$LAB_DIR/worker.sh"
sudo rmdir -- "$LAB_DIR" "$LAB_MOUNT_DIR"
sudo systemctl daemon-reload
```

Пример результата:

```text
Вывода нет при успешной очистке.
```

`rm` удаляет только перечисленные обычные файлы; `--` завершает разбор флагов и отделяет пути. Флагов рекурсивного удаления и принудительного игнорирования ошибок нет. `rmdir` удаляет только пустые каталоги; `--` также отделяет имена. `sudo` нужен для объектов root. Последний `daemon-reload` перечитывает определения после удаления.

Если вы пропускали отдельные упражнения, соответствующего файла может не быть: сообщение об отсутствии ожидаемо, но проверяйте каждый путь. Если `rmdir` отказал из-за непустого каталога, изучите оставшееся содержимое вместо рекурсивного удаления. Удаляемая точка монтирования должна быть уже размонтирована по предыдущей проверке. При штатном выполнении временные данные tmpfs исчезли при остановке, а не удаляются этими командами.

### Проверяем состояние после удаления

```bash
systemctl show "$LAB_SERVICE" "$LAB_FAIL" "$LAB_TICK_SERVICE" "$LAB_TIMER" "$LAB_MOUNT_UNIT" -p Id -p LoadState -p ActiveState
systemctl --failed --no-pager
sudo dpkg --audit
systemctl is-active ssh.service
```

Пример результата:

```text
Id=astra-practice-1000.service
LoadState=not-found
ActiveState=inactive

Для остальных четырёх учебных юнитов также: LoadState=not-found, ActiveState=inactive.

  UNIT LOAD ACTIVE SUB DESCRIPTION
0 loaded units listed.
active
```

`systemctl show` читает перечисленные имена; `-p Id` показывает имя, `-p LoadState` — наличие определения, `-p ActiveState` — активность. `not-found` и `inactive` ожидаются для удалённых объектов. `--failed --no-pager` читает список отказов без просмотрщика: сравните его с исходным, а не требуйте пустоты на чужой системе. `sudo dpkg --audit` снова проверяет незавершённые состояния пакетов и при норме ничего не печатает. `is-active ssh.service` подтверждает активность SSH без перезапуска.

В примере поясняющая строка заменяет повтор однотипных свойств, она не является буквальным сообщением systemd. Если SSH назывался иначе, используйте ранее найденное имя только для чтения. Продолжающая работать сессия и активный сервер — полезные признаки, но они не заменяют проверку нового входа отдельным разрешённым сеансом при необходимости.

### При желании удаляем свои исходники и архивы по точным именам

```bash
rm -- "$LAB_WORK/pkg/DEBIAN/control" "$LAB_WORK/pkg/usr/share/$LAB_PACKAGE/note.txt" "$LAB_WORK/${LAB_PACKAGE}_1.0_all.deb" "$LAB_WORK/${LAB_PACKAGE}_1.1_all.deb" "$LAB_WORK/heartbeat-journal.txt"
rmdir -- "$LAB_WORK/pkg/usr/share/$LAB_PACKAGE" "$LAB_WORK/pkg/usr/share" "$LAB_WORK/pkg/usr" "$LAB_WORK/pkg/DEBIAN" "$LAB_WORK/pkg" "$LAB_WORK"
```

Пример результата:

```text
Вывода нет, если все перечисленные файлы и каталоги существовали и удалены.
```

Этот шаг необязателен: рабочую папку можно сохранить для повторного изучения. `rm --` удаляет только перечисленные пользовательские файлы; `rmdir --` удаляет каталоги от вложенных к внешним, только когда они пусты. `--` завершает разбор флагов. `sudo` не используется, потому что это ваши собственные файлы. Если экспорт журнала или какая-либо версия не создавались, сообщение об отсутствии нормально. Не добавляйте рекурсивное удаление для обхода ошибки: проверьте, какой именно файл остался.

## 16. Разбираем типичные затруднения

| Наблюдение | Что это означает и как действовать |
| --- | --- |
| Внутри удалённого терминала команда не найдена. | Проверьте написание и среду. Не устанавливайте большой набор пакетов наугад. Согласуйте отсутствующий инструмент с администратором. |
| `Failed to connect to bus` или systemd не PID 1. | Среда не предоставляет ожидаемый системный менеджер. Нужна полноценная подходящая ВМ. |
| `Permission denied`, запрет sudo или отказ политики безопасности. | Прочитайте полный текст. Не меняйте права системных файлов, метки и режимы защиты ради упражнения. |
| `Unit ... not found` до создания определения. | Нормально при проверке свободных имён. После создания проверьте путь, имя и выполнение перечитывания определений. |
| В `verify` указан неизвестный параметр. | Сопоставьте написание и установленную версию systemd; не запускайте юнит с неразобранным предупреждением. |
| Учебная служба не запускается. | Читайте её состояние, выбранные свойства и её журнал из раздела диагностики. Не перезапускайте SSH. |
| `status` не показывает все записи. | Он даёт только краткий обзор; используйте журнал с фильтром по своему юниту. |
| Одноразовая задача `inactive`, но `Result=success`. | Нормальное завершение oneshot без сохранения активного состояния. |
| Предыдущая загрузка не найдена в журнале. | Сохранённой истории нет; не нужно перезагружать ВМ или менять хранение. |
| После изменения юнита поведение прежнее. | Перечитайте определения; для процесса новое действие обычно нужно проверить новым запуском. Перечитывание systemd само процесс не заменяет. |
| Mount-юнит не загружается из-за имени. | Сверьте имя, полученное из пути, и точное значение `Where=`. |
| Размонтирование сообщает `busy`. | Выйдите из точки монтирования в своих терминалах и закройте свои файлы; не применяйте принудительное размонтирование. |
| После размонтирования исчез учебный текст. | Это ожидаемые свойства tmpfs, а не потеря данных с системного диска. |
| APT ожидает носитель или не находит репозиторий. | Индексы можно не обновлять для локального пакета; не подменяйте источники другой ОС. |
| APT/dpkg сообщает о блокировке. | Дождитесь штатного менеджера пакетов, не удаляйте блокировки. |
| План APT содержит чужие обновления или удаления. | Не применяйте его. Для нашего пакета не требуется изменение других пакетов. |
| После переподключения переменные пусты. | Повторите только блок присваиваний из раздела 4 под той же учётной записью. |
| ВМ перезагрузилась независимо от практики. | Содержимое `/run` и tmpfs исчезнет. Исходники в домашнем каталоге и установленный учебный пакет могут сохраниться; проверьте их отдельно. |

Если SSH-соединение оборвалось, не делайте вывод, что удалённая команда обязательно отменена. Службы, запущенные systemd, обычно продолжают работать независимо от терминала. После повторного входа восстановите переменные и прочитайте состояние своих объектов. Диагностика локального SSH-клиента описана в отдельной инструкции подключения.

## 17. Самостоятельная проверка понимания

Ответьте без изменения системных настроек:

1. Назовите стадии от прошивки до появления SSH. Какие из них можно исследовать в уже работающей ВМ?
2. Покажите версию ядра и объясните, почему она не равна версии Astra Linux.
3. Найдите PID 1 и target по умолчанию. Почему не нужно переключать target в SSH-практике?
4. Чем активная служба отличается от включённой? Какое наблюдение в вашей работе это доказало?
5. Для чего нужно перечитывание определений systemd? Почему оно не заменяет запуск приложения?
6. Найдите в журнале последнее сообщение heartbeat и поясните каждый использованный фильтр.
7. Как отличить старую запись об отказе от текущего исправного состояния?
8. Почему синтаксически корректная служба с программой `false` завершилась ошибкой?
9. Объясните, зачем в дополнении сначала очищался `ExecStart`.
10. Почему таймер активен между срабатываниями, а его oneshot-служба может быть неактивной?
11. Чем зависимость порядка отличается от требования монтирования?
12. Покажите имя своей точки монтирования и соответствующего mount-юнита. Почему нельзя произвольно назвать такой юнит?
13. Почему tmpfs не требует форматировать диск и почему его данные нельзя считать постоянными?
14. Какие ограничения мы назначили tmpfs и какое назначение у каждого?
15. Что можно узнать из списка модулей? Почему нулевой счётчик использования не является разрешением выгрузить драйвер?
16. Какие параметры сделали команду modprobe диагностической?
17. Чем индекс APT отличается от установленного пакета? Что менялось при обновлении индексов?
18. Почему содержимое пакета проверялось до установки и зачем архиву назначались владельцы root/root?
19. Какие свидетельства подтвердили переход учебного пакета с 1.0 на 1.1?
20. Какие проверки подтвердили удаление только ваших объектов и сохранение работоспособности SSH?

Для повторения применяйте только уже разобранные команды чтения с собственными именами. Не проверяйте ответы выключением ВМ, выгрузкой драйвера или остановкой инфраструктурной службы.
