# Модуль 1. Установка и обновление пакетов из локального репозитория

Эта практика предназначена для Astra Linux Special Edition 1.7. Работа выполняется в Bash на удалённой учебной машине, к которой вы уже подключились по SSH. Вводите команды по порядку. Многострочный блок копируйте целиком, включая завершающую строку `EOF`, если она есть. При ошибке сначала разберитесь с её причиной, затем продолжайте.

Мы подготовим обновление учебного приложения, перенесём его вместе с зависимостью в другой каталог, подключим этот каталог к APT и установим обновление. Приложение состоит из текстового файла: оно не открывает порты, не создаёт службы и не изменяет настройки SSH. Это позволяет изучить процесс обновления без замены действующего критического сервиса.

Для основной практики достаточно одной ВМ. Каталоги «шлюз» и «входящие файлы сервера» моделируют две машины. Интернет для этого варианта не нужен. В конце отдельно разобрана работа с настоящим шлюзом: получение пакетов из доверенного репозитория и перенос по SSH. Копирование между каталогами одной ВМ само по себе не создаёт сетевую изоляцию.

Примеры результатов условные. Язык сообщений, размеры файлов и версии системных программ могут отличаться. В примерах UID пользователя равен `1000`; команды сами подставят ваш UID.

## 1. Что такое пакеты, пакетные менеджеры и репозитории

### 1.1. Зачем нужен пакет

Программа обычно состоит из нескольких файлов: исполняемого файла, библиотек, документации, настроек. Установка простым копированием неудобна: трудно понять, какие файлы относятся к программе и что нужно удалить при обновлении.

Пакет `.deb` — архив с файлами программы и описанием правил установки. В описании указаны имя, версия, архитектура и зависимости. Иногда пакет содержит сценарии, выполняемые при установке и удалении. Поэтому установка неизвестного `.deb` с правами администратора означает доверие его содержимому.

Зависимость — другой пакет, необходимый приложению. Например, приложение может требовать библиотеку определённой версии. Пакет может зависеть от нескольких пакетов, а каждый из них — от следующих. Получается цепочка зависимостей.

### 1.2. Чем отличаются dpkg, APT и apt-get

| Инструмент | Для чего нужен | Что нужно учитывать |
| --- | --- | --- |
| `dpkg` | Устанавливает и удаляет конкретные `.deb`, ведёт базу установленных пакетов | Сам не скачивает недостающие зависимости из репозиториев |
| `dpkg-deb` | Собирает и исследует архивы `.deb` | Сборка архива ещё не устанавливает пакет |
| `apt` | Позволяет искать, устанавливать и обновлять пакеты через APT | Удобен при ручной работе в терминале |
| `apt-get` | Выполняет операции APT с устойчивым интерфейсом команд | В практике используется для явных, повторяемых команд |
| `apt-cache` | Показывает сведения из индексов APT | Не устанавливает программы |
| `dpkg-scanpackages` | Создаёт индекс `Packages` для каталога с `.deb` | Входит в пакет `dpkg-dev` |
| `apt-ftparchive` | Также умеет создавать индекс репозитория | Входит в пакет `apt-utils`; может заменить `dpkg-scanpackages` |

APT — система управления пакетами; `apt`, `apt-get` и `apt-cache` — её инструменты. Устанавливать другой пакетный менеджер, например `pacman`, на Astra Linux для этой работы не нужно. `apt` и `dpkg` входят в обычную установленную систему. Если они повреждены или отсутствуют, это отдельная задача восстановления ОС, а не повод скачивать случайные исполняемые файлы.

### 1.3. Что такое репозиторий

Репозиторий — источник пакетов с индексом. Индекс `Packages` содержит имена пакетов, версии, зависимости, пути к `.deb` и контрольные суммы. APT читает индекс и определяет, что можно установить.

Репозиторий может находиться на веб-сервере или в локальном каталоге. Для каталога используется адрес `file:///...`. Такой адрес означает путь на той машине, где запущен APT. В SSH-сеансе это путь на удалённой Astra Linux, а не на вашем ноутбуке.

Подключение репозитория означает добавление описания источника. Оно не устанавливает находящиеся в нём программы автоматически. После подключения нужно обновить индексы, проверить план и явно установить выбранный пакет.

### 1.4. Почему update и upgrade — разные операции

| Операция | Что меняется |
| --- | --- |
| `update` | APT получает сведения о доступных пакетах |
| `install` | APT устанавливает выбранный пакет или обновляет его до выбранной версии |
| `upgrade` | APT пытается обновить множество уже установленных пакетов |
| `dist-upgrade` | Возможны более широкие изменения зависимостей, включая удаления |

В этой практике системное обновление не выполняется. Обновляется только наше учебное приложение. Не добавляйте `upgrade`, `dist-upgrade` или `autoremove` к приведённым командам.

## 2. Подготовка удалённой Astra Linux

### 2.1. Убедитесь, на какой машине вы работаете

```bash
whoami
hostname
cat /etc/os-release
dpkg --print-architecture
```

**Пояснение.** `whoami` выводит имя текущего пользователя; `hostname` — имя узла. У этих команд здесь нет флагов. `cat` выводит содержимое указанного файла; `/etc/os-release` содержит сведения об ОС. `dpkg --print-architecture` показывает основную архитектуру пакетов; `--print-architecture` не меняет настройки.

**Пример результата:**

```text
student
astra-lab
PRETTY_NAME="Astra Linux"
NAME="Astra Linux"
...
amd64
```

**Что должно получиться.** Вы узнали пользователя и имя удалённой ВМ. В Astra Linux сведения в `os-release` могут не отражать полный номер оперативного обновления.

```bash
cat /etc/astra_version
```

`cat` читает файл; `/etc/astra_version` содержит сведения о версии Astra Linux. Флагов нет.

**Пример результата:**

```text
1.7.x
```

Точное значение зависит от установленного обновления. Если файл отсутствует, уточните версию образа у администратора. Не подключайте репозитории другой ОС на основании одного похожего номера версии.

### 2.2. Проверьте права и состояние пакетной базы

```bash
sudo -v
sudo dpkg --audit
```

`sudo` выполняет разрешённую команду с повышенными правами. `-v` проверяет возможность использовать `sudo` и обновляет срок действия подтверждённых полномочий. Может потребоваться пароль вашей учётной записи; символы при вводе не показываются. Это не пароль другого сервера.

`dpkg --audit` проверяет базу на частично установленные пакеты и другие несогласованности. `--audit` ничего не устанавливает и не исправляет. `sudo` обеспечивает доступ к нужным данным.

**Ожидаемый результат:** после возможного запроса пароля команды завершаются без текста. Если `dpkg` перечислил проблемные пакеты, остановитесь и покажите вывод администратору. Не запускайте автоматическое исправление зависимостей на общей машине.

### 2.3. Проверьте наличие инструментов

```bash
command -v apt apt-get apt-cache dpkg dpkg-deb
command -v dpkg-scanpackages
command -v apt-ftparchive
```

`command` — встроенный инструмент Bash; `-v` просит вывести путь к программе. Здесь ничего не устанавливается.

**Пример результата:**

```text
/usr/bin/apt
/usr/bin/apt-get
/usr/bin/apt-cache
/usr/bin/dpkg
/usr/bin/dpkg-deb
/usr/bin/dpkg-scanpackages
/usr/bin/apt-ftparchive
```

Для создания индекса нужен хотя бы один из последних двух инструментов. Если `dpkg-scanpackages` отсутствует, но найден `apt-ftparchive`, используйте его варианты команд, приведённые ниже. Если отсутствуют оба, индекс нужно подготовить на шлюзе с этими инструментами и перенести вместе с пакетами. При полностью отсутствующих инструментах не продолжайте основной вариант до подготовки шлюза.

### 2.4. Как устанавливаются недостающие инструменты на настоящем шлюзе

Этот подраздел относится **только к отдельному учебному шлюзу**, на котором разрешена установка ПО и уже настроены доверенные репозитории нужной Astra Linux. На удалённом целевом сервере выполнять эти команды ради упражнения не требуется.

```bash
sudo apt-get update
sudo apt-get --simulate --no-remove --no-install-recommends install dpkg-dev
```

`apt-get update` загружает индексы из настроенных источников. `--simulate` показывает план без установки. `--no-remove` запрещает операцию, требующую удаления пакетов. `--no-install-recommends` исключает рекомендуемые пакеты, сохраняя обязательные зависимости. `install dpkg-dev` выбирает пакет с `dpkg-scanpackages`.

**Пример сокращённого результата:**

```text
Reading package lists... Done
The following NEW packages will be installed:
  dpkg-dev ...
0 upgraded, ... newly installed, 0 to remove ...
```

Количество зависимостей определяется состоянием шлюза. Если план согласован для этого шлюза, установка выглядит так:

```bash
sudo apt-get --no-remove --no-install-recommends install dpkg-dev
```

Значения всех параметров те же, но `--simulate` убран: теперь установка настоящая. Прочитайте план перед ответом на запрос подтверждения.

**Пример результата:**

```text
Setting up dpkg-dev (... ) ...
```

Если шлюз не имеет доступа к доверенному репозиторию, сначала нужен установочный носитель или подготовленные администратором пакеты. Эта команда сама по себе не создаёт доступ в Интернет. Для `apt-ftparchive` аналогичным источником инструмента служит пакет `apt-utils`.

### 2.5. Посмотрите, откуда APT уже получает пакеты

```bash
cat /etc/apt/sources.list
ls -l /etc/apt/sources.list.d/
apt-cache policy
```

`cat` читает основной список источников. `ls` перечисляет содержимое каталога; `-l` показывает подробности, включая права и владельцев. `apt-cache policy` показывает источники и приоритеты, известные по существующим индексам. `policy` — действие, а не флаг. Интернет эти команды не опрашивают.

**Пример сокращённого результата:**

```text
deb ...
total ...
Package files:
 100 /var/lib/dpkg/status
     release a=now
 ...
```

Строки будут зависеть от вашей ВМ. Не заменяйте их примерами из Интернета: в Astra Linux важны редакция, выпуск, оперативное обновление и разрешённый набор репозиториев. Пакеты Debian, Ubuntu и Astra Linux нельзя считать взаимозаменяемыми только потому, что у них расширение `.deb`.

## 3. Как устроено задание

Представим, что в изолированной сети необходимо обновить важное приложение. На сервере нет Интернета, но на шлюзе можно подготовить комплект пакетов. Чтобы изучить действия без риска для SSH, заменим реальный сервис учебным пакетом.

| Объект | Содержание | Роль |
| --- | --- | --- |
| `point1-app-UID`, версия `1.0` | Текстовый файл приложения | Имитирует прежнюю установленную версию |
| `point1-app-UID`, версия `1.1` | Обновлённый текстовый файл | Имитирует исправленную версию |
| `point1-data-UID`, версия `1.0` | Дополнительный текстовый файл | Обязательная зависимость новой версии приложения |

Никакой уязвимости в учебных файлах нет: названия «исправление» и «обновление безопасности» описывают модель процесса. Установка настоящего исправления критического сервиса может запустить его сценарии и перезапустить сервис; здесь такой пакет не используется.

Мы добавим отдельный файл в `/etc/apt/sources.list.d/`. Основной `/etc/apt/sources.list` редактировать не понадобится. Для команд практики зададим отдельные каталоги индексов и единственный источник `file:`. Это ограничивает источники конкретных вызовов APT, но не запрещает сетевые подключения всей ОС.

## 4. Создание рабочих каталогов

### 4.1. Задайте имена объектов

```bash
LAB_UID="$(id -u)"
LAB_ID="point1-$LAB_UID"
LAB_APP="point1-app-$LAB_UID"
LAB_DATA="point1-data-$LAB_UID"
LAB_WORK="$HOME/$LAB_ID"
LAB_GATEWAY="$LAB_WORK/gateway"
LAB_BUNDLE="$LAB_WORK/bundle"
LAB_INCOMING="$LAB_WORK/incoming"
LAB_ROOT="/var/lib/$LAB_ID"
LAB_SOURCE="/etc/apt/sources.list.d/$LAB_ID.list"
printf '%s\n' "$LAB_APP" "$LAB_DATA" "$LAB_WORK" "$LAB_ROOT" "$LAB_SOURCE"
```

**Пояснение.** `id -u` выводит числовой идентификатор пользователя; `-u` выбирает именно UID. Конструкция `$(...)` подставляет результат команды. Присваивание `ИМЯ="значение"` создаёт переменную Bash; вокруг `=` пробелов нет. `$HOME` содержит домашний каталог текущего пользователя; его значение не изменяется. Остальные переменные обозначают только объекты этой практики.

`printf` выводит значения. Формат `%s` означает строку, `\n` — переход на новую строку. Двойные кавычки сохраняют путь одним аргументом. Эти обозначения — работающие переменные, вручную заменять их в последующих командах не нужно.

**Пример результата:**

```text
point1-app-1000
point1-data-1000
/home/student/point1-1000
/var/lib/point1-1000
/etc/apt/sources.list.d/point1-1000.list
```

Выполняйте основную практику в одном SSH-сеансе Bash. После переподключения переменные нужно задать заново этим же блоком; каталоги и пакеты при разрыве SSH не исчезают. Не выполняйте повторно создание и установку старой версии поверх уже завершённой работы.

### 4.2. Проверьте отсутствие объектов от предыдущего запуска

```bash
ls -ld "$LAB_WORK" "$LAB_ROOT" "$LAB_SOURCE"
dpkg-query -W -f='${binary:Package}: ${Status}\n' "$LAB_APP" "$LAB_DATA"
```

`ls -l` показывает подробности; `-d` показывает сам каталог, а не его содержимое. `dpkg-query` читает базу пакетов; `-W` запрашивает сведения о названных пакетах; `-f` задаёт формат. `${binary:Package}` и `${Status}` здесь являются полями `dpkg-query`. Одинарные кавычки предотвращают их подстановку оболочкой.

**Ожидаемый результат при первом запуске:** сообщения `No such file or directory` и `no packages found matching ...`. Здесь они ожидаемы: объектов пока нет. Если пути или пакеты уже существуют, сначала завершите и очистите предыдущую практику по разделу 12; не перезаписывайте их.

### 4.3. Создайте каталоги

```bash
mkdir "$LAB_WORK"
mkdir -p "$LAB_GATEWAY" "$LAB_BUNDLE" "$LAB_INCOMING" "$LAB_WORK/build" "$LAB_WORK/gateway-lists/partial" "$LAB_WORK/empty-sources"
sudo mkdir "$LAB_ROOT"
sudo chmod 0755 "$LAB_ROOT"
sudo install -d -m 0755 "$LAB_ROOT/repo" "$LAB_ROOT/lists/partial" "$LAB_ROOT/archives/partial" "$LAB_ROOT/empty-sources"
```

`mkdir` создаёт каталог. Первая команда без `-p` обнаружит повторный запуск: существующий каталог вызовет ошибку. `mkdir -p` создаёт недостающие промежуточные каталоги и не считает существующий каталог ошибкой.

`sudo mkdir` создаёт отдельный системный каталог от имени администратора. `chmod 0755` задаёт владельцу чтение, запись и проход, остальным — чтение и проход. `install` здесь создаёт каталоги: `-d` выбирает этот режим, `-m 0755` задаёт права. Владельцем созданных через `sudo` каталогов будет root. Права нужны в том числе пользователю `_apt`, который может читать репозиторий при загрузке пакетов.

**Ожидаемый результат:** команды завершаются без текста. Если получена ошибка, не переходите к сборке. Не заменяйте права на `777`.

## 5. Подготовка учебных пакетов на моделируемом шлюзе

### 5.1. Соберите прежнюю версию приложения

```bash
mkdir -p "$LAB_WORK/build/app-old/DEBIAN" "$LAB_WORK/build/app-old/usr/share/$LAB_ID"
cat > "$LAB_WORK/build/app-old/DEBIAN/control" <<EOF
Package: $LAB_APP
Version: 1.0
Section: misc
Priority: optional
Architecture: all
Maintainer: Training <training@example.invalid>
Description: Harmless offline repository training application
EOF
printf '%s\n' 'Application version 1.0: initial training state.' > "$LAB_WORK/build/app-old/usr/share/$LAB_ID/app.txt"
dpkg-deb --root-owner-group --build "$LAB_WORK/build/app-old" "$LAB_GATEWAY/${LAB_APP}_1.0_all.deb"
```

`mkdir -p` создаёт служебный каталог пакета `DEBIAN` и каталог будущего файла. Путь внутри дерева `usr/share/...` после установки станет `/usr/share/...` на сервере.

`cat > файл <<EOF` записывает следующие строки в файл до отдельной строки `EOF`. `>` направляет вывод в файл и перезаписывает его. Незакавыченный `EOF` позволяет подставить переменную `$LAB_APP`. Сам маркер `EOF` в файл не попадает. В завершающей строке не добавляйте пробелы или другие слова.

Поля `control` означают:

| Поле | Значение |
| --- | --- |
| `Package` | Имя пакета, которое затем используется в APT |
| `Version` | Версия пакета |
| `Section` | Тематическая категория |
| `Priority: optional` | Необязательный пакет |
| `Architecture: all` | Нет машинного кода, пакет не привязан к процессорной архитектуре |
| `Maintainer` | Контакт автора пакета; здесь вымышленный адрес в зарезервированном домене |
| `Description` | Короткое описание |

`printf` записывает строку в `app.txt`. `dpkg-deb` собирает архив: `--build` выбирает сборку, первый путь указывает дерево пакета, второй — выходной `.deb`. `--root-owner-group` записывает владельца и группу файлов архива как root, не требуя сборки через `sudo`. Этот параметр поддерживается штатным поколением dpkg в Astra Linux 1.7; при неизвестном параметре остановитесь и проверьте окружение.

**Пример результата:**

```text
dpkg-deb: building package 'point1-app-1000' in '.../point1-app-1000_1.0_all.deb'.
```

Файл создан, но приложение пока не установлено.

### 5.2. Соберите пакет зависимости

```bash
mkdir -p "$LAB_WORK/build/data/DEBIAN" "$LAB_WORK/build/data/usr/share/$LAB_ID"
cat > "$LAB_WORK/build/data/DEBIAN/control" <<EOF
Package: $LAB_DATA
Version: 1.0
Section: misc
Priority: optional
Architecture: all
Maintainer: Training <training@example.invalid>
Description: Harmless data dependency for offline repository training
EOF
printf '%s\n' 'Required training data version 1.0.' > "$LAB_WORK/build/data/usr/share/$LAB_ID/data.txt"
dpkg-deb --root-owner-group --build "$LAB_WORK/build/data" "$LAB_GATEWAY/${LAB_DATA}_1.0_all.deb"
```

`mkdir -p` создаёт дерево пакета. `cat`, `>`, `<<EOF` формируют описание с подстановкой имени. `printf '%s\n'` записывает строку данных. `dpkg-deb --build` создаёт архив из дерева `data`; `--root-owner-group` назначает root владельцем файлов в архиве. Все поля описания имеют смысл, разобранный выше.

**Пример результата:**

```text
dpkg-deb: building package 'point1-data-1000' in '.../point1-data-1000_1.0_all.deb'.
```

### 5.3. Соберите исправленную версию приложения

```bash
mkdir -p "$LAB_WORK/build/app-new/DEBIAN" "$LAB_WORK/build/app-new/usr/share/$LAB_ID"
cat > "$LAB_WORK/build/app-new/DEBIAN/control" <<EOF
Package: $LAB_APP
Version: 1.1
Section: misc
Priority: optional
Architecture: all
Depends: $LAB_DATA (= 1.0)
Maintainer: Training <training@example.invalid>
Description: Updated harmless offline repository training application
EOF
printf '%s\n' 'Application version 1.1: training update applied.' > "$LAB_WORK/build/app-new/usr/share/$LAB_ID/app.txt"
dpkg-deb --root-owner-group --build "$LAB_WORK/build/app-new" "$LAB_GATEWAY/${LAB_APP}_1.1_all.deb"
```

Команды создают дерево, описание, текстовый файл и архив новой версии. `mkdir -p`, `cat`, перенаправление `>`, ввод `<<EOF`, формат `printf`, `--build` и `--root-owner-group` работают так же, как при сборке предыдущих пакетов.

Новое поле `Depends` задаёт обязательную зависимость. Запись `имя (= 1.0)` требует ровно версию `1.0` пакета данных. APT должен установить её автоматически вместе с версией `1.1` приложения.

**Пример результата:**

```text
dpkg-deb: building package 'point1-app-1000' in '.../point1-app-1000_1.1_all.deb'.
```

### 5.4. Проверьте содержимое архивов

```bash
for deb in "$LAB_GATEWAY/"*.deb; do
    dpkg-deb --info "$deb"
    dpkg-deb --contents "$deb"
done
```

`for ... in ...; do ... done` повторяет команды для каждого файла. `*.deb` означает все имена, заканчивающиеся на `.deb`; раскрытие выполняет Bash. Переменная `deb` получает путь очередного файла.

`dpkg-deb --info` показывает описание и список управляющих файлов; `--contents` — файлы устанавливаемого содержимого. Эти параметры только читают архивы.

**Пример сокращённого результата для новой версии:**

```text
new Debian package, version 2.0.
... control
 Package: point1-app-1000
 Version: 1.1
 Depends: point1-data-1000 (= 1.0)
...
drwxr-xr-x root/root ... ./usr/share/point1-1000/
-rw-r--r-- root/root ... ./usr/share/point1-1000/app.txt
```

Проверьте все три архива. В управляющей части должен быть только `control`, без `preinst`, `postinst`, `prerm`, `postrm` и `triggers`. Полезные файлы находятся только в `/usr/share/point1-ваш_UID/`. Это важно перед установкой с правами root.

## 6. Создание исходного репозитория и получение комплекта обновления

### 6.1. Создайте индекс на моделируемом шлюзе

```bash
cd "$LAB_GATEWAY"
dpkg-scanpackages --multiversion . /dev/null > Packages
```

`cd` меняет текущий каталог. `dpkg-scanpackages` исследует `.deb` и печатает индекс. `--multiversion` включает обе версии приложения; без этого параметра обычно останется только наиболее новая. Точка `.` задаёт текущий каталог, поэтому пути `Filename` будут относительными. `/dev/null` используется вместо дополнительной таблицы переопределения свойств пакетов. `>` сохраняет индекс в `Packages`.

**Пример результата:**

```text
dpkg-scanpackages: warning: Packages in archive but missing from override file:
dpkg-scanpackages: warning:   point1-app-1000 point1-data-1000
dpkg-scanpackages: info: Wrote 3 entries to output Packages file.
```

Предупреждение о missing override file в этом примере означает отсутствие дополнительной таблицы переопределений; индекс всё равно создан. Ориентируйтесь на итог `Wrote 3 entries` и проверку содержимого индекса.

Если используется **apt-ftparchive**, вместо команды сканирования выполните:

```bash
apt-ftparchive packages . > Packages
```

`apt-ftparchive` создаёт метаданные; действие `packages` выбирает индекс бинарных пакетов; `.` означает текущий каталог; `>` сохраняет результат. Отдельный флаг для нескольких версий здесь не нужен.

**Ожидаемый результат альтернативы:** текста в терминале нет, файл `Packages` создан. Используйте один способ создания индекса, а не оба.

### 6.2. Настройте отдельный APT для шлюза

```bash
printf 'deb [trusted=yes] file://%s ./\n' "$LAB_GATEWAY" > "$LAB_WORK/gateway.list"
cat > "$LAB_WORK/gateway-apt.conf" <<EOF
Dir::Etc::sourcelist "$LAB_WORK/gateway.list";
Dir::Etc::sourceparts "$LAB_WORK/empty-sources";
Dir::State::lists "$LAB_WORK/gateway-lists";
Dir::Cache::pkgcache "";
Dir::Cache::srcpkgcache "";
Acquire::Languages "none";
EOF
apt-get -c "$LAB_WORK/gateway-apt.conf" update
```

`printf` формирует строку источника; `%s` заменяется абсолютным путём. Так как путь начинается с `/`, после `file://` получается `file:///`. Значения `deb`, `trusted=yes` и `./` подробно разобраны в разделе 9.

`cat` с `<<EOF` записывает конфигурацию; двойные кавычки и `;` — синтаксис APT. `Dir::Etc::sourcelist` выбирает один список источников. `sourceparts` указывает пустой каталог, исключая системные дополнительные списки из этого вызова. `Dir::State::lists` задаёт отдельное место для индексов. Пустые `pkgcache` и `srcpkgcache` отключают запись общих двоичных кэшей. `Acquire::Languages "none"` исключает загрузку переводов описаний.

`apt-get -c файл update` читает указанный дополнительный конфигурационный файл и обновляет индексы. `-c` означает путь конфигурации. Здесь `sudo` не нужен: все записываемые файлы находятся в вашем рабочем каталоге.

**Пример сокращённого результата:**

```text
Get:1 file:/home/student/point1-1000/gateway ./ InRelease
Ign:1 file:/home/student/point1-1000/gateway ./ InRelease
...
Get:3 file:/home/student/point1-1000/gateway ./ Packages [... B]
Reading package lists... Done
```

Для простого локального репозитория без `Release` возможны строки `Ign`. Итогом должно быть успешное чтение `Packages`. Ни одного источника `http:` или `https:` в этом вызове быть не должно.

### 6.3. Скачайте обновление и его зависимость

```bash
cd "$LAB_BUNDLE"
apt-get -c "$LAB_WORK/gateway-apt.conf" download "$LAB_APP=1.1" "$LAB_DATA=1.0"
ls -lh "$LAB_BUNDLE"
```

`cd` выбирает каталог получения файлов. `apt-get download` получает указанные бинарные пакеты в текущий каталог, не устанавливая их. `-c` использует конфигурацию шлюза. Запись `имя=версия` выбирает точную версию. `ls -l` показывает подробности; `-h` делает размеры удобными для чтения.

**Пример результата:**

```text
Get:1 file:/... point1-app-1000 1.1 [... B]
Get:2 file:/... point1-data-1000 1.0 [... B]
...
point1-app-1000_1.1_all.deb
point1-data-1000_1.0_all.deb
```

Здесь загрузка выполняется из подготовленного `file:`-источника шлюза. `download` не собирает зависимости автоматически: мы явно указали единственную зависимость, которую сами задали в `control`. Для настоящего пакета с большой цепочкой зависимостей используйте способ из раздела 13, учитывающий состояние целевого сервера.

### 6.4. Запишите контрольные суммы

```bash
cd "$LAB_BUNDLE"
sha256sum ./*.deb > SHA256SUMS
cat SHA256SUMS
```

`sha256sum` вычисляет SHA-256 для каждого `.deb`. `./*.deb` выбирает файлы текущего каталога и сохраняет в ведомости относительные имена. `>` записывает ведомость, `cat` показывает её.

**Пример структуры результата:**

```text
<64 шестнадцатеричных символа>  ./point1-app-1000_1.1_all.deb
<64 шестнадцатеричных символа>  ./point1-data-1000_1.0_all.deb
```

В вашем выводе вместо описания будут настоящие суммы. Они позволяют обнаружить повреждение при переносе. Если злоумышленник заменит и пакеты, и ведомость, проверка не установит подлинность: для настоящих обновлений нужны доверенный источник и проверка подписей.

## 7. Перенос комплекта на моделируемый сервер

```bash
cp "$LAB_BUNDLE/"*.deb "$LAB_BUNDLE/SHA256SUMS" "$LAB_INCOMING/"
cd "$LAB_INCOMING"
sha256sum -c SHA256SUMS
```

`cp` копирует два архива и ведомость в каталог приёма. Флагов у `cp` здесь нет; последний аргумент — каталог назначения. `cd` делает его текущим. `sha256sum -c` читает ведомость, заново вычисляет суммы и сравнивает их; `-c` означает проверку.

**Пример результата:**

```text
./point1-app-1000_1.1_all.deb: OK
./point1-data-1000_1.0_all.deb: OK
```

Продолжайте только при двух `OK`. Эта операция моделирует перенос между машинами, сохраняя работу внутри одной удалённой ВМ. Настоящий перенос по SSH разобран отдельно ниже. Не отключайте сеть сервера для доказательства отсутствия Интернета: это может оборвать ваш единственный доступ.

## 8. Установка исходной версии и создание репозитория на сервере

### 8.1. Создайте исходное состояние приложения

```bash
sudo dpkg --install "$LAB_GATEWAY/${LAB_APP}_1.0_all.deb"
dpkg-query -W -f='${binary:Package} ${Version} ${Status}\n' "$LAB_APP"
cat "/usr/share/$LAB_ID/app.txt"
```

`dpkg --install` устанавливает конкретный архив. `--install` не скачивает зависимости; у нашей версии `1.0` их нет. `sudo` нужен для записи в системный каталог и пакетную базу. Это единственная предварительная установка напрямую через `dpkg`; обновление будет выполнено через APT.

`dpkg-query -W` читает сведения; `-f` задаёт формат с именем, версией и состоянием. `cat` читает установленный файл.

**Пример результата:**

```text
Selecting previously unselected package point1-app-1000.
Unpacking point1-app-1000 (1.0) ...
Setting up point1-app-1000 (1.0) ...
point1-app-1000 1.0 install ok installed
Application version 1.0: initial training state.
```

### 8.2. Скопируйте принятые пакеты в каталог репозитория

```bash
sudo install -m 0644 "$LAB_INCOMING/"*.deb "$LAB_ROOT/repo/"
ls -l "$LAB_ROOT/repo/"
```

`install` без `-d` копирует файлы. `-m 0644` назначает владельцу чтение и запись, остальным — чтение. При вызове через `sudo` новые файлы принадлежат root. Это защищает уже подключённый репозиторий от случайной подмены обычным пользователем. `ls -l` показывает права и владельцев.

**Пример результата:**

```text
-rw-r--r-- 1 root root ... point1-app-1000_1.1_all.deb
-rw-r--r-- 1 root root ... point1-data-1000_1.0_all.deb
```

### 8.3. Создайте индекс целевого репозитория

```bash
cd "$LAB_ROOT/repo"
dpkg-scanpackages . /dev/null > "$LAB_WORK/Packages"
gzip -c "$LAB_WORK/Packages" > "$LAB_WORK/Packages.gz"
sudo install -m 0644 "$LAB_WORK/Packages" "$LAB_WORK/Packages.gz" "$LAB_ROOT/repo/"
```

`cd` выбирает корень репозитория. `dpkg-scanpackages . /dev/null` создаёт индекс относительных путей. Здесь по одной версии каждого пакета, поэтому `--multiversion` не нужен. `>` сохраняет результат в доступном вам рабочем каталоге: обычный пользователь не должен записывать в каталог root.

`gzip -c` сжимает данные и отправляет результат на стандартный вывод, сохраняя исходный файл. Перенаправление записывает `Packages.gz`. Для `file:` достаточно несжатого `Packages`; сжатый вариант также полезен для APT. `sudo install -m 0644` переносит оба индекса в защищённый каталог с правами чтения для всех.

**Пример результата:**

```text
dpkg-scanpackages: info: Wrote 2 entries to output Packages file.
```

Если используется **apt-ftparchive**, замените только строку сканирования на:

```bash
apt-ftparchive packages . > "$LAB_WORK/Packages"
```

`packages` создаёт индекс бинарных пакетов текущего каталога `.`; `>` сохраняет его в рабочий файл. **Ожидаемый результат:** команда завершается без текста. Затем выполните приведённые выше команды `gzip` и `install`.

### 8.4. Проверьте имена, зависимости и пути в индексе

```bash
grep -E '^(Package|Version|Depends|Filename|SHA256):' "$LAB_ROOT/repo/Packages"
```

`grep` выбирает строки. `-E` включает расширенные регулярные выражения. `^` означает начало строки, скобки объединяют варианты, `|` внутри шаблона означает «или». Здесь этот символ находится в кавычках и не является конвейером оболочки.

**Пример сокращённого результата:**

```text
Package: point1-app-1000
Version: 1.1
Depends: point1-data-1000 (= 1.0)
Filename: ./point1-app-1000_1.1_all.deb
SHA256: ...
Package: point1-data-1000
Version: 1.0
Filename: ./point1-data-1000_1.0_all.deb
SHA256: ...
```

Порядок полей может отличаться. `Filename` должен указывать на существующие файлы относительно корня репозитория, а не на домашний каталог шлюза.

## 9. Подключение репозитория к APT

### 9.1. Создайте отдельный список источников

```bash
printf 'deb [trusted=yes] file://%s ./\n' "$LAB_ROOT/repo" | sudo tee "$LAB_SOURCE"
```

`printf` формирует строку; `%s` подставляет путь, `\n` завершает строку. `|` передаёт вывод следующей программе. `sudo tee` записывает полученный текст в файл от имени root и одновременно показывает его в терминале. Без `-a` файл перезаписывается: поэтому ранее проверялось отсутствие именно нашего файла.

**Пример результата:**

```text
deb [trusted=yes] file:///var/lib/point1-1000/repo ./
```

| Часть строки | Что означает |
| --- | --- |
| `deb` | Источник готовых бинарных пакетов |
| `[trusted=yes]` | APT считает этот источник доверенным без обычной проверки подписи репозитория |
| `file:///var/lib/point1-1000/repo` | Каталог на целевом сервере |
| `./` | Плоский репозиторий: индекс находится прямо в указанном каталоге |

В строке нет названия дистрибутива и компонентов вроде `main`, потому что используется плоский каталог. `trusted=yes` относится только к этой записи. Он не доказывает безопасность пакетов. Здесь это осознанное упрощение для собственных проверенных текстовых пакетов; боевой репозиторий должен иметь проверяемую подпись и управляемые права доступа.

Не используйте конструкцию `sudo echo ... > /etc/...`: перенаправление выполняет обычная оболочка до запуска команды и прав `sudo` для записи может не хватить. `tee` решает эту задачу явно.

### 9.2. Ограничьте источники и каталоги APT для практики

```bash
cat > "$LAB_WORK/target-apt.conf" <<EOF
Dir::Etc::sourcelist "$LAB_SOURCE";
Dir::Etc::sourceparts "$LAB_ROOT/empty-sources";
Dir::State::lists "$LAB_ROOT/lists";
Dir::Cache::archives "$LAB_ROOT/archives";
Dir::Cache::pkgcache "";
Dir::Cache::srcpkgcache "";
Acquire::Languages "none";
EOF
cat "$LAB_SOURCE"
cat "$LAB_WORK/target-apt.conf"
```

Первый `cat` записывает конфигурацию до `EOF`; два следующих читают готовые файлы. `sourcelist` выбирает только нашу запись, `sourceparts` — пустой каталог дополнительных источников. `lists` хранит индексы отдельно от системных, `archives` — полученные APT архивы отдельно от системного кэша. Пустые `pkgcache` и `srcpkgcache` отключают общие двоичные кэши; `Acquire::Languages` отключает получение переводов.

**Пример результата:** сначала строка `deb ... file:///... ./`, затем параметры с вашими путями. Команды ничего не устанавливают.

Файл `target-apt.conf` применяется только при явном `-c`. Он не заменяет общую конфигурацию APT. База установленных пакетов остаётся настоящей: установка и удаление учебных пакетов реальны. Не путайте изоляцию источников с контейнером или отдельной ОС.

### 9.3. Обновите индексы только локального источника

```bash
sudo apt-get -c "$LAB_WORK/target-apt.conf" update
```

`sudo` разрешает запись в выделенные системные каталоги. `apt-get` запускает APT. `-c` читает нашу конфигурацию; `update` получает индексы, а не устанавливает пакеты.

**Пример сокращённого результата:**

```text
Get:1 file:/var/lib/point1-1000/repo ./ InRelease
Ign:1 file:/var/lib/point1-1000/repo ./ InRelease
...
Get:3 file:/var/lib/point1-1000/repo ./ Packages [... B]
Reading package lists... Done
```

Строки `Ign` для отсутствующих `InRelease` и `Release` допустимы в этой учебной схеме с `trusted=yes`. Не должно остаться итоговой ошибки чтения `Packages`. Все источники этого вызова должны начинаться с `file:`. Существующие Интернет-источники не требуется удалять или отключать.

## 10. Проверка плана и установка обновления

### 10.1. Посмотрите установленную и доступную версии

```bash
apt-cache -c "$LAB_WORK/target-apt.conf" policy "$LAB_APP" "$LAB_DATA"
```

`apt-cache` читает сведения APT. `-c` выбирает ту же конфигурацию, что использовалась при обновлении индексов. `policy` показывает версии и источники. Далее перечислены два конкретных пакета.

**Пример сокращённого результата:**

```text
point1-app-1000:
  Installed: 1.0
  Candidate: 1.1
  Version table:
     1.1 500
        500 file:/var/lib/point1-1000/repo ./ Packages
 *** 1.0 100
        100 /var/lib/dpkg/status
point1-data-1000:
  Installed: (none)
  Candidate: 1.0
```

`Installed` — уже установленная версия, `Candidate` — выбранная APT версия. Системные правила приоритетов могут повлиять на результат; при отличиях сначала разберите их, не меняйте общие приоритеты.

### 10.2. Выполните симуляцию

```bash
sudo apt-get -c "$LAB_WORK/target-apt.conf" --simulate --no-remove --no-install-recommends install "$LAB_APP=1.1"
```

`--simulate` показывает план без установки. `--no-remove` прерывает операцию, если она требует удаления пакетов. `--no-install-recommends` не добавляет рекомендованные пакеты. `install` устанавливает или обновляет названный пакет; `=1.1` фиксирует версию. `-c` сохраняет единственный локальный источник. `sudo` позволяет симуляции читать настройки с теми же правами, что и будущая установка.

**Пример сокращённого результата:**

```text
The following additional packages will be installed:
  point1-data-1000
The following NEW packages will be installed:
  point1-data-1000
The following packages will be upgraded:
  point1-app-1000
1 upgraded, 1 newly installed, 0 to remove ...
Inst point1-data-1000 (1.0 ...)
Inst point1-app-1000 [1.0] (1.1 ...)
Conf point1-data-1000 (1.0 ...)
Conf point1-app-1000 (1.1 ...)
```

В плане допустимы только наши два пакета. Число пакетов, оставленных без обновления, может зависеть от системы. Если APT предлагает менять SSH, ядро, библиотеки или другие пакеты, не подтверждайте установку и проверьте имена и конфигурацию. Симуляция не заменяет контроль следующего плана: состояние машины может измениться между командами.

### 10.3. Установите обновление из локального репозитория

```bash
sudo apt-get -c "$LAB_WORK/target-apt.conf" --no-remove --no-install-recommends install "$LAB_APP=1.1"
```

Команда повторяет проверенный план, но без `--simulate`: теперь изменения выполняются. Все остальные параметры сохраняют прежний смысл. Параметр автоматического подтверждения не используется. Прочитайте план и подтвердите его только при ожидаемых двух пакетах.

**Пример сокращённого результата:**

```text
1 upgraded, 1 newly installed, 0 to remove ...
Do you want to continue? [Y/n]
Get:1 file:/var/lib/point1-1000/repo ./ point1-data-1000 1.0 [... B]
Get:2 file:/var/lib/point1-1000/repo ./ point1-app-1000 1.1 [... B]
Unpacking point1-data-1000 (1.0) ...
Unpacking point1-app-1000 (1.1) over (1.0) ...
Setting up point1-data-1000 (1.0) ...
Setting up point1-app-1000 (1.1) ...
```

В локализованном терминале приглашение подтверждения будет переведено. APT сам установил зависимость, хотя в `install` названо только приложение. Источник `file:` показывает чтение с диска сервера. Отсутствие сетевого трафика всей машины этим не доказывается, но для получения пакетов данной команды Интернет не требуется.

Не добавляйте `--no-download` для первого обращения к `file:`-репозиторию: APT всё равно должен получить архивы из источника. Этот параметр запрещает стадию получения пакетов, а не только HTTP-доступ.

### 10.4. Проверьте версию и целостность зависимостей

```bash
dpkg-query -W -f='${binary:Package}\t${Version}\t${Status}\n' "$LAB_APP" "$LAB_DATA"
cat "/usr/share/$LAB_ID/app.txt"
cat "/usr/share/$LAB_ID/data.txt"
sudo apt-get -c "$LAB_WORK/target-apt.conf" check
sudo dpkg --audit
```

`dpkg-query -W` показывает два установленных пакета; `-f` задаёт поля, `\t` разделяет их табуляцией, `\n` завершает строку. Одинарные кавычки защищают поля от Bash. `cat` читает фактические файлы. `apt-get check` проверяет согласованность зависимостей; `-c` сохраняет учебные настройки. `dpkg --audit` ищет незавершённые состояния пакетов.

**Пример результата:**

```text
point1-app-1000    1.1    install ok installed
point1-data-1000   1.0    install ok installed
Application version 1.1: training update applied.
Required training data version 1.0.
Reading package lists... Done
Building dependency tree
Reading state information... Done
```

`dpkg --audit` при нормальном состоянии ничего не выводит. Проверка затрагивает состояние пакетной базы всей машины: неожиданную ошибку не исправляйте удалением системных пакетов.

## 12. Очистка после сохранения результата

### 12.1. Проверьте и удалите только два учебных пакета

```bash
sudo apt-get -c "$LAB_WORK/target-apt.conf" --simulate purge "$LAB_APP" "$LAB_DATA"
```

`purge` удаляет названные пакеты и их учитываемые пакетной системой настройки. `--simulate` показывает план без изменений. `-c` выбирает учебные источники, `sudo` даёт те же права чтения, что и при реальном удалении.

**Пример результата:**

```text
The following packages will be REMOVED:
  point1-app-1000* point1-data-1000*
0 upgraded, 0 newly installed, 2 to remove ...
```

В плане должны быть только эти два пакета. Затем выполните:

```bash
sudo apt-get -c "$LAB_WORK/target-apt.conf" purge "$LAB_APP" "$LAB_DATA"
```

Значения параметров те же; без `--simulate` удаление настоящее. `--no-remove` здесь не используется, потому что удаление — цель команды.

**Пример результата:**

```text
Removing point1-app-1000 (1.1) ...
Removing point1-data-1000 (1.0) ...
```

Не запускайте общий `autoremove`: он может затронуть автоматически установленные пакеты, не относящиеся к этой работе.

### 12.2. Проверьте пути перед удалением каталогов

```bash
printf '%s\n' "$LAB_SOURCE" "$LAB_ROOT" "$LAB_WORK"
```

`printf '%s\n'` выводит по одному значению на строку. Флагов нет.

**Пример результата:**

```text
/etc/apt/sources.list.d/point1-1000.list
/var/lib/point1-1000
/home/student/point1-1000
```

Не продолжайте, если переменные пусты или пути отличаются от созданных в начале работы. После разрыва SSH сначала восстановите переменные блоком 4.1.

```bash
cd "$HOME"
if [ "$LAB_ID" = "point1-$(id -u)" ] && [ "$LAB_ROOT" = "/var/lib/$LAB_ID" ] && [ "$LAB_SOURCE" = "/etc/apt/sources.list.d/$LAB_ID.list" ] && [ "$LAB_WORK" = "$HOME/$LAB_ID" ]; then
    sudo rm -i -- "$LAB_SOURCE"
    sudo rm -rI -- "$LAB_ROOT"
    rm -rI -- "$LAB_WORK"
else
    printf '%s\n' 'Paths do not match this practice. Nothing was removed.'
fi
```

`cd "$HOME"` выводит оболочку из удаляемых каталогов. `if ... then ... else ... fi` выполняет удаление только при совпадении всех ожидаемых путей. `[ ... ]` проверяет условие, `=` сравнивает строки, `&&` требует успеха каждой проверки. `id -u` заново получает ваш UID.

`rm -i` спрашивает подтверждение удаления файла источника. `-r` рекурсивно удаляет содержимое каталога; большая `-I` запрашивает подтверждение перед рекурсивным удалением. `--` завершает список флагов. `sudo` используется только для объектов root. Здесь нет `-f`: при ошибках удаление не следует принудительно расширять. Подтверждайте каждый запрос только для показанного учебного пути; при отказе объекты останутся и их нужно будет удалить отдельно после проверки.

**Пример результата:**

```text
rm: remove regular file '/etc/apt/sources.list.d/point1-1000.list'?
rm: remove 1 argument recursively?
rm: remove 1 argument recursively?
```

Ответ подтверждения зависит от языка сообщений. После подтверждения файл источника и учебные каталоги удалены. Команда не удаляет весь `/var/lib` или домашний каталог.

### 12.3. Проверьте состояние системы

```bash
sudo dpkg --audit
dpkg-query -W -f='${binary:Package} ${Status}\n' "$LAB_APP" "$LAB_DATA"
```

`dpkg --audit` проверяет незавершённые состояния; нормальный результат — отсутствие вывода. `dpkg-query -W -f` пытается получить состояния только двух учебных пакетов.

**Ожидаемый результат:** `dpkg-query` сообщает, что пакеты не найдены. Это ожидаемо после `purge`. Общий `apt-get update` для очистки не нужен: индексы практики находились в удалённом выделенном каталоге.

## 13. Как перенести подход на настоящий шлюз

Этот раздел — отдельный вариант для двух машин. Не выполняйте его подряд после основной практики на единственной ВМ. На шлюзе используются настоящие доверенные репозитории, а на сервере — только доставленный комплект. Реальное исправление критического сервиса сначала испытывают на копии сервера: установка может выполнить сценарии пакета и перезапустить службу.

### 13.1. Что нужно сопоставить до загрузки

Шлюз подготовки должен иметь совместимые Astra Linux SE 1.7, архитектуру и набор разрешённых репозиториев. Недостаточно совпадения слова Linux. Версию исправления выбирают по уведомлению безопасности производителя и доступности в вашем контуре, а не по предположению о самой свежей версии.

Для расчёта зависимостей нужен снимок состояния целевого сервера. Пакеты, уже установленные на шлюзе, могут отсутствовать на сервере. Поэтому команда скачивания, ориентированная только на состояние шлюза, может получить неполный комплект.

**На целевом сервере:**

```bash
mkdir -p "$HOME/point1-transfer"
cp /var/lib/dpkg/status "$HOME/point1-transfer/target.status"
dpkg --print-architecture > "$HOME/point1-transfer/target.arch"
```

`mkdir -p` создаёт каталог передачи; `cp` копирует описание установленных пакетов без изменения базы. `dpkg --print-architecture` выводит основную архитектуру; `>` записывает её в файл. Флагов у `cp` нет.

**Ожидаемый результат:** текста нет, появились `target.status` и `target.arch`. Снимок содержит перечень ПО; переносите его по разрешённому каналу. Если на сервере используются дополнительные архитектуры или сложные правила приоритетов, подготовку должен учитывать администратор; этот вариант рассчитан на обычную однородную учебную систему.

### 13.2. Получение файлов по SSH без записи реквизитов в инструкцию

**На шлюзе**, из которого доступен SSH целевого сервера:

```bash
read -r -p 'Адрес целевого сервера: ' TARGET_HOST
read -r -p 'SSH-порт целевого сервера: ' TARGET_PORT
read -r -p 'Логин на целевом сервере: ' TARGET_USER
mkdir -p "$HOME/point1-gateway/bundle"
scp -P "$TARGET_PORT" "$TARGET_USER@$TARGET_HOST:point1-transfer/target.status" "$TARGET_USER@$TARGET_HOST:point1-transfer/target.arch" "$HOME/point1-gateway/"
```

`read` получает значение с клавиатуры. `-r` отключает специальное толкование обратной косой черты; `-p` задаёт текст приглашения. Пароль в переменную не вводится и в команды не добавляется. `mkdir -p` создаёт каталоги подготовки.

`scp` передаёт файлы через SSH. Большая `-P` задаёт порт: маленькая `-p` в `scp` имеет другой смысл. Аргументы вида `пользователь@адрес:путь` указывают файлы на сервере. Относительный путь здесь находится в домашнем каталоге указанного пользователя. Последний аргумент — локальный каталог шлюза.

**Пример результата:**

```text
target.status    100% ...
target.arch      100% ...
```

При первом соединении проверьте отпечаток ключа сервера по данным администратора. Не отключайте проверку ключей. Если из шлюза нет маршрута к серверу, используйте разрешённую промежуточную машину или носитель; менять маршруты и правила firewall целевого сервера ради упражнения не нужно.

### 13.3. Выберите конкретный пакет и версию

**На шлюзе:**

```bash
cat "$HOME/point1-gateway/target.arch"
dpkg --print-architecture
read -r -p 'Имя согласованного пакета: ' UPDATE_PACKAGE
apt-cache policy "$UPDATE_PACKAGE"
read -r -p 'Точная согласованная версия: ' UPDATE_VERSION
```

`cat` показывает архитектуру сервера, `dpkg --print-architecture` — архитектуру шлюза. Они должны совпасть для этого варианта. `read -r -p` получает имя и версию. `apt-cache policy` показывает известные версии и источники пакета, не устанавливая его.

**Пример структуры результата:**

```text
amd64
amd64
...
Installed: ...
Candidate: ...
Version table:
 ...
```

Здесь намеренно нет имени критического системного сервиса для бездумного копирования. Используйте согласованный пакет и версию из уведомления безопасности. Если подходящей версии нет, проверьте разрешённые источники шлюза; не подменяйте их источниками Ubuntu или Debian.

### 13.4. Рассчитайте комплект по состоянию целевого сервера

```bash
sudo apt-get -o "Dir::State::status=$HOME/point1-gateway/target.status" --simulate --no-remove --no-install-recommends install "$UPDATE_PACKAGE=$UPDATE_VERSION"
```

`-o` задаёт один параметр APT. `Dir::State::status=...` выбирает **копию** описания установленных пакетов сервера, чтобы решение о зависимостях учитывало его состояние. `--simulate` запрещает установку, `--no-remove` запрещает план с удалением, `--no-install-recommends` исключает необязательные рекомендации. `install имя=версия` выбирает согласованное исправление.

**Ожидаемый результат:** план с выбранным пакетом и необходимыми зависимостями. Это ещё не проверка всех особенностей настоящего сервера: окончательный план обязательно проверяется на нём. Не передавайте этот параметр в реальную установку на шлюзе: файл статуса используется только для расчёта и скачивания.

```bash
sudo apt-get -o "Dir::State::status=$HOME/point1-gateway/target.status" -o "Dir::Cache::archives=$HOME/point1-gateway/bundle" --download-only --reinstall --no-remove --no-install-recommends install "$UPDATE_PACKAGE=$UPDATE_VERSION"
```

Первая настройка `-o` по-прежнему выбирает снимок сервера. Вторая направляет загружаемые архивы в выделенный `bundle`. `--download-only` разрешает получение файлов и запрещает распаковку и установку. `--reinstall` позволяет получить названный пакет даже при совпадении версии со снимком. Остальные параметры ограничивают план, как при симуляции. Обязательные недостающие зависимости рассчитывает APT.

**Пример сокращённого результата:**

```text
Get:1 https://... ...
Get:2 https://... ...
Fetched ...
Download complete and in download only mode
```

В отличие от учебного `apt-get download` с явными двумя именами, здесь зависимости рассчитываются автоматически. Уже удовлетворённые по снимку зависимости повторно скачиваться не обязаны. Состояние сервера до установки должно соответствовать снимку. Если требуется самодостаточный комплект для нескольких разных серверов, одного снимка недостаточно.

### 13.5. Создайте индекс и ведомость на шлюзе

```bash
cd "$HOME/point1-gateway/bundle"
dpkg-scanpackages . /dev/null > Packages
sha256sum ./*.deb > SHA256SUMS
```

`cd` выбирает каталог архивов. `dpkg-scanpackages . /dev/null` создаёт индекс с относительными путями, `>` сохраняет его. `sha256sum` вычисляет суммы `.deb`; второй `>` записывает ведомость. Для индекса также можно использовать ранее разобранный `apt-ftparchive packages . > Packages`.

**Пример результата:**

```text
dpkg-scanpackages: info: Wrote ... entries to output Packages file.
```

Предупреждения об отсутствующих override-записях у настоящих пакетов не равны ошибке зависимости. Проверьте, что индекс содержит все доставляемые архивы. Если нет прав на чтение файлов, созданных через `sudo`, исправление прав должен выполнить владелец комплекта; не расширяйте права системных каталогов.

### 13.6. Передайте комплект на сервер

```bash
scp -P "$TARGET_PORT" ./*.deb Packages SHA256SUMS "$TARGET_USER@$TARGET_HOST:point1-transfer/"
```

`scp` отправляет все `.deb`, индекс и ведомость в ранее созданный каталог сервера. `-P` выбирает SSH-порт. `./*.deb` раскрывается в список архивов текущего каталога. Последний аргумент задаёт удалённое назначение.

**Пример результата:** строки имён файлов с индикатором `100%`. Если политика изолированного сегмента запрещает такой канал, используйте утверждённый перенос; этот вариант не требует открывать новый сетевой сервис на целевой машине.

**На целевом сервере:**

```bash
cd "$HOME/point1-transfer"
sha256sum -c SHA256SUMS
```

`cd` выбирает каталог получения; `sha256sum -c` сравнивает архивы с ведомостью.

**Ожидаемый результат:** `OK` для каждого архива. После этого администратор подключает защищённый локальный каталог по схеме разделов 8–10: копирование, индекс, отдельный `.list`, отдельная конфигурация APT, `update`, `policy`, симуляция и только затем согласованная установка. Имена учебных пакетов из основной практики здесь не используются.

На единственной удалённой машине ограничьтесь основной практикой. Самостоятельно обновлять настоящий SSH-сервер, ядро или критический сервис для её зачёта не требуется.

## 14. Если что-то не получилось

| Симптом | Что означает | Что проверить |
| --- | --- | --- |
| `command not found` для генератора индекса | Нет инструмента | Наличие второго генератора; подготовку индекса на шлюзе |
| `Permission denied` при чтении репозитория | Недостаточно прав на файл или проход по каталогу | Владельца root и права 0755 каталогов, 0644 файлов |
| `Unable to locate package` | APT не видит имя | `Package` в индексе, правильный `-c`, успешный `update` |
| `Version ... was not found` | Нет выбранной версии в индексах | `Version`, `policy`, повторную генерацию индекса после изменения `.deb` |
| `Unmet dependencies` | Не найден нужный пакет или версия | Доставку зависимости, её версию и запись `Depends` |
| `File not found` при получении `.deb` | Путь в `Filename` не соответствует каталогу | Генерацию индекса из корня репозитория с аргументом `.` |
| `Hash Sum mismatch` | Файл отличается от описания в индексе | Повторную проверку сумм, пересоздание индекса и затем `update` |
| `Could not get lock` | Работает другой пакетный процесс | Дождитесь его завершения; не удаляйте lock-файлы и не убивайте неизвестные процессы |
| `FAILED` при `sha256sum -c` | Архив повреждён или заменён | Повторный перенос из доверенного источника |

Не используйте для обхода ошибок `--force-*`, `--allow-unauthenticated`, удаление системных зависимостей или отключение средств защиты Astra Linux. При запрете политиками безопасности покажите администратору точную команду и вывод. SSH-доступ, мандатные механизмы и сетевые настройки в рамках этой практики не перенастраиваются.
